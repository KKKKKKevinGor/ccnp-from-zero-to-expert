# 04 · 802.1X 与 NAC

## ① 这章解决什么问题

**场景**：公司会议室有 8 个网口。

```
   ★ 现状 ★
   · 任何人插上网线 → 自动拿到 IP → ★ 进入内网 ★
   · 供应商、访客、外包，谁都能插
   · 有人把自己的路由器插上去，起了 DHCP，★ 整层楼断网 ★
   · 有人插了个未打补丁的笔记本，★ 勒索软件在内网横向传播 ★
        ↓
   ★★ "物理接入 = 网络授权" 这个假设已经不成立了 ★★
```

**NAC（Network Access Control，网络准入控制）要回答三个问题**：

```
   ★ 1. 你是谁？★        → 认证（Authentication）
   ★ 2. 你能干什么？★    → 授权（Authorization）
   ★ 3. 你的设备安全吗？★ → 合规检查（Posture）
```

**802.1X 是实现 NAC 的核心技术。**

## ② 原理讲透

### 2.1 ★ 三个角色 ★

```
   ┌──────────┐        ┌──────────────┐        ┌────────────┐
   │ Supplicant│  EAPOL │ Authenticator │ RADIUS │Authentication│
   │  请求者   │◄──────►│   认证者      │◄──────►│   Server    │
   │           │        │              │        │  认证服务器  │
   │ PC 上的   │        │ ★ 交换机 ★    │        │ ★ ISE ★     │
   │ 802.1X    │        │  (或 WLC)     │        │ (或 FreeRADIUS│
   │ 客户端    │        │              │        │  / NPS)     │
   └──────────┘        └──────────────┘        └────────────┘
        │                     │                       │
   ★ EAP over LAN ★      ★ 中继者 ★           ★ 真正做决策的 ★
   （EAPOL，二层）        自己不做决策            查用户库/证书
```

**★ 关键理解**：
```
   ★ 交换机【不知道】密码对不对 ★
   它只是把 EAP 报文在
   【EAPOL（二层）】和【RADIUS（UDP）】之间来回搬运
        ↓
   ★ 决策权在 RADIUS 服务器 ★
        ↓
   服务器回：
   · Access-Accept  → ★ 交换机打开端口 ★
   · Access-Reject  → ★ 交换机保持端口关闭 ★
   · Access-Challenge → 继续下一轮 EAP 交互
```

### 2.2 ★ 认证流程 ★

```
   ① 端口初始状态：★ 只允许 EAPOL，其他全丢 ★
        ↓
   ② 交换机周期性发 ★ EAP-Request/Identity ★
      （或 PC 插上后主动发 EAPOL-Start）
        ↓
   ③ PC 回 ★ EAP-Response/Identity ★（用户名）
        ↓
   ④ 交换机把它封装进 ★ RADIUS Access-Request ★ 发给服务器
        ↓
   ⑤ 服务器回 ★ Access-Challenge ★（EAP 方法协商、证书交换等）
      ↕ 多轮往返（具体轮数取决于 EAP 方法）
        ↓
   ⑥ 服务器验证通过 → ★ RADIUS Access-Accept ★
      ★ 里面可以携带授权属性：VLAN、ACL、SGT ★
        ↓
   ⑦ 交换机 ★ 打开端口 ★，并应用授权属性
        ↓
   ⑧ PC 发 DHCP → 拿 IP → 正常上网
```

**⚠️ 一个关键的时序问题**：
```
   ★ 认证在 DHCP【之前】★
        ↓
   如果动态下发 VLAN，PC 可能已经在旧 VLAN 拿了 IP
        ↓
   ★ 需要 PC 重新 DHCP ★
   （Windows 客户端一般会自动处理；
     ★ 但有些设备不会 → 这是"认证成功但没网"的常见根因 ★）
```

### 2.3 ★ EAP 方法对比 ★

| 方法 | 服务器证书 | ★ **客户端证书** | 安全性 | 部署难度 |
|:--|:--|:--|:--|:--|
| **EAP-MD5** | ❌ | ❌ | ★ ❌ **已废弃**（明文哈希，可爆破） | 低 |
| **PEAP-MSCHAPv2** | ✅ | ❌ | ⚠️ 中（用户名密码） | ★ **低**（最常用） |
| **EAP-TTLS** | ✅ | ❌ | 中 | 低 |
| ★ **EAP-TLS** | ✅ | ★ ✅ **需要** | ★ ✅ **最高** | ★ **高**（需要 PKI） |
| **EAP-FAST** | 可选 | 可选 | 中高 | 中（Cisco 专有） |
| **EAP-TEAP** | ✅ | 可选 | 高 | 中高（支持链式认证） |

**★ EAP-TLS 为什么最安全**：
```
   ★ 双向证书认证 ★
   · 服务器验证客户端证书 → 确认设备/用户身份
   · 客户端验证服务器证书 → ★ 防止假冒的 RADIUS 服务器 ★
        ↓
   ★ 没有密码可以被钓鱼/爆破/撞库 ★
        ↓
   ⚠️ 代价：必须有 PKI，要给每台设备签发和轮换证书
```

**★ PEAP 的隐患**：
```
   如果客户端【不验证服务器证书】（很多用户会点"始终信任"）
        ↓
   攻击者架一个假 AP + 假 RADIUS
        ↓
   ★★ 捕获 MSCHAPv2 挑战响应 → 离线爆破密码 ★★
        ↓
   ★ 所以用 PEAP 必须强制客户端验证服务器证书 ★
   （通过组策略下发配置，不让用户自己勾）
```

### 2.4 ★ 不支持 802.1X 的设备怎么办 ★

**现实**：打印机、IP 电话、摄像头、门禁、扫码枪、老旧工控设备——**大部分没有 802.1X 客户端**。

```
   ★ MAB（MAC Authentication Bypass）★
   
   交换机等待 802.1X 超时后
        ↓
   ★ 用设备的 MAC 地址作为【用户名和密码】★
   发 RADIUS Access-Request
        ↓
   服务器查 MAC 白名单
        ↓
   在白名单里 → ★ Access-Accept（可以给专属 VLAN）★
```

**⚠️ MAB 的安全性很弱**：
```
   ★ MAC 地址可以随便伪造 ★
        ↓
   攻击者拔掉打印机，改自己网卡的 MAC，插上去
        ↓
   ★ 直接进入打印机 VLAN ★
        ↓
   ★ 缓解措施 ★
   · ★ 给 MAB 设备一个【严格受限】的 VLAN + ACL ★
     （只能访问打印服务器，不能访问其他任何东西）
   · 配合 ★ Profiling ★（ISE 通过 DHCP 指纹、HTTP UA、
     CDP/LLDP、SNMP 判断"这真的是打印机吗"）
   · ★ 微分段 ★：IoT 设备之间也不互通
```

### 2.5 ★ 认证顺序与优先级 ★

```cisco
! ★ 顺序：先试 802.1X，超时后试 MAB ★
authentication order dot1x mab
authentication priority dot1x mab
```

```
   ★ order ★：★ 按什么顺序【尝试】★
   ★ priority ★：如果多种方式都成功，★ 哪个说了算 ★
   
   ★ 典型配置：order dot1x mab ★
   · 先发 EAP-Identity 请求
   · 等 tx-period × max-reauth-req（默认 30×2=60 秒）
   · ★ 超时 → 降级到 MAB ★
   
   ⚠️ ★ 这 60 秒的等待会让打印机开机后 1 分钟才能用 ★
      优化：对确定是 MAB 的端口，把顺序改成 mab dot1x
           或缩短 tx-period
```

### 2.6 ★ Host Mode（端口上能有几个设备）★

| 模式 | 含义 | ★ 用途 ★ |
|:--|:--|:--|
| **`single-host`** | ★ **只允许 1 个 MAC** | 最严格 |
| **`multi-host`** | ★ **第一个认证通过，后面的全部放行** | ⚠️ **不安全**，不推荐 |
| ★ **`multi-domain`** | ★ **1 个数据域 + 1 个语音域** | ★ **IP 电话 + PC 串接（最常用）** |
| ★ **`multi-auth`** | ★ **每个 MAC 独立认证** | ★ **下挂哑交换机/虚拟机（最安全）** |

**★ `multi-host` 为什么危险**：
```
   端口上接了一个小交换机
        ↓
   第一台 PC 认证通过
        ↓
   ★★ 后面接的所有设备都不用认证，直接放行 ★★
        ↓
   ★ 等于没有 802.1X ★
        ↓
   ★ 有这种需求就用 multi-auth ★
```

**★ `multi-domain` 的典型场景**：
```
   ┌─────────┐        ┌────────┐        ┌────┐
   │  交换机  │────────│ IP 电话 │────────│ PC │
   └─────────┘        └────────┘        └────┘
        ↑                  ↑                ↑
   一个物理端口     ★ 语音域 ★         ★ 数据域 ★
                   VLAN 100            VLAN 10
                   （电话认证）         （PC 认证）
   
   ★ 两个设备【各自独立认证】，各自进各自的 VLAN ★
```

### 2.7 ★★ 降级机制（生产必配）★★

**★ 最可怕的场景：RADIUS 服务器挂了 → 全公司所有人都上不了网。**

| 机制 | 触发条件 | ★ 行为 ★ |
|:--|:--|:--|
| ★ **Critical Auth（Inaccessible Auth Bypass）** | ★ **RADIUS 不可达** | ★ **放行到指定 VLAN**（业务不中断） |
| **Guest VLAN** | ★ **客户端不支持 802.1X**（不响应 EAPOL） | 放到访客 VLAN |
| **Auth-Fail VLAN (Restricted)** | ★ **认证失败**（密码错） | 放到受限 VLAN |

**★ 三者的区别（考点）**：
```
   ★ Guest VLAN ★
      → 客户端【压根没回应】EAPOL（说明没装 802.1X 客户端）
      → 例：访客的私人笔记本
   
   ★ Auth-Fail VLAN ★
      → 客户端【回应了】，但认证【失败】（密码错、证书无效）
      → 例：员工密码过期
   
   ★★ Critical VLAN ★★
      → 客户端可能是好的，但【RADIUS 服务器联系不上】
      → ★ 这是【网络故障】，不是【用户问题】★
      → ★ 必须放行，否则全公司瘫痪 ★
```

> ⚠️ **★ 生产环境不配 Critical Auth = 给自己埋一颗核弹。**
> RADIUS 服务器维护、网络中断、证书过期，任何一个都能让全公司断网。

## ③ 配置命令

### 3.1 ★ 完整的 802.1X 配置（Cisco IOS-XE，新式 IBNS 2.0）★

```cisco
!═══════ ① AAA 基础 ═══════
aaa new-model

! ★ RADIUS 服务器（配两台做冗余）★
radius server ISE-1
 address ipv4 10.1.1.10 auth-port 1812 acct-port 1813
 key MyRadiusSecret123
 ★ automate-tester username probe-user idle-time 5 ★

radius server ISE-2
 address ipv4 10.1.1.11 auth-port 1812 acct-port 1813
 key MyRadiusSecret123
 automate-tester username probe-user idle-time 5

aaa group server radius ISE-GROUP
 server name ISE-1
 server name ISE-2
 ★ deadtime 5 ★

! ★ 认证 / 授权 / 计费 ★
aaa authentication dot1x default group ISE-GROUP
aaa authorization network default group ISE-GROUP
aaa accounting dot1x default start-stop group ISE-GROUP

! ★ 允许服务器下发 CoA（动态改变授权）★
aaa server radius dynamic-author
 client 10.1.1.10 server-key MyRadiusSecret123
 client 10.1.1.11 server-key MyRadiusSecret123

! ★ 允许 RADIUS 下发 VLAN / ACL / SGT ★
aaa authorization config-commands
radius-server attribute 6  on-for-login-auth
radius-server attribute 8  include-in-access-req
radius-server attribute 25 access-request include
ip radius source-interface Loopback0

!═══════ ② 全局开启 802.1X ═══════
★ dot1x system-auth-control ★
dot1x critical eapol

! ★ IBNS 2.0：新式配置模型 ★
authentication display new-style

!═══════ ③ Critical Auth（★ 保命 ★）═══════
class-map type control subscriber match-all AAA-DOWN
 ★ match result-type aaa-timeout ★

class-map type control subscriber match-all DOT1X-NO-RESP
 match method dot1x
 match result-type method dot1x agent-not-found

class-map type control subscriber match-all DOT1X-FAILED
 match method dot1x
 match result-type method dot1x authoritative

class-map type control subscriber match-all MAB-FAILED
 match method mab
 match result-type method mab authoritative

!═══════ ④ 策略（认证状态机）═══════
policy-map type control subscriber POLICY-DOT1X-MAB
 event session-started match-all
  10 class always do-until-failure
   10 authenticate using dot1x priority 10

 event authentication-failure match-first
  ! ★ RADIUS 挂了 → Critical VLAN ★
  10 class AAA-DOWN do-until-failure
   10 ★ authorize ★
   20 ★ activate service-template CRITICAL-ACCESS ★
   30 terminate dot1x
   40 terminate mab
  ! ★ 客户端不支持 802.1X → 降级 MAB ★
  20 class DOT1X-NO-RESP do-until-failure
   10 terminate dot1x
   20 ★ authenticate using mab priority 20 ★
  ! ★ 802.1X 认证失败 → 也试试 MAB ★
  30 class DOT1X-FAILED do-until-failure
   10 terminate dot1x
   20 authenticate using mab priority 20
  ! ★ MAB 也失败 → 访客 VLAN ★
  40 class MAB-FAILED do-until-failure
   10 ★ activate service-template GUEST-ACCESS ★
  50 class always do-until-failure
   10 terminate dot1x
   20 terminate mab
   30 authentication restart 60

 event aaa-available match-all
  ! ★ RADIUS 恢复了 → 重新认证 ★
  10 class always do-until-failure
   10 clear-session

 event agent-found match-all
  10 class always do-until-failure
   10 terminate mab
   20 authenticate using dot1x priority 10

! ★ 服务模板 ★
service-template CRITICAL-ACCESS
 ★ vlan 999 ★
 description RADIUS不可达时的降级VLAN

service-template GUEST-ACCESS
 ★ vlan 900 ★
 access-group ACL-GUEST-RESTRICT
 description 访客受限VLAN

!═══════ ⑤ 接口配置 ═══════
interface range GigabitEthernet1/0/1-40
 switchport mode access
 switchport access vlan 10
 switchport voice vlan 100

 ! ★ 接入层安全基线 ★
 spanning-tree portfast
 spanning-tree bpduguard enable

 ! ★ 802.1X ★
 ★ access-session host-mode multi-domain ★
 ★ access-session port-control auto ★
 ★ access-session closed ★
 ★ mab ★
 dot1x pae authenticator
 dot1x timeout tx-period 7
 dot1x max-reauth-req 2
 ★ subscriber aging inactivity-timer 60 probe ★
 ★ service-policy type control subscriber POLICY-DOT1X-MAB ★
```

### 3.3 ★★ 三阶段部署法（生产环境必须遵守）★★

```
   ★★ 绝对不要直接上"强制模式"，会让全公司断网 ★★

   ┌────────────────────────────────────────────────┐
   │ ★ 阶段 1：Monitor Mode（监控模式）★             │
   │ authentication open       ← ★ 关键 ★            │
   │                                                 │
   │ · 认证失败也【放行】                             │
   │ · ★ 只是记录日志 ★                              │
   │ · 用来【发现】：                                 │
   │   - 哪些设备不支持 802.1X                        │
   │   - 哪些设备的证书有问题                          │
   │   - 哪些 MAC 需要加白名单                         │
   │ · ★ 至少跑 2-4 周 ★                             │
   ├────────────────────────────────────────────────┤
   │ ★ 阶段 2：Low-Impact Mode（低影响模式）★         │
   │ authentication open + ★ 预置 ACL ★              │
   │                                                 │
   │ ip access-list extended ACL-PREAUTH             │
   │  permit udp any any eq 67 68     ← DHCP         │
   │  permit udp any any eq 53        ← DNS          │
   │  permit tcp any host <PXE服务器> eq 80           │
   │  deny   ip any any                              │
   │ interface ...                                    │
   │  ip access-group ACL-PREAUTH in                 │
   │                                                 │
   │ · 认证前只能访问【最基本的服务】                   │
   │ · 认证后 RADIUS 下发完整权限                      │
   │ · ★ 兼顾安全和可用性，很多企业停在这一步 ★         │
   ├────────────────────────────────────────────────┤
   │ ★ 阶段 3：Closed Mode（强制模式）★               │
   │ ★ access-session closed ★                       │
   │                                                 │
   │ · 认证前【什么都不允许】（只有 EAPOL）             │
   │ · ★ 最安全 ★                                    │
   │ · ⚠️ PXE 网络启动、Wake-on-LAN 会受影响           │
   └────────────────────────────────────────────────┘
```


```
★ Domain: DATA ★                    ← 数据域还是语音域

Server Policies:
      ★ Vlan Group: Vlan: 10 ★      ← RADIUS 下发的 VLAN

      ★ SGT Value: 10 ★             ← 下发的 SGT

      Method     ★ State ★
      ★ dot1x    Authc Success ★    ← 802.1X 成功
      mab        Stopped
```

**★ State 的常见值和含义**：
| State | 含义 | 下一步 |
|:--|:--|:--|
| ★ **Authc Success** | 认证成功 | ✅ |
| **Authc Failed** | ★ **认证失败**（密码/证书错） | 查 ISE 日志 |
| ★ **Running** | 正在认证中 | 等或看是否卡住 |
| ★ **Not run** | ★ **没有触发**（客户端没发 EAPOL） | 检查客户端配置 |
| **Stopped** | 被策略终止（正常，比如降级到 MAB） | ✅ |
| ★ **Authz Failed** | 认证成功但**授权失败** | ★ VLAN 不存在 / ACL 下发失败 ★ |

**拓扑**：

```bash
        Tunnel-Type = VLAN,
        Tunnel-Medium-Type = IEEE-802,

# MAB：MAC 作为用户名和密码（注意格式）
```

**④ ★★ 故障注入 ★★**

## ⑦ 自测题

**1.** Guest VLAN、Auth-Fail VLAN、Critical VLAN 分别在什么条件下触发？为什么 Critical VLAN 在生产环境是必配的？

<details><summary>答案</summary>

**★ 三者的触发条件完全不同**：

| | **触发条件** | **典型场景** | 本质 |
|:--|:--|:--|:--|
| ★ **Guest VLAN** | ★ **客户端完全不响应 EAPOL** | 访客的私人笔记本、没装 802.1X 客户端的设备 | **设备不支持** |
| ★ **Auth-Fail VLAN**<br>(Restricted VLAN) | ★ **客户端【响应了】但认证【失败】** | 员工密码过期、证书无效、账号被禁用 | **凭据有问题** |
| ★★ **Critical VLAN** ★★<br>(Inaccessible Auth Bypass) | ★★ **RADIUS 服务器【联系不上】** ★★ | RADIUS 维护、网络中断、ISE 崩溃 | ★ **网络故障，不是用户问题** ★ |

**★ 关键区分**：
```
   ★ Guest ★：交换机发了 EAP-Identity，
                ★ 等了 tx-period × max-reauth-req 都没人回 ★
                → 说明这台设备根本没装客户端
   
   ★ Auth-Fail ★：客户端回了，走完了 EAP 交互，
                   ★ RADIUS 明确返回了 Access-Reject ★
                   → 服务器说"这个人不行"
   
   ★ Critical ★：★ 交换机根本联系不上 RADIUS ★
                  （超时、无响应）
                  → ★ 服务器没说话，不是"拒绝"，是"失联" ★
```

**★ 配置对照**：
```cisco
! 旧式（IBNS 1.0）
authentication event no-response action authorize vlan 900   ← Guest
authentication event fail        action authorize vlan 901   ← Auth-Fail
★ authentication event server dead action authorize vlan 999 ★ ← Critical
★ authentication event server alive action reinitialize ★      ← 恢复后重认证

! 新式（IBNS 2.0）用 class-map
class-map type control subscriber match-all AAA-DOWN
 ★ match result-type aaa-timeout ★
```

---

**★★ 为什么 Critical VLAN 是必配项 ★★**

**不配的后果**：
```
   周六凌晨 2 点，ISE 服务器打补丁重启
        ↓
   或者：核心交换机故障，交换机到 ISE 的路径断了
   或者：ISE 的证书过期了
   或者：有人误改了 ISE 的策略
        ↓
   ★★ 交换机联系不上 RADIUS ★★
        ↓
   所有 802.1X 端口的认证全部超时
        ↓
   ★★★ 全公司所有有线用户【瞬间断网】★★★
        ↓
   · 生产线停了
   · 客服接不了电话（IP 电话也认证不了）
   · ★ 你自己也 SSH 不上交换机去救（如果管理也走 802.1X）★
   · 只能跑机房插 Console 线
```

**★ 这不是假设，是每年都在各个公司真实发生的事故。**

**配了之后**：
```
   RADIUS 联系不上
        ↓
   ★ 交换机自己做决定：先放行到 VLAN 999 ★
        ↓
   · 业务继续跑（VLAN 999 可以给一个受限但够用的权限）
   · 你有时间从容修复 RADIUS
        ↓
   ★ authentication event server alive action reinitialize ★
        ↓
   RADIUS 恢复后，★ 交换机自动重新认证所有端口 ★
   → 用户无感知地回到正确的 VLAN
```

**★ 配套必须做的事**：

**① 探测机制（让交换机快速发现 RADIUS 挂了）**
```cisco
radius server ISE-1
 address ipv4 10.1.1.10 auth-port 1812 acct-port 1813
 key MyRadiusSecret123
 ★ automate-tester username probe-user idle-time 5 ★
 ! 每 5 分钟主动发一个测试请求，快速发现 dead
```

**② Critical VLAN 的权限设计**
```
   ★ 不要给 Critical VLAN 全网权限 ★
   （否则 RADIUS 一挂 = 所有人变管理员）
   
   ★ 建议：给一个"够用但受限"的权限 ★
   · 能访问核心业务系统
   · 不能访问服务器管理网段
   · 不能访问其他部门的敏感数据
   · ★ 记录日志，事后审计谁在降级期间接入了 ★
```

**③ 语音也要配**
```cisco
★ dot1x critical eapol ★
authentication event server dead action authorize voice
```
**否则 RADIUS 挂了 IP 电话也打不了。**

**④ 冗余 RADIUS**
```cisco
aaa group server radius ISE-GROUP
 server name ISE-1
 server name ISE-2
 ★ deadtime 5 ★
```
**★ Critical Auth 是最后一道保险，不是替代冗余。**

**2.** MAB 的安全性为什么很弱？在必须使用 MAB 的场景下（打印机、摄像头、门禁），应该怎么缓解风险？

<details><summary>答案</summary>

**★ MAB 弱在哪里 ★**

```
   ★ MAB 的本质：用 MAC 地址当【用户名】和【密码】★
        ↓
   ★ 而 MAC 地址是：★
   · ★ 明文在网络上广播的 ★（任何人抓包就能拿到）
   · ★ 可以随意伪造 ★（Windows/Linux 改网卡 MAC 只要一条命令）
   · 不会过期、不会轮换
   · 贴在设备背面的标签上
        ↓
   ★★ 等于把密码写在设备外壳上，还到处广播 ★★
```

**攻击过程（3 分钟）**：
```
   ① 找到一台打印机 → 从标签或 ARP 表读它的 MAC
        ↓
   ② 拔掉打印机网线
        ↓
   ③ 把自己笔记本的 MAC 改成打印机的 MAC
      Linux: ip link set eth0 address 00:11:22:33:44:55
        ↓
   ④ 插上网线
        ↓
   ★★ MAB 认证通过，进入打印机 VLAN ★★
```

---

**★ 缓解措施（分层）★**

**① ★ 最小权限的 VLAN + dACL（最重要）★**
```
   ★ 核心思路：假设 MAB 一定会被绕过，
     那就让"绕过之后也拿不到什么" ★
   
   打印机 VLAN 的 ACL：
```
```cisco
ip access-list extended ACL-PRINTER
 ! 只允许访问打印服务器的打印端口
 permit tcp any host 10.1.1.50 eq 9100
 permit tcp any host 10.1.1.50 eq 631
 permit udp any host 10.1.1.50 eq 161
 ! DHCP / DNS
 permit udp any any eq 67
 permit udp any host 10.1.1.53 eq 53
 ! ★ 其他全拒绝 ★
 ★ deny ip any any log ★
```
```
   ★ 效果：攻击者伪造成打印机进来了，
     但只能连打印服务器的 9100 端口，
     ★ 横向移动完全被堵死 ★
```

**② ★ Profiling（设备画像）★**
```
   ISE 通过多种信号判断"这真的是打印机吗"：
   · ★ DHCP 指纹 ★（Option 55 参数请求列表的顺序）
   · ★ HTTP User-Agent ★
   · ★ CDP / LLDP 上报的设备类型 ★
   · ★ SNMP 查设备的 sysDescr / sysObjectID ★
   · ★ NMAP 扫描开放端口特征 ★
   · ★ MAC OUI ★（前 24 位 = 厂商）
        ↓
   ★ 伪造 MAC 容易，但要同时伪造
     DHCP 指纹 + HTTP UA + SNMP 响应 + 端口特征
     难度大幅上升 ★
        ↓
   ★ 配合 CoA：一旦 Profiling 发现"这台设备行为
     不像打印机了"，★ 立刻下发 CoA 断开或改权限 ★
```

**③ ★ 微分段（IoT 设备之间也不互通）★**
```cisco
! 同一个 VLAN 内的设备互相隔离
interface range Gi1/0/1-20
 ★ switchport protected ★

! 或者用 Private VLAN
! 或者用 SGT：IoT → IoT = Deny
```
```
   ★ 防止一台被攻陷的摄像头去攻击另一台摄像头 ★
```

**④ ★ MAC 白名单的严格管理 ★**
```
   · ★ 白名单必须是【显式登记】的，不能自动学习 ★
   · 定期审计：这个 MAC 还在用吗？设备还在吗？
   · 设备报废时★ 立刻从白名单删除 ★
   · ★ MAB 账号绑定端口/位置 ★
     （ISE 策略：这个 MAC 只允许在 3 楼的这几个端口上认证）
```

**⑤ ★ 端口级加固 ★**
```cisco
interface Gi1/0/30
 ★ access-session host-mode single-host ★   ← 只允许 1 个 MAC
 ★ authentication violation restrict ★
 ★ switchport port-security maximum 1 ★
 ★ switchport port-security violation restrict ★
```

**⑥ ★ 长远方案：证书 ★**
```
   现代的打印机/摄像头★ 越来越多支持 802.1X（EAP-TLS）★
        ↓
   采购时★ 把"支持 802.1X"写进技术规格 ★
        ↓
   ★ 逐步淘汰 MAB ★
```

**★ 总结的心智模型**：
```
   ★ MAB 不是"认证"，是"识别" ★
   
   它只能回答"这台设备看起来是什么"，
   ★ 不能回答"这台设备真的是它声称的那个吗" ★
        ↓
   ★ 所以 MAB 设备的权限必须按
     "这个身份随时可能被冒充"来设计 ★
```
</details>

**3.** 为什么生产环境部署 802.1X 必须走"三阶段"？直接上 Closed Mode 会发生什么？

<details><summary>答案</summary>

**★ 直接上 Closed Mode 的后果 ★**

```
   周一早上 9 点，你把全公司 800 个端口一次性切到 Closed Mode
        ↓
   ★★ 灾难现场 ★★
   
   ① ★ 打印机全部离线 ★
      → 没人提前统计过 MAC，白名单是空的
   
   ② ★ 会议室的视频设备连不上 ★
      → 不支持 802.1X，也不在白名单
   
   ③ ★ IP 电话认证不了 ★
      → 没配 multi-domain host-mode
   
   ④ ★ 一批老 Windows 机器连不上 ★
      → Wired AutoConfig 服务是关的（Windows 默认关闭！）
   
   ⑤ ★ 门禁系统断了 ★
      → 大楼门打不开
   
   ⑥ ★ PXE 网络装机全部失败 ★
      → Closed Mode 挡了 DHCP/TFTP
   
   ⑦ ★ Linux/Mac 客户端配置不对 ★
      → 证书链不完整
   
   ⑧ ★ 你自己也上不去交换机 ★
      → 如果管理网段也走了 802.1X
        ↓
   ★★ 结果：紧急回滚，项目被叫停，你被约谈 ★★
```

**★ 根本问题：你不知道网络里到底有什么设备。**

---

**★ 三阶段部署法 ★**

```
   ┌─────────────────────────────────────────────────┐
   │ ★★ 阶段 1：Monitor Mode（监控模式）★★           │
   │                                                  │
   │  interface range Gi1/0/1-48                      │
   │   ★ authentication open ★     ← 关键             │
   │   authentication port-control auto               │
   │   mab                                            │
   │   dot1x pae authenticator                        │
   │                                                  │
   │  ★ 行为：认证失败也【照样放行】★                  │
   │  ★ 目的：【只收集数据，不影响业务】★              │
   │                                                  │
   │  ★ 要收集的信息：★                               │
   │  · 哪些设备认证成功了（这些没问题）                │
   │  · ★ 哪些设备完全没响应 EAPOL ★                  │
   │    → 需要加 MAB 白名单，或推客户端配置             │
   │  · ★ 哪些设备认证失败 ★                          │
   │    → 证书问题？账号问题？                          │
   │  · ★ 全网 MAC 清单 ★（用于建 MAB 白名单）        │
   │                                                  │
   │  ★ 时长：至少 2-4 周 ★                           │
   │  （要覆盖：月末结算、季度盘点、临时设备接入等       │
   │    低频场景）                                     │
   │                                                  │
   │  ★ 数据来源：★                                   │
   │  · ISE 的 Live Logs（最全）                       │
   │  · show access-session（交换机侧）                │
   │  · RADIUS 计费日志                                │
   ├─────────────────────────────────────────────────┤
   │ ★★ 阶段 2：Low-Impact Mode（低影响模式）★★       │
   │                                                  │
   │  ★ authentication open ★ + ★ 预置 ACL ★         │
   │                                                  │
   │  ip access-list extended ACL-PREAUTH             │
   │   permit udp any any eq bootps      ← DHCP       │
   │   permit udp any any eq domain      ← DNS        │
   │   permit tcp any host <PXE> eq 80                │
   │   permit udp any host <PXE> eq tftp              │
   │   permit udp any host <NTP> eq ntp               │
   │   ★ deny ip any any log ★                        │
   │                                                  │
   │  interface range Gi1/0/1-48                      │
   │   ★ ip access-group ACL-PREAUTH in ★            │
   │                                                  │
   │  ★ 行为：★                                       │
   │  · 认证【之前】：只能访问 DHCP/DNS/PXE            │
   │  · 认证【之后】：RADIUS 下发 dACL，覆盖预置 ACL    │
   │                                                  │
   │  ★ 好处：★                                       │
   │  · ★ 未认证设备被严格限制，但不会完全断网 ★       │
   │  · ★ PXE 网络启动仍然可用 ★                      │
   │  · 遗漏的设备造成的影响可控                        │
   │                                                  │
   │  ★ 很多企业【长期停在这一步】，这是合理的 ★       │
   ├─────────────────────────────────────────────────┤
   │ ★★ 阶段 3：Closed Mode（强制模式）★★            │
   │                                                  │
   │  interface range Gi1/0/1-48                      │
   │   ★ no authentication open ★                     │
   │   （IBNS 2.0：access-session closed）             │
   │                                                  │
   │  ★ 行为：认证前【只有 EAPOL 能通】★              │
   │  ★ 最安全 ★                                      │
   │                                                  │
   │  ⚠️ 前提条件（缺一不可）：★                      │
   │  · MAB 白名单已经完整                             │
   │  · ★ Critical Auth 已配置并【测试过】★           │
   │  · Guest / Auth-Fail VLAN 已配                    │
   │  · ★ PXE 装机改用其他方式（或保留部分端口）★     │
   │  · 有回滚方案和回滚脚本                            │
   │  · ★ 分批推进：先一层楼 → 观察一周 → 再推 ★      │
   └─────────────────────────────────────────────────┘
```

**★ 每个阶段的推进标准**：

| 从 → 到 | ★ 推进条件 ★ |
|:--|:--|
| Monitor → Low-Impact | ★ 连续 1 周没有新的"未知设备"出现 ★；MAB 白名单覆盖率 >99% |
| Low-Impact → Closed | ★ Critical Auth 演练通过 ★；PXE 有替代方案；试点楼层跑满 2 周无工单 |

**★ 额外的保命措施**：
```cisco
! ★ 下发前开启配置回滚保险 ★
configure terminal revert timer 15
  ... 下发配置 ...
! 验证通过后
configure confirm

! ★ 如果 15 分钟内没 confirm，配置自动回滚 ★
! → 就算把自己锁死了，15 分钟后自动恢复
```

```
   ★ 还要预留"逃生端口"★
   
   每台交换机★ 保留 1-2 个端口不做 802.1X ★
   （物理上锁在机柜里，或者只有网管知道）
        ↓
   ★ 出事时可以插上笔记本救场 ★
   
   同时确保：★ 管理网段/带外管理不走 802.1X ★
```

**★ 一句话总结**：
```
   ★★ 802.1X 项目 90% 的工作量不在配置，
      在【摸清网络里到底有什么设备】★★
   
   Monitor Mode 就是干这个的。
   跳过它 = 在不知道有什么的情况下把门锁上。
```
</details>
