# 05 · 零信任与网络分段

> ★ 这是本模块最重要的一章，也是 **ENCOR 考纲 5.5「描述网络安全设计」** 的核心内容。

---

## ① 这章解决什么问题

**一个真实的勒索软件事故复盘**：

```
   ★ Day 0，14:30 ★
   财务部一位员工点开了一封"发票"邮件的附件
        ↓
   ★ 14:31 ★
   恶意软件在这台 PC 上运行
        ↓
   ★ 14:35 ★
   扫描内网 → ★ 发现同一个 VLAN 里还有 200 台 PC ★
        ↓
   ★ 14:40 ★
   利用未打补丁的 SMB 漏洞 → ★ 445 端口全网开放 ★
   → 横向传播到 50 台机器
        ↓
   ★ 15:20 ★
   拿到一个域管账号 → ★ 访问服务器网段 ★
   （因为核心交换机上"内网互通"是默认配置）
        ↓
   ★ 18:00 ★
   ★★ 全公司 600 台设备被加密，包括文件服务器和备份服务器 ★★
        ↓
   ★ 复盘结论 ★
   · 边界防火墙：★ 完好无损，一点用没有 ★
   · 杀毒软件：★ 拦住了一部分，没拦住全部 ★
   · ★★ 真正的问题：内网是"一马平川"的 ★★
```

**★ 核心教训**：
```
   ★★ 边界防护只能防"外面进来"，
      防不了"里面扩散" ★★
        ↓
   而现代攻击的路径是：
   钓鱼/供应链/内鬼 → ★ 直接落在内网里 ★ → 横向移动
        ↓
   ★★ 边界从一开始就被绕过了 ★★
```

**这一章讲的是：怎么让"里面"也不再是一马平川。**

## ② 原理讲透

### 2.1 ★ 从"城堡护城河"到"零信任"★

```
   ┌───────────────────────────────────────────────┐
   │ ★ 传统模型：城堡与护城河 ★                     │
   │                                                │
   │        🌐 互联网（不可信）                      │
   │             │                                  │
   │        ┌────▼────┐                             │
   │        │ 防火墙   │ ← ★ 唯一的检查点 ★          │
   │        └────┬────┘                             │
   │             │                                  │
   │   ┌─────────▼─────────┐                        │
   │   │  ★ 内网（可信）★   │                        │
   │   │  PC ↔ PC ↔ 服务器  │ ← ★ 全部互通 ★         │
   │   │  ↕    ↕    ↕      │                        │
   │   └───────────────────┘                        │
   │                                                │
   │ ★ 假设：进来了就是自己人 ★                      │
   └───────────────────────────────────────────────┘
                    ↓ 为什么崩了
   ┌───────────────────────────────────────────────┐
   │ ① ★ 边界消失了 ★                               │
   │   云、SaaS、远程办公 → "内网"在哪里？            │
   │ ② ★ 攻击直接落地内网 ★                         │
   │   钓鱼、供应链、U 盘、内鬼 → 绕过边界             │
   │ ③ ★ BYOD 和 IoT ★                              │
   │   不受管控的设备大量接入                          │
   │ ④ ★ 勒索软件证明了横向移动的破坏力 ★            │
   └───────────────────────────────────────────────┘
                    ↓
   ┌───────────────────────────────────────────────┐
   │ ★★ 零信任：Never Trust, Always Verify ★★       │
   │                                                │
   │  ★ 不再基于【位置】授权 ★                       │
   │     （"你在内网 = 你可信" ❌）                   │
   │  ★ 而是基于【身份 + 设备状态 + 上下文】授权 ★    │
   │                                                │
   │   用户 ─┐                                      │
   │   设备 ─┼→ ★ 策略引擎 ★ → 允许/拒绝/受限        │
   │   位置 ─┤    (每一次访问都判断)                  │
   │   时间 ─┤                                      │
   │   行为 ─┘                                      │
   └───────────────────────────────────────────────┘
```

### 2.2 ★★ 零信任的三大原则 ★★

```
   ★ 1. 显式验证（Verify Explicitly）★
      · 每一次访问请求都要验证
      · 不是"登录一次，全天畅通"
      · 验证依据：身份 + 设备健康 + 位置 + 行为 + 数据敏感度
   
   ★ 2. 最小权限（Least Privilege）★
      · 只给完成任务所需的最小权限
      · JIT（Just-In-Time）：需要时才给，用完收回
      · JEA（Just-Enough-Access）：够用就行
   
   ★ 3. 假设已被攻破（Assume Breach）★
      · ★ 这条最反直觉，也最重要 ★
      · 不问"怎么防止被攻破"，而问
        ★ "已经被攻破了，怎么限制损失" ★
      · → ★ 微分段、端到端加密、持续监控 ★
```

**★ "Assume Breach" 如何改变设计**：
```
   ★ 传统思路 ★
   "怎么不让攻击者进来？"
   → 投入全在边界
   → ★ 一旦被突破，全盘皆输 ★
   
   ★ 零信任思路 ★
   "假设攻击者【已经】在财务部那台 PC 上了，
     ★ 他能走多远？★"
   → 如果答案是"整个公司"→ ★ 设计有问题 ★
   → 如果答案是"只能访问财务系统的这三个端口"
     → ★ 设计正确 ★
```

### 2.3 ★ 网络分段的四个层次 ★

```
   ┌──────────────────────────────────────────────────┐
   │ ★ L1：VLAN 分段（二层隔离）★                      │
   │  · 按部门/功能划 VLAN                              │
   │  · ⚠️ ★ 只隔离二层广播域 ★                        │
   │  · ⚠️ ★ 三层默认还是全通的 ★（有 SVI 就互通）      │
   │  · 粒度：粗                                        │
   │  ★ 这是绝大多数企业的现状，也是不够的原因 ★         │
   ├──────────────────────────────────────────────────┤
   │ ★ L2：ACL / 防火墙分段（三层策略）★                │
   │  · VLAN 间用 ACL 或防火墙控制                       │
   │  · ✅ 真正实现了隔离                                │
   │  · ⚠️ ★ 基于 IP 地址 → 地址一变策略就废 ★          │
   │  · ⚠️ ★ 规则数量爆炸：N 个组 → N² 条策略 ★         │
   │  · 粒度：中                                        │
   ├──────────────────────────────────────────────────┤
   │ ★ L3：VRF / 虚拟化分段 ★                          │
   │  · 完全独立的路由表                                 │
   │  · ✅ ★ 强隔离（默认不通，要通必须显式配置）★       │
   │  · 适合：访客网、IoT 网、生产网、办公网彻底分开      │
   │  · ⚠️ 数量有限，管理复杂                            │
   │  · 粒度：粗但强                                     │
   ├──────────────────────────────────────────────────┤
   │ ★★ L4：微分段 / SGT（基于身份的分段）★★           │
   │  · ★ 策略基于【身份标签】，不是 IP 地址 ★          │
   │  · ✅ ★ 地址变了策略不用改 ★                       │
   │  · ✅ ★ 同一个 VLAN 内也能做策略 ★                 │
   │  · ✅ ★ 规则数量从 N² 降到 组数² ★                 │
   │  · 实现：Cisco TrustSec (SGT) / SD-Access          │
   │  · 粒度：★ 细 ★                                    │
   └──────────────────────────────────────────────────┘
```

### 2.4 ★★ 为什么 SGT 是关键突破 ★★

**★ 传统 ACL 的规模灾难 ★**：
```
   假设有 10 个用户组 × 10 个资源组
        ↓
   ★ 需要 10 × 10 = 100 条策略 ★
        ↓
   每个组有多个网段（比如财务部散布在 5 层楼 = 5 个网段）
        ↓
   ★★ 实际 ACL 条目：数千条 ★★
        ↓
   · ★ 没人敢删任何一条 ★（不知道谁在用）
   · 新增一个网段 → 要改几十个地方
   · ★ ACL 长度撞上硬件 TCAM 上限 ★
   · 排障：从 3000 条里找命中哪一条
```

**★ SGT（Security Group Tag）的解法 ★**：
```
   ┌──────────────────────────────────────────────┐
   │ ★ 步骤 1：打标签（分类）★                     │
   │                                               │
   │  用户认证时，★ ISE 根据身份下发 SGT ★         │
   │   · 财务部员工   → SGT 10                     │
   │   · 研发部员工   → SGT 20                     │
   │   · 访客        → SGT 30                     │
   │   · IoT 设备    → SGT 40                     │
   │   · 财务服务器   → SGT 100                    │
   │   · 研发服务器   → SGT 200                    │
   │                                               │
   │  ★ 标签跟着【身份】走，不跟着 IP 走 ★          │
   ├──────────────────────────────────────────────┤
   │ ★ 步骤 2：传播（Propagation）★                │
   │                                               │
   │  · ★ 内联（Inline）★：SGT 写进以太帧的         │
   │    Cisco Meta Data 字段，逐跳传递              │
   │  · ★ SXP ★：设备不支持内联时，用 SXP 协议      │
   │    把 IP↔SGT 映射传给其他设备                  │
   │  · ★ VXLAN ★：SD-Access 把 SGT 放在           │
   │    VXLAN 头里跨 Fabric 传递                    │
   ├──────────────────────────────────────────────┤
   │ ★ 步骤 3：执行（Enforcement）★                │
   │                                               │
   │  ★ SGACL 矩阵 ★（不是 IP，是标签）：           │
   │                                               │
   │        目的→ │ SGT100 │ SGT200 │ SGT40 │      │
   │  源↓        │ 财务服务│ 研发服务│ IoT   │      │
   │  ───────────┼────────┼────────┼───────┤      │
   │  SGT10 财务  │ ★允许★ │ 拒绝   │ 拒绝  │      │
   │  SGT20 研发  │ 拒绝   │ ★允许★ │ 拒绝  │      │
   │  SGT30 访客  │ 拒绝   │ 拒绝   │ 拒绝  │      │
   │  SGT40 IoT   │ 拒绝   │ 拒绝   │★拒绝★│      │
   │                                        ↑      │
   │              ★ IoT 之间也不通（微分段）★      │
   └──────────────────────────────────────────────┘
```

**★ 关键优势**：
```
   ★ 1. 地址无关 ★
      财务部搬到新楼层、换了网段
      → ★ 策略一个字都不用改 ★（SGT 跟着人走）
   
   ★ 2. 规模可控 ★
      10 组 × 10 组 = ★ 100 个矩阵格子 ★
      而不是"每个网段两两组合"的数千条 ACL
   
   ★ 3. 组内微分段 ★
      ★ 同一个 VLAN、同一个网段内的两台 PC
        也可以被策略隔离 ★
      → 这是传统 ACL 做不到的（ACL 在三层，同网段流量不过三层）
      → ★ 直接掐死勒索软件的横向传播路径 ★
   
   ★ 4. 策略即业务语言 ★
      "财务可以访问财务系统" 比
      "10.1.5.0/24 和 10.2.7.0/24 可以访问 10.100.3.15" 
      ★ 可读性高一个数量级 ★
```

### 2.5 ★ SD-Access：把这些整合起来 ★

```
   ★ SD-Access = LISP + VXLAN + TrustSec + DNA Center ★
   
   ┌────────────────────────────────────────────┐
   │ ★ 控制平面：LISP ★                          │
   │  · EID（终端身份）与 RLOC（位置）分离         │
   │  · Map Server/Resolver 维护映射              │
   │  · ★ 终端漫游时位置变了，身份不变 ★           │
   ├────────────────────────────────────────────┤
   │ ★ 数据平面：VXLAN ★                         │
   │  · 在任意 IP 底层网络上构建 Overlay           │
   │  · ★ VXLAN 头里携带 SGT ★                   │
   │  · VNI 区分虚拟网络（相当于 VRF）             │
   ├────────────────────────────────────────────┤
   │ ★ 策略平面：TrustSec (SGT) ★                │
   │  · ISE 下发 SGT 和 SGACL                     │
   │  · ★ 策略跟着身份走 ★                        │
   ├────────────────────────────────────────────┤
   │ ★ 管理平面：DNA Center ★                    │
   │  · 图形化定义策略                             │
   │  · 自动下发到所有设备                          │
   │  · ★ 网络工程师不用逐台配 CLI ★              │
   └────────────────────────────────────────────┘
   
   ★ 两级分段 ★
   · ★ 宏分段（Macro）★：VN（Virtual Network）
     → 相当于 VRF，★ 不同 VN 之间【完全隔离】★
     → 例：办公网 VN / IoT VN / 访客 VN
   · ★ 微分段（Micro）★：SGT
     → ★ 同一个 VN 内部的细粒度策略 ★
     → 例：办公 VN 里，财务组不能访问研发服务器
```

## ③ 配置命令

### 3.1 ★ VRF 宏分段（不用 SD-Access 也能做）★

```cisco
!═══ 定义 VRF ═══
vrf definition OFFICE
 rd 65000:10
 address-family ipv4
 exit-address-family

vrf definition IOT
 rd 65000:20
 address-family ipv4
 exit-address-family

vrf definition GUEST
 rd 65000:30
 address-family ipv4
 exit-address-family

!═══ SVI 划入 VRF ═══
interface Vlan10
 ★ vrf forwarding OFFICE ★
 ip address 10.1.10.1 255.255.255.0

interface Vlan40
 ★ vrf forwarding IOT ★
 ip address 10.1.40.1 255.255.255.0

interface Vlan90
 ★ vrf forwarding GUEST ★
 ip address 10.1.90.1 255.255.255.0

!═══ ★ 结果：三个 VRF 之间【天然不通】★ ═══
! 要通必须显式配置（RT 互导、防火墙串接、静态路由泄露）

!═══ 访客只能出互联网，不能进内网 ═══
ip route ★ vrf GUEST ★ 0.0.0.0 0.0.0.0 203.0.113.1
```

**★ VRF 分段的价值**：
```
   ★ 默认拒绝，而不是默认允许 ★
        ↓
   传统单一路由表：忘了配 ACL = 全通
   ★ VRF：忘了配互访 = 不通 ★
        ↓
   ★★ 安全的默认值（Secure by Default）★★
```

### 3.2 ★ TrustSec / SGT 配置 ★

```cisco
!═══ ① 交换机加入 TrustSec 域 ═══
cts authorization list ISE-LIST
aaa authorization network ISE-LIST group ISE-GROUP

! ★ 从 ISE 获取环境数据（SGT 名称、SGACL 策略）★
★ cts role-based enforcement ★
★ cts role-based enforcement vlan-list 10,20,40 ★

!═══ ② 静态 IP-SGT 映射（服务器等固定资源）═══
★ cts role-based sgt-map 10.100.1.0/24 sgt 100 ★    ! 财务服务器
★ cts role-based sgt-map 10.100.2.0/24 sgt 200 ★    ! 研发服务器
cts role-based sgt-map vlan-list 40 sgt 40           ! IoT VLAN

!═══ ③ 动态 SGT：由 802.1X 认证时 ISE 下发 ═══
! （在 RADIUS Access-Accept 里携带 cts:security-group-tag）

!═══ ④ SGACL（策略）═══
! 通常由 ISE 集中下发，也可以本地定义：
ip access-list role-based DENY-ALL-LOG
 deny ip log

ip access-list role-based PERMIT-FINANCE-APP
 permit tcp dst eq 443
 permit tcp dst eq 1433
 deny ip log

! 应用矩阵
★ cts role-based permissions from 10 to 100 PERMIT-FINANCE-APP ★
★ cts role-based permissions from 20 to 100 DENY-ALL-LOG ★
★ cts role-based permissions from 40 to 40  DENY-ALL-LOG ★   ← ★ IoT 之间隔离 ★
★ cts role-based permissions default DENY-ALL-LOG ★

!═══ ⑤ SXP（设备不支持内联标签时）═══
cts sxp enable
cts sxp default password MySxpPassword
cts sxp default source-ip 10.1.1.1
★ cts sxp connection peer 10.1.1.2 password default mode local speaker ★
```

**★ 验证命令 ★**：
```cisco
! ★ 看 IP↔SGT 映射 ★
show cts role-based sgt-map all

! ★★ 看策略矩阵和命中计数（排障核心）★★
show cts role-based permissions
show cts role-based counters

! 环境数据
show cts environment-data
show cts pacs

! SXP
show cts sxp connections brief
```

**`show cts role-based counters` 的读法**：
```
Role-based counters
From    To      SW-Denied  HW-Denied  SW-Permit  HW-Permit
★ 10 ★  ★ 100 ★    0          0        1523     ★ 98452 ★   ← 财务访问财务系统，允许
★ 20 ★  ★ 100 ★    0      ★ 3421 ★       0          0       ← ★ 研发想访问财务，被拒 ★
★ 40 ★  ★ 40 ★     0      ★ 88231 ★      0          0       ← ★ IoT 互相扫描，全被拒 ★
                              ↑
                    ★ 这个数字在涨 = 有东西在做横向扫描 ★
                    ★ 这就是微分段的价值可视化 ★
```

### 3.3 ★ 不用 SGT 也能做的微分段（务实方案）★

**★ 大部分企业买不起 ISE + SD-Access，但仍然可以做分段。**

**① ★ Protected Port（同 VLAN 内隔离）★**
```cisco
interface range GigabitEthernet1/0/1-40
 ★ switchport protected ★
```
```
   ★ 效果：标记为 protected 的端口之间【不能互相通信】★
           但都能访问非 protected 的上联口
        ↓
   ★ 适用：访客网络、IoT 网络、酒店/宿舍网络 ★
   ★ 局限：只在同一台交换机内有效（跨交换机无效）★
```

**② ★ Private VLAN（跨交换机的同 VLAN 隔离）★**
```cisco
vtp mode transparent

vlan 100
 ★ private-vlan primary ★
 private-vlan association 101,102
vlan 101
 ★ private-vlan isolated ★     ← ★ 互相不通 ★
vlan 102
 ★ private-vlan community ★    ← 组内互通，组间不通

interface Vlan100
 private-vlan mapping 101,102

! 上联口（Promiscuous）
interface GigabitEthernet1/0/48
 switchport mode private-vlan promiscuous
 private-vlan mapping 100 101,102

! 接入口（Isolated）
interface range GigabitEthernet1/0/1-40
 switchport mode private-vlan host
 ★ switchport private-vlan host-association 100 101 ★
```

**③ ★ VACL（VLAN 内的三层过滤）★**
```cisco
! ★ 关键：能过滤【同一个 VLAN 内】的流量 ★
!    （普通 ACL 挂在 SVI 上，只能管跨 VLAN 的）
ip access-list extended ACL-BLOCK-SMB
 permit tcp any any eq 445
 permit tcp any any eq 139
 permit tcp any any eq 135

vlan access-map VMAP-SEGMENT 10
 ★ match ip address ACL-BLOCK-SMB ★
 ★ action drop ★
vlan access-map VMAP-SEGMENT 20
 action forward

★ vlan filter VMAP-SEGMENT vlan-list 10,20,30 ★
```
```
   ★★ 这一条配置就能挡住大部分勒索软件的横向传播 ★★
   （PC 之间根本不需要互相访问 445 端口）
        ↓
   ⚠️ 部署前确认：★ 有没有业务依赖 PC 之间的文件共享 ★
   （建议先用 NetFlow 观察 1-2 周）
```

**④ ★ 出站过滤（阻断 C2 通信）★**
```cisco
ip access-list extended ACL-EGRESS
 ! 只允许必要的出站
 permit tcp 10.0.0.0 0.255.255.255 any eq 80
 permit tcp 10.0.0.0 0.255.255.255 any eq 443
 permit udp 10.0.0.0 0.255.255.255 host 10.1.1.53 eq 53
 permit tcp 10.0.0.0 0.255.255.255 any eq 22
 ! ★ 明确拒绝高危出站 ★
 ★ deny tcp any any eq 445 log ★
 ★ deny tcp any any eq 3389 log ★
 ★ deny udp any any eq 53 log ★     ← ★ 只允许走内部 DNS ★

```
```
   ★ 只允许走内部 DNS，是一个被严重低估的措施 ★
   · 阻断 DNS 隧道（数据外泄的常用手段）
```

## ④ 配套实验

### 实验：用最小成本实现微分段

**目标**：不用 ISE，在一台交换机上实现"同 VLAN 内 PC 之间不能互访 445"。

**拓扑**：
```
   PC1 (10.1.10.11) ─┐
   PC2 (10.1.10.12) ─┼─ SW1 (VLAN 10) ─ R1 ─ 服务器 10.100.1.10
   PC3 (10.1.10.13) ─┘
```

**步骤**：

**① 基线测试（配置前）**
```
   PC1 → PC2 :445    → ★ ✅ 通（这就是勒索软件的传播路径）★
   PC1 → PC2 ping    → ✅ 通
   PC1 → 服务器      → ✅ 通
```

**② 方案 A：VACL 阻断 PC 之间的 SMB**
```cisco
ip access-list extended ACL-SMB
 permit tcp any any eq 445
 permit tcp any any eq 139
 permit tcp any any eq 135
 permit udp any any eq 137
 permit udp any any eq 138

vlan access-map VMAP-SEG 10
 match ip address ACL-SMB
 ★ action drop log ★
vlan access-map VMAP-SEG 20
 action forward

vlan filter VMAP-SEG vlan-list 10
```
**验证**：
```
   PC1 → PC2 :445    → ★ ❌ 不通（已阻断）★
   PC1 → PC2 ping    → ✅ 通
   PC1 → 服务器:445  → ★ ❌ 也被挡了 ★
   ⚠️ ★ VACL 是 VLAN 级的，也会挡掉去服务器的 SMB ★
   → ★ 需要在 ACL 里排除服务器 ★
```

**修正**：
```cisco
ip access-list extended ACL-SMB
 ★ deny tcp any host 10.100.1.10 eq 445 ★   ← ★ 排除文件服务器 ★
 permit tcp any any eq 445
 permit tcp any any eq 139
```
```
   ★ 注意这个反直觉的写法 ★
   在 VACL 里，ACL 的 permit = "匹配上，交给 action 处理（drop）"
                ACL 的 deny  = "不匹配，落到下一条 map（forward）"
   ★★ VACL 里的 permit/deny 不是"允许/拒绝"，
      是"匹配/不匹配" ★★
```

**③ 方案 B：Protected Port**
```cisco
interface range Gi1/0/1-3
 ★ switchport protected ★
```
**验证**：
```
   PC1 → PC2 任何流量 → ★ ❌ 全部不通 ★
   PC1 → 服务器       → ✅ 通（上联口不是 protected）
   
   ★ 更彻底，但也更粗暴（连 ping 都不通）★
   ★ 适合访客/IoT，不适合办公网（可能有 AirPlay、
     打印机发现、协作软件的局域网功能）★
```

**④ ★ 故障注入 / 副作用观察 ★**

| # | 场景 | 观察 | ★ 教训 ★ |
|:--|:--|:--|:--|
| **F1** | 开了 VACL 后，用户投诉"网上邻居打不开了" | 符合预期 | ★ **分段一定有副作用，要提前沟通** |
| **F2** | 开了 Protected Port 后，AirPlay/Chromecast 失效 | mDNS 组播被挡 | ★ **组播/发现类协议是分段的主要痛点** |
| **F3** | VACL 里忘了排除文件服务器 | ★ 所有人访问不了共享盘 | ★ **VACL 是 VLAN 级的，不区分方向** |
| **F4** | Protected Port 只在一台交换机上配 | ★ **跨交换机的 PC 之间仍能互访** | ★ **Protected Port 不跨设备** → 用 PVLAN |
| **F5** | 部署前没做流量基线 | 上线后一堆未知业务中断 | ★ **必须先用 NetFlow 观察 2 周** |

**★ F5 是最重要的**：
```
   ★★ 网络分段项目的第一步不是配置，
      是【搞清楚现在谁在和谁通信】★★
        ↓
   ★ 工具 ★
   · NetFlow / IPFIX（谁→谁→什么端口→多少流量）
   · Stealthwatch / ntopng / Elastiflow 做可视化
   · ★ 先在核心交换机开 NetFlow，导出 2-4 周 ★
        ↓
   ★ 分析产出 ★
   · "PC 网段 → 服务器网段" 的端口清单
   · ★ "PC 网段 → PC 网段" 的流量（★ 这些大部分可以砍掉 ★）★
   · 意料之外的通信（老系统、影子 IT）
        ↓
   ★ 然后才开始设计策略 ★
```

## ⑤ 排障思路

### 5.1 ★ 分段项目的典型故障 ★

| 症状 | ★ 根因 ★ | 排查 |
|:--|:--|:--|
| ★ **某个业务突然不通** | ★ **分段策略挡了没人知道的依赖** | ★ 看 ACL/SGACL 的 **deny 计数和 log** ★ |
| **打印机发现不了** | ★ **mDNS/SSDP 组播被挡** | 需要 mDNS Gateway 或 Bonjour Gateway |
| **域控认证失败** | ★ **Kerberos/LDAP 端口被挡** | 88/389/636/445/135 + 动态 RPC 高端口 |
| **VRF 之间不通** | ★ **正常，需要显式互导** | `show ip route vrf X` |
| **SGT 策略不生效** | ★ **没开 `cts role-based enforcement`** | `show cts role-based permissions` |
| **SGT 到了但标签是 0** | ★ **中间设备不支持内联标签，SGT 丢了** | ★ 用 **SXP** 传播 |
| **Protected Port 跨交换机失效** | ★ **本来就不跨设备** | 改用 PVLAN |
| **VACL 挡了不该挡的** | ★ **VACL 是 VLAN 级、双向的** | 在 ACL 里显式 `deny` 排除 |

### 5.2 ★ 排障的关键工具：deny 计数和日志 ★

```
   ★★ 部署分段策略时，【一定要加 log】★★
   
   ip access-list extended ACL-SEGMENT
    permit ...
    ★ deny ip any any log ★
   
   ip access-list role-based DENY-ALL-LOG
    ★ deny ip log ★
        ↓
   ★ 好处 ★
   · 用户报障时，★ 立刻能看到"什么流量被挡了" ★
   · 平时可以从日志里发现"原来还有这个业务"
   · ★ 从"猜"变成"看" ★
        ↓
   ⚠️ 注意
   · log 会消耗 CPU（软件处理）→ ★ 配合限速 ★
   · 生产环境用 `log-input` 还能看到入接口
```

### 5.3 ★ 分段项目的完整方法论 ★

```
   ★ 阶段 1：可视化（2-4 周）★
   · ★ 开 NetFlow，收集全网流量 ★
   · 产出"谁和谁在通信"的矩阵
   · ★ 不做任何策略变更 ★
        ↓
   ★ 阶段 2：分组 ★
   · 按【业务功能】分组，不是按部门
     （例：财务组、研发组、生产组、IoT 组、访客组、
          服务器组、管理组）
   · ★ 每个组明确"需要访问什么" ★
        ↓
   ★ 阶段 3：设计策略矩阵 ★
   · 画出 组×组 的允许/拒绝矩阵
   · ★ 从"默认拒绝"开始，逐个添加需要的 ★
   · ★ 每一条允许都要有业务负责人签字 ★
        ↓
   ★ 阶段 4：监控模式部署 ★
   · ★ 策略配成"允许 + 记日志"★
   · 观察 2 周："如果真的拒绝，会挡掉什么"
   · ★ 补漏 ★
        ↓
   ★ 阶段 5：分批强制 ★
   · ★ 从风险最低的组开始 ★（访客 → IoT → 办公 → 生产）
   · 每批之间间隔 1-2 周
   · ★ 保留快速回滚能力 ★
        ↓
   ★ 阶段 6：持续运营 ★
   · 定期审计策略（哪些从来没命中过？可以删）
   · 新业务上线时走策略变更流程
   · ★ 监控 deny 计数的异常突增（可能是攻击）★
```

<details><summary>答案</summary>

**★ 为什么"城堡护城河"模型失效 ★**

**① 边界防火墙只管"穿越边界"的流量**
```
   防火墙部署在 内网 ↔ 外网 之间
        ↓
   ★ 内网设备之间的流量【根本不经过防火墙】★
        ↓
   PC ↔ PC、PC ↔ 服务器（同一栋楼内）
   → 在接入交换机/核心交换机上就转发了
   → ★ 防火墙看都看不到 ★
```

**② 现代攻击的入口不在边界**
```
   ★ 攻击者不再"攻破防火墙进来" ★
        ↓
   而是：
   · ★ 钓鱼邮件 ★ → 员工自己点开 → 恶意代码在内网运行
   · ★ 供应链攻击 ★ → 合法软件的更新包带毒

   · ★ 内鬼 ★ → 本来就有合法访问权
   · ★ 远程办公 VPN ★ → 家里的电脑中毒了，VPN 一连全进来
        ↓
   ★★ 这些路径全部【绕过了边界防火墙】★★
```

**③ 边界本身正在消失**
```
   · 业务系统上了公有云 → 数据在防火墙外面
   · 员工用 SaaS（Office365、飞书、Salesforce）
   · 远程办公成为常态
   · 分支机构直接上网（DIA）
        ↓
   ★ "内网"到底指什么？"边界"画在哪里？★
```

**④ 内网"一马平川"放大了后果**
```
   一台机器被攻陷
        ↓
   · 同 VLAN 里几百台机器随便访问
```

**★ 零信任三大原则各自解决什么 ★**

| 原则 | ★ 解决什么问题 ★ | 具体技术 |
|:--|:--|:--|
| ★ **1. 显式验证**<br>Verify Explicitly | ★ **"在内网 = 可信" 这个错误假设** ★<br>不再基于位置授权 | 802.1X、MFA、设备合规检查、持续认证、条件访问 |

**2.** SGT（Security Group Tag）相比传统基于 IP 的 ACL，优势在哪里？举一个传统 ACL 做不到的场景。

**① ★ 地址无关（策略跟着身份走）★**

```
   SGT：★ 直接掐死 ★
```

**④ ★ 策略即业务语言 ★**
```
   ★ 传统 ★
   "permit tcp 10.1.5.0 0.0.0.255 host 10.100.3.15 eq 1433"
   → ★ 三个月后没人记得这条是干嘛的 ★
   
   ★ SGT ★
   "Finance_Users → Finance_Servers : Allow SQL"
   → ★ 业务方也能看懂，能签字确认 ★
   → ★ 审计的时候能直接给合规看 ★
```

---

**★ 代价（要诚实说明）★**
```
   ⚠️ SGT 不是免费的：
   · ★ 需要 ISE（licence 不便宜）★
   · ★ 需要 802.1X 全面部署 ★（不然没法打标签）
   · ★ 需要交换机支持 TrustSec ★（老设备可能不支持）
   · ★ 中间不支持内联标签的设备要靠 SXP ★（复杂度上升）
   · 排障难度提高（多了一层抽象）
        ↓
   ★ 务实的替代方案（见 §3.3）★
   · VACL 阻断 PC↔PC 的 445/139/135
   · Protected Port / Private VLAN
   · VRF 做宏分段
        ↓
   ★★ 这些方案成本近乎为零，
      却能挡住 80% 的横向移动 ★★
```
</details>

**3.** 一个网络分段项目应该怎么推进？为什么"先做流量可视化"比"先设计策略"更重要？

<details><summary>答案</summary>

**★ 六阶段方法论 ★**

```
   ★ 阶段 1：可视化（2-4 周，不做任何变更）★
      · 在核心/汇聚开 ★ NetFlow / IPFIX ★
      · 导出到 Stealthwatch / ntopng / Elastiflow
      · ★ 产出："谁 → 谁 → 什么端口 → 多少流量" 的矩阵 ★
        ↓
   ★ 阶段 2：分组 ★
      · ★ 按【业务功能】分组，不是按部门/楼层 ★
      · 每个组明确"需要访问什么"
      · 典型分组：办公终端 / 生产终端 / IoT / 访客 /
                 服务器（再细分）/ 管理 / 打印
        ↓
   ★ 阶段 3：设计策略矩阵 ★
      · 画 组×组 的允许/拒绝矩阵
      · ★ 从"默认全部拒绝"开始 ★
      · ★ 每一条"允许"都要有业务负责人签字 ★
        （这一步能筛掉大量"其实没人用"的通道）
        ↓
   ★ 阶段 4：监控模式部署（2 周）★
      · ★ 策略配成"允许 + 记日志" ★
      · 观察："如果真的拒绝，会挡掉什么？"
      · ★ 补漏 ★
        ↓
   ★ 阶段 5：分批强制 ★
      · ★ 从风险最低的组开始 ★
        访客 → IoT → 打印 → 办公 → 生产
      · 每批间隔 1-2 周
      · ★ 保留一键回滚脚本 ★
        ↓
   ★ 阶段 6：持续运营 ★
      · ★ 定期审计：哪些策略从来没命中过？→ 可以删 ★
      · 新业务上线走变更流程
      · ★ 监控 deny 计数突增（可能是攻击或配置漂移）★
```

---

**★★ 为什么"先可视化"最重要 ★★**

**核心原因：★ 你不知道网络里到底在跑什么 ★**

```
   ★ 每个运行了 5 年以上的网络，都有大量"没人知道的通信" ★
   
   · 十年前部署的老系统，文档早丢了
   · 某个部门自己买的软件（影子 IT）
   · 服务器之间的定时同步任务
   · 监控/备份/日志 Agent 的回连
   · ★ 某台机器一直在给某个 IP 发数据，没人知道为什么 ★
   · 打印机的 SNMP 轮询
   · 会议室设备的组播发现
   · 门禁/考勤系统的心跳
        ↓
   ★★ 你去问业务方"你们需要访问什么"，
      他们的答案永远是不完整的 ★★
   （因为他们自己也不知道）
```

**★ 跳过可视化的后果 ★**：
```
   凭"理论上应该这样"设计了策略
        ↓
   上线
        ↓
   ① ★ 一堆没人预料到的业务中断 ★
   ② 工单爆炸，运维被骂
   ③ ★ 压力之下开始"临时放行" ★
      permit ip any any  ← 为了赶紧恢复业务
   ④ 临时变永久
        ↓
   ★★ 最终结果：策略形同虚设，
      但复杂度和维护成本全留下了 ★★
        ↓
   ★ 项目失败，而且下次没人愿意再做 ★
```

**★ 可视化带来的三个具体价值 ★**：

**① ★ 数据驱动的分组 ★**
```
   NetFlow 数据会告诉你"实际的通信簇"
        ↓
   有时候会发现：
   · ★ 你以为的"财务部"其实分两拨，
     一拨用 ERP，一拨用另一套系统 ★
   · ★ 你以为独立的两个部门，其实共用一台服务器 ★
        ↓
   ★ 按【真实的通信模式】分组，而不是按组织架构 ★
```

**② ★ 发现"可以砍掉"的流量（最大收益）★**
```
   ★ 典型发现 ★
   · PC 网段 → PC 网段 的流量占比 15%
     其中 ★ 90% 是 Windows 的网络发现广播和 SMB 探测 ★
     ★ 真正的业务需求几乎为零 ★
        ↓
   ★★ 这 15% 就是勒索软件的高速公路 ★★
   ★★ 砍掉它 = 项目最大的安全收益，且几乎无副作用 ★★
   
   · IoT 设备之间的流量：★ 应该是 0，如果不是 0 就要查 ★
   · 访客网 → 内网：★ 应该是 0 ★
```

**③ ★ 量化风险，说服管理层 ★**
```
   ★ 没有数据的汇报 ★
   "我们需要做网络分段，因为安全很重要"
   → 管理层："成本多少？影响业务吗？先放放"
   
   ★★ 有数据的汇报 ★★
   "过去 30 天，我们的办公网内部有
     ★ 12 万次 PC 之间的 445 端口连接 ★，
     其中 ★ 0 次 ★ 对应实际业务需求。
     如果有一台机器中招，
     ★ 它可以在 15 分钟内触达 600 台设备。★
     阻断这条路径的成本是：
     ★ 一条 VACL 配置，零采购成本 ★。"
   → ★ 管理层：批准 ★
```

**★ 可视化的具体做法（低成本版）★**：
```cisco
! ★ 在核心交换机/路由器开 Flexible NetFlow ★
flow record RECORD-SEG
 match ipv4 source address
 match ipv4 destination address
 match ipv4 protocol
 match transport source-port
 match transport destination-port
 collect counter bytes
 collect counter packets
 collect timestamp absolute first
 collect timestamp absolute last

flow exporter EXP-1
 destination 10.1.1.60
 transport udp 2055
 source Loopback0
 template data timeout 60

flow monitor MON-SEG
 record RECORD-SEG
 exporter EXP-1
 cache timeout active 60

interface Vlan10
 ★ ip flow monitor MON-SEG input ★
 ★ ip flow monitor MON-SEG output ★
```
```
   ★ 采集端可以用免费的 ★
   · ntopng（开源，够用）
   · Elastiflow（ELK 栈）
   · nfdump / nfsen
        ↓
   ★ 跑 2-4 周，导出"源组→目的组→端口"的汇总表 ★
```

**★ 一句话总结 ★**：
```
   ★★ 网络分段的难点不在技术，在【认知】 ★★
   
   配 VACL、配 SGT、配 VRF —— 技术上都不难
   ★ 难的是"知道该放行什么、该拦截什么" ★
        ↓
   ★ 而这个认知，只能从【真实流量数据】里来 ★
```
</details>
