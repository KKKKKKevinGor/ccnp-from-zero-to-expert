## ② ACL 排障

### 2.1 ACL 不生效的六个原因

| 原因 | 验证 |
|:--|:--|
| **① 没应用到接口** | `show ip interface Gi0/0 \| include access list` |
| **② 方向搞反了** | `show access-lists` 看命中计数为 0 |
| **③ 顺序错**（宽泛规则在前） | `show access-lists` 看哪条命中 |
| **④ 隐含 deny 生效** | 检查末尾有没有 permit |
| **⑤ 通配符掩码写错** | 重新计算 |
| **⑥ NAT 与 ACL 的处理顺序** | 见 2.3 节 |

### 2.2 用命中计数快速定位

```cisco
! ① 清零
R1# clear access-list counters WEB-POLICY

! ② 让用户重现问题

! ③ 看哪条命中
R1# show access-lists WEB-POLICY
Extended IP access list WEB-POLICY
    10 permit tcp 192.168.1.0 0.0.0.255 host 10.0.0.100 eq www (245 matches)
    20 permit tcp 192.168.1.0 0.0.0.255 host 10.0.0.100 eq 443 (0 matches)
                                                                 ↑
                                        ★ 0 命中 = 规则没匹配上或流量没到
    30 deny ip any any log (89 matches)
                              ↑
                    ★ 有 89 个包被拒绝，看日志知道是谁
```

```cisco
! ④ 看被拒绝的详情
R1# show logging | include IPACCESSLOG
%SEC-6-IPACCESSLOGP: list WEB-POLICY denied tcp 192.168.1.50(51234) -> 10.0.0.200(8080), 3 packets
                                                    ↑ 源              ↑ 目的
```

**这个流程能在 2 分钟内定位 90% 的 ACL 问题。**

### 2.3 ACL 与 NAT 的处理顺序（★ ENARSI 高频考点）

```
   Inside → Outside（内网访问外网）：
   ① 入接口 ACL          ← 看到【私网】源地址
   ② 路由查找
   ③ ★ NAT（源地址转换）★
   ④ 出接口 ACL          ← 看到【公网】源地址

   Outside → Inside（外网访问内网）：
   ① 入接口 ACL          ← ★ 看到【公网】目的地址 ★
   ② ★ NAT（目的地址还原）★
   ③ 路由查找
   ④ 出接口 ACL          ← 看到【私网】目的地址
```

**实战含义**：

```cisco
! 内网服务器 192.168.1.100 通过静态 NAT 映射到公网 202.100.1.10
! 在【外网接口 in 方向】写 ACL 放行访问：

! ❌ 错误：写私网地址
R1(config-ext-nacl)# permit tcp any host 192.168.1.100 eq 80
! → 永远 0 命中（ACL 在 NAT 之前，看到的是公网地址）

! ✅ 正确：写公网地址
R1(config-ext-nacl)# permit tcp any host 202.100.1.10 eq 80
```

**记忆口诀**：**ACL 看到的永远是"那一侧接口上真实传输的地址"。**

### 2.4 时间 ACL 与自反 ACL

```cisco
! ── 时间 ACL（按时间生效）──
R1(config)# time-range WORK-HOURS
R1(config-time-range)#  periodic weekdays 09:00 to 18:00
R1(config-time-range)#  absolute start 00:00 1 January 2026 end 23:59 31 December 2026

R1(config)# ip access-list extended TIME-BASED
R1(config-ext-nacl)#  permit tcp any any eq 80 time-range WORK-HOURS
R1(config-ext-nacl)#  deny ip any any

R1# show time-range
R1# show access-lists TIME-BASED
! 非工作时间会显示 (inactive)
```
> ⚠️ **时间 ACL 依赖系统时钟。NTP 没同步 → 时间 ACL 行为不可预测。**

```cisco
! ── 自反 ACL（真正的状态跟踪）──
R1(config)# ip access-list extended OUTBOUND
R1(config-ext-nacl)#  permit tcp any any reflect MIRROR timeout 300
R1(config-ext-nacl)#  permit udp any any reflect MIRROR timeout 60
R1(config-ext-nacl)#  permit icmp any any reflect MIRROR timeout 30

R1(config)# ip access-list extended INBOUND
R1(config-ext-nacl)#  evaluate MIRROR                    ! ★ 动态放行回程
R1(config-ext-nacl)#  permit tcp any host 202.100.1.10 eq 80    ! 对外发布的服务
R1(config-ext-nacl)#  deny ip any any log

R1(config)# interface GigabitEthernet0/1
R1(config-if)# ip access-group OUTBOUND out
R1(config-if)# ip access-group INBOUND in

R1# show ip access-lists MIRROR                          ! 看动态生成的条目
Reflexive IP access list MIRROR
     permit tcp host 200.1.1.1 eq 80 host 202.100.1.1 eq 51234 (12 matches) (280 remaining)
                                                                              ↑ 剩余超时
```

**自反 ACL vs `established`**：

| | `established` | **自反 ACL** |
|:--|:--|:--|
| 状态跟踪 | ❌ 只看 ACK 位（伪状态） | ✅ **真正的会话表** |
| 支持 UDP | ❌ | ✅ |
| 支持 ICMP | ❌ | ✅ |
| 可被伪造绕过 | ✅ 容易 | ❌ 难 |

## ③ uRPF（防 IP 源地址欺骗）

**原理**：收到一个包，检查**它的源地址是否可以从收到它的那个接口路由回去**。

```cisco
R1(config)# interface GigabitEthernet0/1
R1(config-if)# ip verify unicast source reachable-via rx        ! 严格模式
! 或
R1(config-if)# ip verify unicast source reachable-via any       ! 松散模式
```

| 模式 | 检查 | 适用 |
|:--|:--|:--|
| **strict (rx)** | 到源地址的**最优路由的出接口**必须**就是收到包的接口** | ★ **单归属的接入边界** |
| **loose (any)** | 到源地址**有任何路由**即可（不管从哪个接口） | ★ **多归属/非对称路由场景** |

**★ 严格模式的误伤风险（考点）**：

```
   非对称路由场景：
   
   流量【进来】走 ISP-A（因为对方的选路）
   流量【出去】走 ISP-B（因为我的路由表这么说）
        ↓
   严格 uRPF 在 ISP-A 接口上检查：
   "去这个源地址的路由，出接口是 ISP-B，不是 ISP-A"
        ↓
   ★ 判定为伪造，丢弃 ★
        ↓
   ★ 合法流量被误杀 ★
```

**什么时候会出现非对称路由**：
- 多归属（接了两个 ISP）
- BGP 的入向和出向策略不对称
- ECMP 负载均衡
- HSRP 主备与路由不对齐

**部署建议**：

| 位置 | 模式 |
|:--|:--|
| **接入层/客户边界**（单归属） | **strict** |
| **运营商边界 / 多归属** | **loose** 或不用 |
| **内部核心** | 通常不用 |

**允许例外**：
```cisco
! 用 ACL 放行特定的源地址（比如合法的非对称流量）
R1(config)# access-list 100 permit ip 203.0.113.0 0.0.0.255 any
R1(config-if)# ip verify unicast source reachable-via rx 100
```

**验证**：
```cisco
R1# show ip interface GigabitEthernet0/1 | include verify|drop
  IP verify source reachable-via RX, allow default
  0 verification drops
  0 suppressed verification drops
     ↑ 如果这个数字持续增长，可能是误伤

R1# show cef interface GigabitEthernet0/1 | include unicast
```

## ④ DHCP 排障（ENARSI 重点）

### 4.1 跨网段 DHCP 的完整链路

```
   客户端 ──广播 DISCOVER──> 网关（中继）──单播──> DHCP 服务器
                                 │                      │
                            填 giaddr              根据 giaddr 选池
                                 │                      │
   客户端 <──广播 OFFER────── 中继 <────单播 OFFER───────┘
```

**必须同时满足的五个条件**：

| # | 条件 | 验证 |
|:--|:--|:--|
| 1 | 客户端端口在正确的 VLAN | `show interfaces Gi1/0/5 switchport` |
| 2 | 端口配了 PortFast | `show spanning-tree interface Gi1/0/5 portfast` |
| 3 | **网关配了 `ip helper-address`** | `show ip interface Vlan10 \| inc Helper` |
| 4 | **DHCP 服务器有回到 giaddr 的路由** | 服务器上 `show ip route <giaddr>` |
| 5 | 地址池有空闲，且网段匹配 giaddr | `show ip dhcp pool` |

### 4.2 `ip helper-address` 的副作用

**它默认转发 8 种 UDP 广播**（不只是 DHCP）：

| 端口 | 服务 |
|:--|:--|
| 37 | Time |
| **49** | TACACS |
| **53** | **DNS** |
| **67/68** | **DHCP/BOOTP** |
| **69** | TFTP |
| **137** | NetBIOS Name Service |
| **138** | NetBIOS Datagram |

**问题**：NetBIOS 广播在 Windows 网络里非常多，全部转发会造成**不必要的流量泛洪**。

**精简**：
```cisco
R1(config)# no ip forward-protocol udp 37
R1(config)# no ip forward-protocol udp 49
R1(config)# no ip forward-protocol udp 53
R1(config)# no ip forward-protocol udp 69
R1(config)# no ip forward-protocol udp 137
R1(config)# no ip forward-protocol udp 138
! 只保留 DHCP
R1(config)# ip forward-protocol udp 67
R1(config)# ip forward-protocol udp 68

R1# show ip forward-protocol
```

### 4.3 giaddr 的作用与陷阱

**giaddr（Gateway IP Address）的两个作用**：
1. **告诉服务器该从哪个池分配**
2. **告诉服务器往哪回包**

**陷阱：SVI 有多个 IP 时**
```cisco
R1(config)# interface Vlan10
R1(config-if)# ip address 192.168.10.1 255.255.255.0
R1(config-if)# ip address 192.168.11.1 255.255.255.0 secondary
```
**giaddr 填的是【主地址】** `192.168.10.1`。
→ **服务器上的地址池必须匹配主地址所在的网段**，secondary 网段的客户端拿不到 IP。

**解法**：用 `ip dhcp smart-relay`
```cisco
R1(config)# ip dhcp smart-relay
```
如果主地址的池耗尽，中继会尝试用 secondary 地址作为 giaddr 重试。

**手工指定 giaddr**：
```cisco
R1(config-if)# ip dhcp relay source-interface Loopback0
```

### 4.4 DHCP Option 82

**中继在转发时插入的额外信息**（端口、VLAN、设备标识），用于**精确定位客户端位置**。

```cisco
! ── 开启（DHCP Snooping 会自动插入）──
SW1(config)# ip dhcp snooping information option

! ── 常见问题：服务器不认识 Option 82，丢弃请求 ──
SW1(config)# no ip dhcp snooping information option

! ── 或者中继侧允许不可信的 Option 82 ──
R1(config)# ip dhcp relay information trust-all
R1(config-if)# ip dhcp relay information trusted

! ── 策略 ──
R1(config)# ip dhcp relay information policy replace     ! 替换（默认）
R1(config)# ip dhcp relay information policy keep        ! 保留
R1(config)# ip dhcp relay information policy drop        ! 丢弃
```

> **★ 经典故障**：开了 DHCP Snooping 后，跨网段的客户端拿不到 IP。
>
> **根因**：Snooping 自动插入 Option 82，但**中继收到带 Option 82 且 giaddr 为 0 的包时默认丢弃**（认为不可信）。
>
> **解法**：
> ```cisco
> ! 方案 1：交换机不插入 Option 82
> SW1(config)# no ip dhcp snooping information option
>
> ! 方案 2：中继信任它
> R1(config)# ip dhcp relay information trust-all
> ```

### 4.5 DHCP 排障速查

| 症状 | 根因 | 验证 |
|:--|:--|:--|
| 拿到 `169.254.x.x` | 完全没收到响应 | 见下面的完整流程 |
| 拿到错误网段的 IP | giaddr / 池匹配错 | 抓包看 giaddr |
| 部分用户拿不到 | 地址池耗尽 | `show ip dhcp pool` |
| **开了 Snooping 后拿不到** | **Option 82 被丢弃** | `no ip dhcp snooping information option` |
| 静态 IP 设备断网 | DAI/IPSG 没做静态绑定 | `show ip dhcp snooping binding` |
| 地址冲突 | 有人手工配了池内地址 | `show ip dhcp conflict` |
| 服务器收到请求但不响应 | 无回程路由 | 服务器上 `show ip route <giaddr>` |

**完整排查流程**：
```cisco
! ① 端口 VLAN 对吗
SW1# show interfaces GigabitEthernet1/0/5 switchport | include Access Mode VLAN

! ② PortFast 配了吗
SW1# show spanning-tree interface Gi1/0/5 portfast

! ③ 网关有 helper 吗
SW1# show ip interface Vlan10 | include Helper

! ④ Snooping 状态
SW1# show ip dhcp snooping
SW1# show ip dhcp snooping binding

! ⑤ 服务器端
DHCP# show ip dhcp pool
DHCP# show ip dhcp binding
DHCP# show ip dhcp conflict
DHCP# show ip route <giaddr>          ← ★ 回程路由

! ⑥ 调试（生产慎用）
R1# debug ip dhcp server events
R1# debug ip dhcp server packet
```

## ⑤ NAT 排障（ENARSI 视角）

### 5.1 NAT 表项耗尽

```cisco
R1# show ip nat statistics
Total active translations: 63500 (2 static, 63498 dynamic; 63498 extended)
Peak translations: 64000, occurred 00:15:23 ago
                   ↑ 快满了

! ── 找出是谁占用最多 ──
R1# show ip nat translations | include 192.168.1.66 | count
Number of lines which match regexp = 45678
                                     ↑ ★ 一台机器占了 4.5 万条 → 大概率中毒在扫描
```

**应急处理**：
```cisco
! ① 限制单主机的表项数
R1(config)# ip nat translation max-entries host 192.168.1.66 100

! ② 全局上限（防止内存耗尽导致设备宕机）
R1(config)# ip nat translation max-entries 60000

! ③ 缩短超时
R1(config)# ip nat translation timeout 300
R1(config)# ip nat translation tcp-timeout 3600
R1(config)# ip nat translation udp-timeout 60
R1(config)# ip nat translation icmp-timeout 10
R1(config)# ip nat translation finrst-timeout 30

! ④ 清理
R1# clear ip nat translation inside 192.168.1.66 *
```

> **实战经验**：出口路由器 CPU 突然飙高、NAT 表暴涨，**十有八九是内网有机器中毒在做端口扫描**。用 `show ip nat translations | include <IP> | count` 逐个排查。
>
> **长期方案**：配 `max-entries host` 限制单机，让中毒机器不至于拖垮整个出口。

### 5.2 NAT ALG 的坑

**ALG（Application Layer Gateway）会改写应用层载荷里的 IP 地址。**

| 协议 | ALG 作用 | 常见问题 |
|:--|:--|:--|
| **FTP** | 改写 PORT/PASV 命令里的地址 | 主动模式穿不过时用被动 |
| **SIP** | 改写 SDP 里的媒体地址 | ★ **实现有 bug，导致单通/注册失败** |
| **H.323** | 同上 | 同上 |
| **TFTP** | 跟踪动态端口 | — |
| **DNS** | 改写 A 记录 | 可能导致解析异常 |

**关闭有问题的 ALG**：
```cisco
R1(config)# no ip nat service sip tcp port 5060
R1(config)# no ip nat service sip udp port 5060
R1(config)# no ip nat service h225
R1(config)# no ip nat service skinny tcp port 2000

R1# show ip nat statistics | include ALG
```

> **★ VoIP 排障第一招：关掉 SIP ALG。** 很多路由器的 SIP ALG 实现有缺陷，改写载荷时改错，反而造成"能注册但没声音"或"单向通话"。
>
> 关掉后让 SIP 服务器/终端自己处理 NAT 穿越（用 STUN 或 SBC）。

### 5.3 NAT 与 VPN 的顺序（回顾）

```cisco
! ★ VPN 流量必须排除在 NAT 之外
R1(config)# ip access-list extended NAT-LIST
R1(config-ext-nacl)#  deny ip 192.168.1.0 0.0.0.255 192.168.99.0 0.0.0.255   ! ★ 先 deny
R1(config-ext-nacl)#  permit ip 192.168.1.0 0.0.0.255 any

R1(config)# ip nat inside source list NAT-LIST interface Gi0/1 overload
```

**验证**：
```cisco
R1# show ip nat translations | include 192.168.99
! ★ 应该是空的 ★

R1# show access-lists NAT-LIST
    10 deny ip 192.168.1.0 0.0.0.255 192.168.99.0 0.0.0.255 (456 matches)   ← 有命中 ✓
    20 permit ip 192.168.1.0 0.0.0.255 any (23451 matches)

R1# show crypto ipsec sa | include pkts
    #pkts encaps: 456, #pkts encrypt: 456        ← 有加密包 = 流量进隧道了 ✓
```

## ⑥ 设备访问控制与日志

### 6.1 管理平面加固

```cisco
! ── 限制谁能 SSH 到设备 ──
R1(config)# ip access-list standard MGMT-HOSTS
R1(config-std-nacl)#  permit 10.1.30.0 0.0.0.255
R1(config-std-nacl)#  permit host 10.1.99.50
R1(config-std-nacl)#  deny any log

R1(config)# line vty 0 15
R1(config-line)#  access-class MGMT-HOSTS in           ! ★ 是 access-class 不是 access-group
R1(config-line)#  transport input ssh
R1(config-line)#  exec-timeout 10 0
R1(config-line)#  logging synchronous

! ── SSH 加固 ──
R1(config)# ip ssh version 2
R1(config)# ip ssh time-out 60
R1(config)# ip ssh authentication-retries 3
R1(config)# ip ssh dh min size 2048
R1(config)# crypto key generate rsa modulus 2048

! ── 登录失败保护 ──
R1(config)# login block-for 300 attempts 5 within 60
!                        ↑          ↑        ↑
!            锁定300秒  60秒内失败5次
R1(config)# login quiet-mode access-class MGMT-HOSTS   ! 锁定期间仍允许管理网段
R1(config)# login delay 3
R1(config)# login on-failure log
R1(config)# login on-success log

R1# show login
R1# show login failures

! ── Management Plane Protection（只允许特定接口做管理）──
R1(config)# control-plane host
R1(config-cp-host)#  management-interface GigabitEthernet0/0 allow ssh snmp

! ── 关闭不必要的服务 ──
R1(config)# no ip http server
R1(config)# no ip http secure-server
R1(config)# no service tcp-small-servers
R1(config)# no service udp-small-servers
R1(config)# no ip bootp server
R1(config)# no ip source-route
R1(config)# no cdp run                        ! 或按接口 no cdp enable
R1(config-if)# no ip redirects
R1(config-if)# no ip unreachables             ! ⚠️ 会影响 PMTUD 和 traceroute
R1(config-if)# no ip proxy-arp
R1(config-if)# no ip directed-broadcast
```

> ⚠️ **`no ip unreachables` 的副作用**：会禁止路由器发送 ICMP Unreachable，包括 **"Fragmentation Needed"（PMTUD 需要的）** 和 traceroute 依赖的消息。
>
> **在有隧道的环境（GRE/IPsec/VXLAN）关掉它会导致 MTU 黑洞。** 建议只在面向不可信网络的接口上关，或者用 CoPP 限速而不是完全禁用。

### 6.2 日志与审计

```cisco
! ── 配置变更审计 ──

    1     1        admin@vty0        |  interface GigabitEthernet0/1
    2     1        admin@vty0        |   shutdown
                                        ↑ ★ 谁在什么时候改了什么，一目了然
```

> **`archive log config` 是审计神器**：它记录**每一条配置命令**，包括是谁、从哪个终端、什么时候执行的。出了事故能立刻定位。

## ⑦ EEM：自动化排障

**EEM (Embedded Event Manager)** 让设备在特定事件发生时**自动执行动作**。

```cisco
! ── 示例 1：接口 down 时自动收集诊断信息 ──
R1(config)# event manager applet INTERFACE-DOWN-DIAG
R1(config-applet)#  event syslog pattern "%LINEPROTO-5-UPDOWN.*GigabitEthernet0/1.*down"
R1(config-applet)#  action 1.0 cli command "enable"
R1(config-applet)#  action 2.0 cli command "show interfaces GigabitEthernet0/1"
R1(config-applet)#  action 3.0 cli command "show interfaces GigabitEthernet0/1 controller"
R1(config-applet)#  action 4.0 cli command "show logging | last 50"
R1(config-applet)#  action 5.0 syslog msg "DIAG: Gi0/1 down, info collected"

! ── 示例 2：CPU 超阈值时记录进程信息 ──
R1(config)# event manager applet HIGH-CPU
R1(config-applet)#  event snmp oid 1.3.6.1.4.1.9.2.1.58.0 get-type exact \
                     entry-op ge entry-val 90 poll-interval 30
R1(config-applet)#  action 1.0 cli command "enable"
R1(config-applet)#  action 2.0 cli command "show processes cpu sorted | exclude 0.00"
R1(config-applet)#  action 3.0 cli command "show ip nat statistics"
R1(config-applet)#  action 4.0 syslog msg "ALERT: CPU > 90%"

! ── 示例 3：配置变更时自动备份 ──
R1(config)# event manager applet AUTO-BACKUP
R1(config-applet)#  event syslog pattern "%SYS-5-CONFIG_I"
R1(config-applet)#  action 1.0 cli command "enable"
R1(config-applet)#  action 2.0 cli command "copy running-config tftp://10.1.30.220/$_event_pub_time-R1.cfg"
R1(config-applet)#  action 3.0 syslog msg "Config changed, backup uploaded"

! ── 示例 4：定时任务 ──
R1(config)# event manager applet DAILY-CHECK
R1(config-applet)#  event timer cron cron-entry "0 3 * * *"        ! 每天凌晨 3 点
R1(config-applet)#  action 1.0 cli command "enable"
R1(config-applet)#  action 2.0 cli command "show ip route summary"
R1(config-applet)#  action 3.0 cli command "show ip bgp summary"

! ── 示例 5：BGP 邻居 down 时自动切换（谨慎使用）──
R1(config)# event manager applet BGP-FAILOVER
R1(config-applet)#  event syslog pattern "%BGP-5-ADJCHANGE.*Down"
R1(config-applet)#  action 1.0 cli command "enable"
R1(config-applet)#  action 2.0 cli command "configure terminal"
R1(config-applet)#  action 3.0 cli command "ip route 0.0.0.0 0.0.0.0 <备份下一跳> 200"
R1(config-applet)#  action 4.0 cli command "end"
R1(config-applet)#  action 5.0 syslog msg "BGP down, backup route installed"

! ── 查看 ──
R1# show event manager policy registered
R1# show event manager history events
R1# show event manager statistics policy
```

> **EEM 的价值**：故障发生的那一刻自动抓取现场信息。**很多间歇性故障之所以难查，就是因为你赶到时现场已经消失了。** EEM 解决了这个问题。
>
> ⚠️ **谨慎使用会改配置的 EEM**：自动改配置可能引发意外后果。**建议先只做"收集信息 + 告警"，改配置的动作人工确认。**

## ⑧ 综合排障流程

### 8.1 万能排障框架

```
   ① 精确描述现象
      "A 能 ping B，B 不能 ping A" ≠ "网络不通"
      ★ 精确的描述本身就包含了 50% 的答案 ★
        ↓
   ② 确定影响范围
      一台？一个网段？一个区域？全网？
      → 范围决定了问题在哪一层
        ↓
   ③ 什么时候开始的？改了什么？
      ★ 80% 的故障是变更引起的 ★
      show archive log config all
      show logging | include CONFIG_I
        ↓
   ④ 分层定位（每层一个明确的验证命令）
      L1 → show interfaces status
      L2 → show mac address-table / show interfaces trunk
      L3 → show ip route / ping / traceroute
      L4 → telnet <ip> <port>
      L7 → 应用日志
        ↓
   ⑤ 二分法缩小范围
      在中间点测试，判断问题在前半段还是后半段
        ↓
   ⑥ 对比法
      能通的 vs 不能通的，配置差在哪？
      show run interface X | show run interface Y
        ↓
   ⑦ ★ 验证假设 ★
      不要凭猜测就改配置
      先用命令证明你的假设成立
```

### 8.2 常见故障的快速判断表

| 现象 | 最可能的层 | 第一个命令 |
|:--|:--|:--|
| 接口 down/down | L1 | `show interfaces status` |
| 接口 up/down | L2 | `show interfaces` 看封装 |
| 同网段不通 | L2 | `show mac address-table` |
| 跨网段不通 | L3 | `show ip route` |
| **A→B 通，B→A 不通** | **L3 回程路由** | 在 B 上 `show ip route <A>` |
| ping 通但业务不通 | L4 | `telnet <ip> <port>` |
| **小包通大包不通** | **MTU** | `ping size 1500 df-bit` |
| **固定延迟 5 秒** | **DNS AAAA 超时** | `dig AAAA <域名>` |
| 时快时慢 | 拥塞 / 干扰 / 环路 | `show interfaces \| inc rate\|drops` |
| 拿到 169.254.x.x | DHCP | `show ip interface Vlan10 \| inc Helper` |
| 证书报"尚未生效" | **NTP** | `show ntp status` |

## ⑨ 自测题

**1.** `ip helper-address` 除了 DHCP 还转发哪些广播？怎么精简？

<details><summary>答案</summary>

**默认转发 8 种 UDP 广播**：

| 端口 | 服务 | 是否常需要 |
|:--|:--|:--|
| 37 | Time | ❌ 已过时 |
| **49** | TACACS | ❌ 通常单播 |
| **53** | **DNS** | ⚠️ 视情况 |
| **67** | **DHCP Server** | ✅ **必需** |
| **68** | **DHCP Client** | ✅ **必需** |
| **69** | TFTP | ⚠️ 视情况（PXE 启动需要） |
| **137** | NetBIOS Name Service | ❌ **流量大，通常不需要** |
| **138** | NetBIOS Datagram | ❌ **同上** |

**问题**：NetBIOS 广播在 Windows 网络里**非常频繁**（浏览器服务、名称解析、网上邻居）。全部转发会：
- 造成不必要的流量泛洪
- 消耗路由器 CPU
- 可能把广播风暴扩散到其他网段

**精简配置**：
```cisco
! 关闭不需要的
R1(config)# no ip forward-protocol udp 37
R1(config)# no ip forward-protocol udp 49
R1(config)# no ip forward-protocol udp 53
R1(config)# no ip forward-protocol udp 69
R1(config)# no ip forward-protocol udp 137
R1(config)# no ip forward-protocol udp 138

! 确保 DHCP 开着
R1(config)# ip forward-protocol udp 67
R1(config)# ip forward-protocol udp 68
```

**验证**：
```cisco
R1# show ip forward-protocol
IP forwarding is enabled
IP forwarding of UDP broadcasts, protocol ports:
  bootps (67), bootpc (68)                   ← 只剩 DHCP ✓
```

**什么时候需要保留其他端口**：

| 场景 | 需要保留 |
|:--|:--|
| PXE 网络启动 | UDP 69 (TFTP) + 67/68 |
| 老式 Windows 网上邻居 | UDP 137/138（不推荐，用 WINS 或 DNS 替代） |
| 跨网段的 WDS 部署 | UDP 4011 + 67/68 |

**转发其他自定义端口**：
```cisco
R1(config)# ip forward-protocol udp 4011      ! WDS/PXE
```

**★ 另一个重要配置：多个 helper-address 做冗余**
```cisco
R1(config)# interface Vlan10
R1(config-if)# ip helper-address 10.1.30.53
R1(config-if)# ip helper-address 10.1.30.54
```
中继会**同时向两个服务器转发**，客户端收到多个 OFFER 时选第一个。

**验证**：
```cisco
R1# show ip interface Vlan10 | include Helper
  Helper address is 10.1.30.53
  Helper address is 10.1.30.54
```
</details>

**2.** uRPF 的严格模式和松散模式有什么区别？什么场景下严格模式会误伤？

<details><summary>答案</summary>

**uRPF（Unicast Reverse Path Forwarding）：检查收到的包的源地址是否"合理"，防 IP 源地址欺骗。**

| 模式 | 命令 | 检查规则 |
|:--|:--|:--|
| **严格 (strict)** | `ip verify unicast source reachable-via rx` | 到源地址的**最优路由的出接口**必须**就是收到包的接口** |
| **松散 (loose)** | `ip verify unicast source reachable-via any` | 到源地址**在路由表里有任何路由**即可（不管出接口是哪个） |

## 严格模式的误伤场景：非对称路由

```
              ┌──── ISP-A ────┐
   Internet ──┤               ├── R1 ── 内网
              └──── ISP-B ────┘
   
   流量【进来】走 ISP-A（对方的选路决定的）
   流量【出去】走 ISP-B（我的路由表决定的）
        ↓
   R1 在 ISP-A 接口上做严格 uRPF 检查：
   "去这个源地址（比如 8.8.8.8）的最优路由，出接口是 ISP-B"
   "但这个包是从 ISP-A 收到的"
        ↓
   ★ 判定为源地址伪造 → 丢弃 ★
        ↓
   ★ 合法流量被误杀 ★
```

**什么时候会出现非对称路由**：

| 场景 | 说明 |
|:--|:--|
| **多归属（接两个 ISP）** | 最常见 |
| **BGP 入向和出向策略不对称** | LOCAL_PREF 和 AS-Path Prepend 的组合 |
| **ECMP 负载均衡** | 多条等价路径 |
| **HSRP 与路由不对齐** | 主备网关和路由方向不一致 |
| **策略路由（PBR）** | PBR 强制某些流量走特定路径 |

**症状**：**部分流量莫名其妙不通**，而且很难复现（取决于对方的选路）。

```cisco
R1# show ip interface GigabitEthernet0/1 | include verification
  ★ 12345 verification drops ★               ← 这个数字持续增长 = 有误伤
  0 suppressed verification drops
```

## 部署建议

| 位置 | 模式 | 理由 |
|:--|:--|:--|
| **接入层 / 客户边界**（单归属） | ✅ **strict** | 路径确定，无非对称风险 |
| **运营商边界 / 多归属** | **loose** 或不用 | 避免误伤 |
| **内部核心** | 通常不用 | 内部流量可信 |
| **面向不可信网络的边界** | **strict**（如果单归属） | 最大化防护 |

## 允许例外

```cisco
! 用 ACL 放行特定的合法非对称流量
R1(config)# access-list 100 permit ip 203.0.113.0 0.0.0.255 any
R1(config)# access-list 100 permit ip host 0.0.0.0 any          ! 允许 DHCP
R1(config)# interface GigabitEthernet0/1
R1(config-if)# ip verify unicast source reachable-via rx 100
!                                                          ↑ ACL 号
```

**允许默认路由匹配**：
```cisco
R1(config-if)# ip verify unicast source reachable-via rx allow-default
```
**默认不允许用默认路由做 uRPF 检查**（否则有默认路由时几乎什么都能通过）。加 `allow-default` 后放宽。

**允许自环**：
```cisco
R1(config-if)# ip verify unicast source reachable-via rx allow-self-ping
```

## 松散模式的局限

**松散模式几乎只能防"完全伪造的地址"**：
```
   源地址是 10.0.0.1（私网）→ 路由表里没有 → ✅ 拦住
   源地址是 8.8.8.8（真实公网）→ 路由表里有 → ❌ 放行
        ↓
   ★ 攻击者用真实存在的公网地址伪造，松散模式拦不住 ★
```

**所以松散模式主要用于**：
- 过滤 Bogon（未分配的地址空间）
- 配合黑洞路由做 RTBH（Remotely Triggered Black Hole）

**RTBH 的用法**（进阶）：
```cisco
! 把攻击源的地址指向 Null0
R1(config)# ip route <攻击源> 255.255.255.255 Null0
! 松散 uRPF 会认为"到这个源的路由指向 Null0" → 判定不可达 → 丢弃来自它的所有包
R1(config-if)# ip verify unicast source reachable-via any
```

**验证**：
```cisco
R1# show ip interface GigabitEthernet0/1 | include verify|drop
  IP verify source reachable-via RX, ACL 100, allow default
  12345 verification drops
  0 suppressed verification drops

R1# show cef interface GigabitEthernet0/1 | include RPF
```
</details>

**3.** 开了 DHCP Snooping 之后，跨网段的客户端拿不到 IP。为什么？

<details><summary>答案</summary>

**因为 DHCP Snooping 默认会插入 Option 82，而中继（或服务器）收到"带 Option 82 但 giaddr 为 0"的包时会认为不可信，直接丢弃。**

**完整过程**：
```
   ① 客户端发 DISCOVER（广播）
        ↓
   ② 接入交换机的 DHCP Snooping ★ 插入 Option 82 ★
      （记录端口、VLAN、交换机 MAC）
      ★ 但 giaddr 依然是 0.0.0.0 ★（交换机不是中继）
        ↓
   ③ 包到达三层网关（中继）
        ↓
   ④ 中继看到："这个包带 Option 82，但 giaddr 是 0"
      → ★ 判定为不可信（可能是伪造的）→ 丢弃 ★
        ↓
   ★ 客户端拿不到 IP ★
```

**根本原因**：RFC 3046 规定，中继在收到已经带 Option 82 的包时要做可信性判断。IOS 默认不信任 giaddr=0 且带 Option 82 的包。

## 三种解法

**方案 1：交换机不插入 Option 82（★ 最简单）**
```cisco
SW1(config)# no ip dhcp snooping information option
```
**代价**：失去 Option 82 提供的端口定位信息（但 Snooping 绑定表依然工作）。

**方案 2：中继信任 Option 82**
```cisco
! 全局信任
R1(config)# ip dhcp relay information trust-all

! 或按接口信任
R1(config)# interface Vlan10
R1(config-if)# ip dhcp relay information trusted
```

**方案 3：交换机上配置 giaddr**（部分平台支持）
```cisco
SW1(config)# ip dhcp snooping information option format remote-id string SW1-1F
SW1(config-if)# ip dhcp snooping vlan 10 information option format-type circuit-id string Gi1/0/5
```

## 相关的策略配置

```cisco
! 中继对已有 Option 82 的处理策略
R1(config)# ip dhcp relay information policy replace     ! 替换（默认）
R1(config)# ip dhcp relay information policy keep        ! 保留原有的
R1(config)# ip dhcp relay information policy drop        ! 丢弃整个包

! 中继自己是否插入 Option 82
R1(config)# ip dhcp relay information option             ! 插入（默认）
R1(config)# no ip dhcp relay information option          ! 不插入

! 检查 Option 82 的合法性
R1(config)# ip dhcp relay information check              ! 检查（默认）
R1(config)# no ip dhcp relay information check           ! 不检查
```

## 验证

```cisco
! 交换机侧
SW1# show ip dhcp snooping
Switch DHCP snooping is enabled
DHCP snooping is configured on following VLANs: 10,20
★ Insertion of option 82 is enabled ★              ← 确认状态
Interface                  Trusted    Rate limit (pps)
GigabitEthernet1/0/24      yes        unlimited

! 中继侧
R1# show ip dhcp relay information trusted-sources
R1# debug ip dhcp server packet
DHCPD: relay information option exists, but giaddr is zero.    ← ★ 找到了
```

## 相关的另一个坑：DAI/IPSG 与静态 IP 设备

**开了 DHCP Snooping 之后，如果接着开 DAI 或 IPSG**：
```
   静态 IP 的设备（服务器、打印机、摄像头）
        ↓
   ★ 它们不用 DHCP，所以不在 Snooping 绑定表里 ★
        ↓
   ★ DAI 认为它们的 ARP 是伪造的 → 丢弃 ★
   ★ IPSG 认为它们的 IP 是盗用的 → 丢弃 ★
        ↓
   ★ 全部断网 ★
```

**必须手工添加静态绑定**：
```cisco
! IPSG 的静态绑定
SW1(config)# ip source binding 0011.2233.4455 vlan 10 192.168.10.200 interface Gi1/0/30

! DAI 的静态绑定（用 ARP ACL）
SW1(config)# arp access-list STATIC-DEVICES
SW1(config-arp-nacl)#  permit ip host 192.168.10.200 mac host 0011.2233.4455
SW1(config-arp-nacl)#  permit ip host 192.168.10.201 mac host 0011.2233.4456
SW1(config)# ip arp inspection filter STATIC-DEVICES vlan 10
```

**部署顺序（★ 必须遵守）**：
```
   ① 先开 DHCP Snooping，跑一个完整租期周期
        ↓
   ② 检查绑定表覆盖率：show ip dhcp snooping binding
        ↓
   ③ ★ 为所有静态 IP 设备添加手工绑定 ★
        ↓
   ④ 再开 DAI
        ↓
   ⑤ 最后开 IPSG
```

**跳过第 ③ 步 = 一半设备断网。**
</details>

**4.** NAT 表项暴涨、CPU 飙高，怎么快速定位和处理？

<details><summary>答案</summary>

**这个症状十有八九是内网有机器中毒在做端口扫描或参与 DDoS。**

## 快速定位

```cisco
! ① 确认表项数量
R1# show ip nat statistics
Total active translations: ★ 63500 ★ (2 static, 63498 dynamic; 63498 extended)
Peak translations: 64000, occurred 00:15:23 ago
Hits: 12845678  Misses: 45678
                          ↑ Misses 高说明转换失败很多（表满了）

! ② 找出占用最多的主机（★ 关键命令）
R1# show ip nat translations | include 192.168.1.66 | count
Number of lines which match regexp = ★ 45678 ★
                                       ↑ 一台机器占了 4.5 万条

! ③ 批量统计（如果不确定是哪台）
R1# show ip nat translations | exclude ---
! 导出后用脚本统计，或者逐个 IP 试

! ④ 看它在连什么
R1# show ip nat translations | include 192.168.1.66
tcp 202.100.1.1:50001  192.168.1.66:51234  1.2.3.4:445    1.2.3.4:445
tcp 202.100.1.1:50002  192.168.1.66:51235  1.2.3.5:445    1.2.3.5:445
tcp 202.100.1.1:50003  192.168.1.66:51236  1.2.3.6:445    1.2.3.6:445
                                            ↑ ★ 连续扫描 445 端口 = 蠕虫特征 ★

! ⑤ 确认 CPU 占用
R1# show processes cpu sorted | exclude 0.00
CPU utilization for five seconds: 98%/45%; one minute: 95%; five minutes: 92%
 PID Runtime(ms)   Invoked   uSecs   5Sec   1Min   5Min TTY Process
  85    12345678   9876543    1250 ★ 45.2% ★ 43.1% 41.5%   0 IP NAT Ager
                                                                  ↑ NAT 老化进程
```

## 应急处理（三步）

**① 立即限制该主机（不影响其他人）**
```cisco
R1(config)# ip nat translation max-entries host 192.168.1.66 100
```

**② 清理它已有的表项**
```cisco
R1# clear ip nat translation inside 192.168.1.66 *
```

**③ 如果情况严重，直接阻断**
```cisco
R1(config)# ip access-list extended BLOCK-INFECTED
R1(config-ext-nacl)#  deny ip host 192.168.1.66 any log
R1(config-ext-nacl)#  permit ip any any
R1(config)# interface Gi0/0
R1(config-if)# ip access-group BLOCK-INFECTED in
```

**同时通知桌面运维去处理那台机器。**

## 长期加固

```cisco
! ── 全局上限（★ 防止内存耗尽导致设备宕机）──
R1(config)# ip nat translation max-entries 60000

! ── 单主机上限（★ 最重要的一条）──
R1(config)# ip nat translation max-entries all-host 500
!            ↑ 所有主机统一限制为 500 条

! ── 缩短超时（让表项更快释放）──
R1(config)# ip nat translation timeout 3600           ! 通用，默认 24 小时
R1(config)# ip nat translation tcp-timeout 3600
R1(config)# ip nat translation udp-timeout 60         ! 默认 5 分钟 → 1 分钟
R1(config)# ip nat translation icmp-timeout 10        ! 默认 60 秒 → 10 秒
R1(config)# ip nat translation finrst-timeout 30      ! FIN/RST 后保留时间
R1(config)# ip nat translation syn-timeout 30         ! ★ 半开连接超时（防扫描）
```

**★ `syn-timeout` 特别有用**：端口扫描会产生大量"发了 SYN 但没有响应"的半开连接。缩短这个超时能快速释放这些表项。

## 判断是扫描还是正常业务

| 特征 | 扫描/中毒 | 正常业务 |
|:--|:--|:--|
| **目的 IP** | 连续变化（1.2.3.4, 1.2.3.5...） | 相对固定 |
| **目的端口** | 固定（445、3389、22） | 多样 |
| **每条流的字节数** | **极少**（只有 SYN） | 正常 |
| **流的持续时间** | 极短 | 有长有短 |
| **成功率** | 极低（大量 SYN 无响应） | 高 |

```cisco
R1# show flow monitor FLOW-MON cache | include 192.168.1.66
! 看 bytes 和 packets 列，如果每条流只有几十字节 → 扫描
```

**5.** 描述一个完整的"用户报网络慢"的排障流程。

<details><summary>答案</summary>

## 第一步：精确化问题（★ 最重要，很多人跳过）

**"网络慢"是最模糊的报障。必须问清楚**：

| 问题 | 为什么问 |
|:--|:--|
| **具体慢什么？** | 打开网页慢？下载慢？某个应用慢？全部？ |
| **什么时候开始的？** | 定位是否与某次变更相关 |
| **所有人都这样吗？** | 一个人 vs 一个部门 vs 全公司 → **决定排查范围** |
| **有线还是无线？** | 完全不同的排查路径 |
| **一直慢还是间歇？** | 间歇的更难查，需要持续监控 |
| **访问内网还是外网？** | 缩小范围 |
| **有没有具体的时间点/规律？** | 比如每天上午 10 点（备份任务？） |

**★ 精确的描述本身就包含了 50% 的答案。**

**例**：
```
   模糊："网络很慢"
   精确："财务部 12 个人，从今天上午 9 点开始，
          访问总部 ERP 系统（10.1.30.50:8080）时页面加载要 30 秒，
          但访问互联网正常，访问本地文件服务器也正常"
        ↓
   ★ 范围明确了：财务部 → 总部 ERP 的这条路径 ★
```

## 第二步：确定影响范围

```
   一个人  → 终端问题、端口问题、该用户的策略
   一个网段 → VLAN、网关、该网段的 ACL/QoS
   一栋楼   → 汇聚层、上联链路
   全公司   → 核心、出口、DNS、DHCP
   
   ★ 范围决定了你该去看哪一层 ★
```

## 第三步：查变更

```cisco
! ★ 80% 的故障是变更引起的 ★
R1# show archive log config all | include <时间范围>
R1# show logging | include CONFIG_I
R1# show logging | include LINK|LINEPROTO
```

**同时问运维团队**："今天有人改过什么吗？"（包括服务器、防火墙、应用）

## 第四步：分层验证

```cisco
! ── L1 物理层 ──
SW1# show interfaces status | include err|down
SW1# show interfaces GigabitEthernet1/0/5 | include error|drop|rate
     ★ CRC error 增长 → 线缆/光模块问题
     ★ late collision → 双工不匹配
     ★ output drops → 拥塞
     ★ input errors → 物理层质量

! ── L2 链路层 ──
SW1# show spanning-tree vlan 10 detail | include occurr|from
     Number of topology changes ★ 1245 ★ last change occurred 00:00:12 ago
             from GigabitEthernet1/0/7
     ★ 拓扑变化次数很高 → 有端口在反复 flap → 找到源头
     
SW1# show mac address-table address <某MAC>
     ★ 反复执行，如果端口在变 → MAC 震荡 → 环路

! ── L3 网络层 ──
R1# ping <目标> source <源接口>
R1# traceroute <目标> source <源接口>
     ★ 看哪一跳开始延迟暴增
     
R1# show ip route <目标>
     ★ 路由走的路径对吗？有没有次优路由？

! ── L4 传输层 ──

     ★ Open = 通；refused = 服务没起；超时 = 被拦

     ★ 小包通大包不通 → MTU 问题（隧道场景高发）
```

## 第七步：应用层（如果网络层都正常）

```
   网络层测试全部正常，但业务还是慢
        ↓
   ① 抓包看 TCP 交互
      · 三次握手耗时多久？→ 网络延迟
      · 服务器第一个响应包耗时多久？→ ★ 服务器处理慢 ★
      · 有没有大量重传？→ 丢包
      · 窗口大小是否被压缩？→ 接收端处理不过来
        ↓
   ② 服务器侧检查
      · CPU/内存/磁盘 IO
      · 数据库慢查询
      · 应用日志
        ↓
   ③ 如果服务器响应就是慢 → ★ 不是网络问题 ★
      → 有理有据地交给应用团队
```

**抓包判断"网络慢"还是"服务器慢"**：
```
   客户端 → SYN                    T=0
   服务器 → SYN+ACK                T=15ms      ← 网络往返 15ms，正常
   客户端 → ACK                    T=15ms
   客户端 → HTTP GET               T=16ms
   服务器 → HTTP 200 OK            T=★ 8500ms ★  ← ★ 服务器处理了 8.5 秒！
   
   ★ 结论：网络没问题，服务器慢 ★
```

**这是网络工程师最有价值的能力之一**：用数据证明问题不在网络，而不是靠嘴争论。

## 第八步：输出结论

**无论结果如何，给出明确的结论**：

```
   ★ 好的结论：
   "财务部访问 ERP 慢的根因是：出口链路在上午 9-10 点被备份流量打满
    （NetFlow 显示 192.168.1.100 在向 203.x.x.x 上传，
     平均 95Mbps，占用了 100M 出口的 95%）。
    已配置 QoS 将备份流量限制在 20Mbps，ERP 流量标记为 AF21 保证 25% 带宽。
    建议：将备份任务调整到夜间执行。"

   ✗ 差的结论：
   "重启一下试试。"
   "应该是网络波动。"
```
