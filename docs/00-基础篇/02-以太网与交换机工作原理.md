# 02 · 以太网与交换机工作原理

## ① 这章解决什么问题

办公室里插了 200 台电脑到几台交换机上，它们互相之间能通信。可交换机凭什么知道"发给张三的数据该从 24 口出去，而不是 1 口"？

更进一步：为什么一台服务器网卡坏了在网上狂发广播，能把整个楼层的网都拖垮？为什么两台交换机之间接两根线会瞬间瘫痪整个网络？

这些问题的答案全在以太网的工作机制里。理解它，你才能理解后面的 VLAN（切割广播域）和 STP（防止环路）为什么必须存在。

## ② 原理讲透

### 2.1 以太网帧结构

```
 ┌─────────┬─────┬────────┬────────┬──────┬──────────────┬─────┐
 │ 前导码   │ SFD │ 目的MAC │ 源MAC  │ 类型 │    数据载荷    │ FCS │
 │  7字节   │1字节│  6字节  │ 6字节  │ 2字节│  46~1500字节  │4字节│
 └─────────┴─────┴────────┴────────┴──────┴──────────────┴─────┘
           ← 硬件同步用，不计入帧长 →
                            ← 帧长 64 ~ 1518 字节 →
```

关键字段：

| 字段 | 说明 |
|:--|:--|
| **目的 MAC** | 交换机唯一关心的转发依据 |
| **源 MAC** | 交换机用它来**学习** MAC 地址表 |
| **类型 (EtherType)** | 上层协议：`0x0800`=IPv4，`0x0806`=ARP，`0x86DD`=IPv6，`0x8100`=802.1Q VLAN标签 |
| **FCS** | CRC 校验，错了就丢，不重传（重传是上层的事） |

**最小帧 64 字节**：这不是随便定的，它源于 CSMA/CD 冲突检测的时间要求——帧太短的话，发完了冲突信号还没传回来，就检测不到冲突。载荷不足 46 字节会被填充（Padding）。

**MTU 1500**：载荷最大 1500 字节，这个数字贯穿你整个网络生涯。**GRE、IPsec、VXLAN、MPLS 都要额外加头，会导致有效 MTU 变小**，进而引发"能 ping 通但打不开网页"的经典故障。这条线索请记牢，ENARSI 排障必考。

### 2.2 MAC 地址

48 位，通常写成 `00:1A:2B:3C:4D:5E` 或 Cisco 风格 `001a.2b3c.4d5e`。

```
 00:1A:2B : 3C:4D:5E
 └───┬──┘   └───┬──┘
   OUI        厂商自行分配
 （厂商标识，向 IEEE 申请）
```

第一个字节的最低位是 **I/G 位**：
- `0` = 单播（Unicast）
- `1` = 组播/广播（Multicast/Broadcast）

所以 `FF:FF:FF:FF:FF:FF` 是广播；`01:00:5E:xx:xx:xx` 是 IPv4 组播映射的 MAC；`01:80:C2:00:00:00` 是 STP BPDU 的目的 MAC（这个后面 STP 章节会再见）。

### 2.3 交换机的三个核心行为

交换机对每个进来的帧，只做三件事之一：

```
                     收到一个帧
                          │
             ┌────────────┴────────────┐
             │  1. 用源MAC学习/刷新表项  │  ← 无条件执行
             └────────────┬────────────┘
                          │
                查目的MAC在MAC表里吗？
                    ┌─────┴─────┐
                   在           不在
                    │             │
              ┌─────▼─────┐  ┌────▼──────────────────┐
              │  转发     │  │  泛洪 Flooding         │
              │ Forward   │  │  除入端口外所有同VLAN口 │
              └───────────┘  └───────────────────────┘

              （若目的口==入端口 → 过滤 Filter，丢弃）
```

| 行为 | 英文 | 触发条件 |
|:--|:--|:--|
| **学习** | Learning | 每收到一个帧，记录 `源MAC ↔ 入端口 ↔ VLAN` |
| **转发** | Forwarding | 目的 MAC 在表里，且出端口 ≠ 入端口 |
| **泛洪** | Flooding | 目的 MAC 不在表里（未知单播）/ 广播 / 未知组播 |
| **过滤** | Filtering | 目的 MAC 对应的端口就是入端口（同一网段，没必要转） |

**MAC 地址表老化时间**：Cisco 默认 **300 秒（5 分钟）**。5 分钟内没再收到某 MAC 的帧，表项删除。

> **实战意义**：这就是为什么"某台机器长时间不通信后，第一个包会走泛洪"。也是网络里持续存在少量泛洪流量的正常原因。

### 2.4 冲突域与广播域（重要概念）

| | 冲突域 (Collision Domain) | 广播域 (Broadcast Domain) |
|:--|:--|:--|
| 定义 | 会发生 CSMA/CD 冲突的范围 | 广播帧能到达的范围 |
| **集线器 Hub** | 所有口是**1 个**冲突域 | 所有口是 1 个广播域 |
| **交换机 Switch** | **每个口 1 个**冲突域 | 所有口（同 VLAN）是 1 个广播域 |
| **路由器 Router** | 每个口 1 个 | **每个口 1 个**（隔离广播） |

**核心结论**：
- **交换机隔离冲突域，不隔离广播域。**
- **路由器（和 VLAN）隔离广播域。**

这一句话直接引出了 VLAN 存在的意义：交换机再多，整栋楼还是一个广播域，一台机器发广播全楼都收——所以必须用 VLAN 切开。

### 2.5 广播风暴：为什么二层环路是灾难

```
        ┌──────────┐
        │   SW1    │
        └──┬────┬──┘
           │    │      ← 两根线，形成环路
        ┌──┴────┴──┐
        │   SW2    │
        └──────────┘
```

一个广播帧进来：
1. SW1 泛洪到两条链路
2. SW2 从链路 A 收到，泛洪到链路 B（和其他口）
3. SW1 从链路 B 又收到，再泛洪到链路 A
4. **无限循环，且每循环一次帧的数量翻倍**

为什么不会自己停？因为**以太网帧头里没有 TTL 字段**。IP 包靠 TTL 防环，二层帧没这个机制。

三个后果：
1. **广播风暴**：链路带宽被瞬间打满
2. **MAC 表震荡**：同一个 MAC 一会儿从 A 口学到、一会儿从 B 口学到，表项疯狂翻转
3. **重复帧**：主机收到多份相同的帧

**症状识别**：交换机所有端口指示灯狂闪、CPU 100%、Console 都登不上去、`show mac address-table` 看到表项不停变化。

这就是 **STP 生成树协议**存在的唯一理由——用软件在有物理冗余的拓扑上，逻辑地阻塞掉多余链路，形成无环的树。详见 [Stage 1 第 2 章](../01-CCNA补齐篇/02-STP生成树协议.md)。

### 2.6 双工与速率协商

| 模式 | 说明 |
|:--|:--|
| 半双工 Half-duplex | 同时只能收或发，需要 CSMA/CD，共享介质时代产物 |
| 全双工 Full-duplex | 收发独立，无冲突，现代交换网络的标准 |

**经典故障：双工不匹配（Duplex Mismatch）**

一端手工设成 `full`，另一端 `auto`。auto 端协商失败会退到 **half**，于是：

- 全双工端：想发就发，不检测冲突
- 半双工端：检测到"冲突"，执行退避重传

**症状**：链路能通，但**性能极差**（可能只有标称带宽的 1/10），大文件传输超时，`show interfaces` 里看到大量 `late collisions`（半双工侧）和 `runts` / `FCS errors`（全双工侧）。

> **排障要点**：`late collision` 计数器不为 0，基本可以直接锁定双工不匹配。正常的冲突发生在帧的前 64 字节内；"late" 意味着冲突发生在已经发了 64 字节之后——这只能是对端不认为存在冲突所致。

**规范做法**：两端都设 auto，或两端都手工写死。**绝不能一端 auto、一端手工。**

## ③ 配置命令

### Cisco

```cisco
! ── 查看 MAC 地址表 ──
Switch# show mac address-table
Switch# show mac address-table dynamic
Switch# show mac address-table address 001a.2b3c.4d5e
Switch# show mac address-table interface GigabitEthernet0/1
Switch# show mac address-table count

! 修改老化时间（默认 300 秒）
Switch(config)# mac address-table aging-time 600

! 配置静态 MAC 表项
Switch(config)# mac address-table static 001a.2b3c.4d5e vlan 10 interface Gi0/5

! 清空动态表项
Switch# clear mac address-table dynamic

! ── 速率与双工 ──
Switch(config)# interface GigabitEthernet0/1
Switch(config-if)# speed auto
Switch(config-if)# duplex auto
! 或写死
Switch(config-if)# speed 1000
Switch(config-if)# duplex full

! ── 接口统计与错误计数 ──
Switch# show interfaces GigabitEthernet0/1
Switch# show interfaces status
Switch# show interfaces counters errors
Switch# clear counters GigabitEthernet0/1

! ── 风暴抑制（限制广播/组播/未知单播占比）──
Switch(config-if)# storm-control broadcast level 5.00
Switch(config-if)# storm-control multicast level 5.00
Switch(config-if)# storm-control action shutdown
Switch# show storm-control
```

## ④ 配套实验：观察 MAC 学习与泛洪

**拓扑**：
```
PC1 ─── Gi0/1 ┌──────────┐ Gi0/2 ─── PC2
              │   SW1    │
PC3 ─── Gi0/3 └──────────┘
```
三台 PC 同网段 `192.168.10.0/24`。

**步骤 1：观察初始空表**
```cisco
SW1# clear mac address-table dynamic
SW1# show mac address-table dynamic
! 应该是空的
```

**步骤 2：单向通信，观察学习**

在 PC1 上 ping PC2 一次，然后立刻：
```cisco
SW1# show mac address-table dynamic
```
**预期**：看到 PC1 和 PC2 两条表项（PC2 回包时被学到）。PC3 不在表里，因为它没发过任何帧。

**步骤 3：验证泛洪**

在 **PC3 上开抓包**，然后清空 MAC 表，立即让 PC1 ping PC2：
```cisco
SW1# clear mac address-table dynamic
```
**预期**：PC3 会抓到 PC1→PC2 的**第一个 ICMP 包**（因为此时目的 MAC 未知，交换机泛洪）。后续的包 PC3 抓不到（表项已学到，改为定向转发）。

这个实验非常直观地证明了「未知单播泛洪」的存在。

**步骤 4：制造并观察环路（危险，仅限实验环境）**

在 SW1 和 SW2 之间接两根线，**先关掉 STP**：
```cisco
SW1(config)# no spanning-tree vlan 1
SW2(config)# no spanning-tree vlan 1
```
然后从任一 PC 发一个广播（比如 `arping` 或 ping 广播地址）。

**预期**：CPU 飙升，`show processes cpu` 看到极高占用，端口灯狂闪。

**恢复**：
```cisco
SW1(config)# spanning-tree vlan 1
```
> ⚠️ **只在实验环境做。生产网络关 STP 后接冗余链路 = 全网瘫痪。**

## ⑤ 排障思路

### 症状 → 怀疑点 → 验证 → 根因

| 症状 | 怀疑点 | 验证命令 | 常见根因 |
|:--|:--|:--|:--|
| 接口 down/down | 物理层 | `show interfaces` 看 `line protocol` | 网线断、对端 shutdown、光模块故障 |
| 接口 up/down | 二层协商 | `show interfaces` 看封装类型 | 封装不匹配（串口）、keepalive 失败 |
| 通但极慢，大量 late collision | 双工不匹配 | `show interfaces counters errors` | 一端 auto 一端手工 |
| 大量 CRC/FCS error | 物理层质量 | `show interfaces` 看 `input errors` | 线缆劣质、超长、电磁干扰、接头氧化 |
| CPU 100% + 端口灯狂闪 | 二层环路 | `show processes cpu`、`show mac address-table` 看是否震荡 | 环路 + STP 未生效/被关 |
| MAC 表项在两个口间跳变 | MAC 震荡 | `show mac address-table address <MAC>` 反复执行 | 环路，或双网卡负载均衡配置错 |
| 某 MAC 学不到 | VLAN 或端口 | `show mac address-table interface X` | 端口在错误 VLAN、端口 err-disabled |

### 关键计数器解读

```cisco
SW1# show interfaces GigabitEthernet0/1
  ...
  5 minute input rate 1000 bits/sec, 2 packets/sec
     12345 packets input, 1234567 bytes
     Received 100 broadcasts (50 multicasts)
     0 runts, 0 giants, 0 throttles
     15 input errors, 15 CRC, 0 frame, 0 overrun, 0 ignored
     ...
     0 output errors, 234 collisions, 0 interface resets
     45 late collision, 0 deferred
```

| 计数器 | 含义 | 指向 |
|:--|:--|:--|
| `runts` | 小于 64 字节的帧 | 冲突、双工不匹配 |
| `giants` | 超过 MTU 的帧 | MTU 不匹配、VLAN 标签未预期 |
| `CRC` | 校验失败 | **物理层**：线缆/接口/干扰 |
| `input errors` | 各类输入错误总和 | 看细分项定位 |
| `collisions` | 正常冲突 | 半双工环境，全双工下应为 0 |
| **`late collision`** | 64 字节后才发生的冲突 | **双工不匹配**（几乎可直接定性） |
| `interface resets` | 接口复位次数 | 链路不稳定、时钟问题 |

## ⑥ 考点提示 + 自测题

### 考点

- **未知单播泛洪**行为是理解 MAC 泛洪攻击（`macof`）和 Port Security 的前提。
- **冲突域 vs 广播域**：ENCOR 设计题会隐含这个概念（比如"如何减少广播域大小"）。
- **MTU 1500** 与后续 GRE/IPsec/VXLAN 的开销叠加是 ENARSI 高频排障点。
- **late collision = 双工不匹配** 是经典送分题。

### 自测题

**1.** 交换机收到一个目的 MAC 为 `FF:FF:FF:FF:FF:FF` 的帧，会怎么处理？

<details><summary>答案</summary>

**泛洪到同 VLAN 的所有端口（入端口除外）**。广播帧永远不会被交换机"学习"或"定向转发"——注意，交换机学习的是**源 MAC**，广播地址只会出现在目的字段，不会被写进 MAC 表。
</details>

**2.** 一台 24 口交换机，全部端口在 VLAN 1。有几个冲突域？几个广播域？

<details><summary>答案</summary>

- **24 个冲突域**（交换机每个端口独立一个冲突域）
- **1 个广播域**（同一 VLAN 内所有端口共享）

如果换成 24 口集线器：1 个冲突域，1 个广播域。
如果把 24 口分成 4 个 VLAN：24 个冲突域，4 个广播域。
</details>

**3.** 为什么二层环路会导致广播风暴，而三层环路不会导致同样严重的后果？

<details><summary>答案</summary>

**以太网帧头没有 TTL（跳数限制）字段**，帧在环路里会无限循环，而且每经过一个泛洪点数量翻倍，呈指数级增长。

IP 头有 **TTL** 字段，每经过一台路由器减 1，到 0 就丢弃。所以三层环路虽然会导致数据包绕圈、延迟增加、路由不可达，但不会出现指数级的流量爆炸。

这也是为什么二层必须有 STP，而三层的路由协议只需要靠水平分割、毒性逆转、SPF 算法等机制防环——严重程度完全不在一个量级。
</details>

**4.** `show interfaces` 里 `late collision` 计数持续增长，最可能是什么问题？怎么修？

<details><summary>答案</summary>

**双工不匹配**（Duplex Mismatch）。一端全双工、一端半双工。

正常冲突发生在帧的前 64 字节（"冲突窗口"）内。发生在 64 字节之后的冲突（late collision）说明对端根本不认为存在冲突，一直在发——这只能是全双工/半双工混搭造成的。

**修法**：检查链路两端的 `speed`/`duplex` 配置，要么两端都 `auto`，要么两端都写死成相同值。**最忌讳一端 auto、一端手工**——因为自动协商依赖对端也参与协商，对端写死后不发协商信号，auto 端只能靠电平检测退回到 10M/half。
</details>

**5.** 客户反馈"网络时快时慢"，你 `show mac address-table address 0050.5600.1234` 连续执行三次，发现该 MAC 一会儿在 Gi0/1、一会儿在 Gi0/24。这说明什么？

<details><summary>答案</summary>

**MAC 地址震荡（MAC flapping）**，几乎可以确定存在**二层环路**。

同一个源 MAC 的帧从两个不同端口进来，说明它绕了一圈又回来了。

**下一步**：
1. `show spanning-tree` 确认 STP 是否运行、根桥在哪、是否有端口该阻塞却没阻塞
2. 检查是否有人把两个网口接到同一台交换机（常见于会议室私接小交换机/傻瓜 HUB）
3. 生产环境应急：先 `shutdown` 其中一个可疑端口止血，再排查
4. 长期：开启 `spanning-tree bpduguard`、`storm-control`、端口下接终端启用 `portfast + bpduguard`
</details>
