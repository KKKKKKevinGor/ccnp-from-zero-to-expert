# 11 · 无线架构与漫游

## ① 这章解决什么问题

[Stage 1 第 8 章](../01-CCNA补齐篇/08-无线与安全基础.md) 讲了无线的物理层基础（信道、干扰、加密）。这一章要解决的是**企业级无线架构**的问题：

1. 一栋楼 48 个 AP，怎么统一管理？总不能一台一台登上去配吧
2. 用户从 3 楼走到 8 楼，**通话不能断**——AP 之间怎么切换？
3. 跨楼层意味着可能跨 VLAN，**IP 变了连接就断了**，怎么办？
4. AP 怎么找到控制器？找不到怎么排查？

这些问题的答案是 **WLC + CAPWAP + 漫游机制**。

## ② 无线架构演进

### 2.1 三代架构

| 架构 | 说明 | 适用规模 |
|:--|:--|:--|
| **自治 AP（Autonomous）** | 每台 AP 独立配置，各管各的 | 1–3 台 |
| **集中式（WLC + Lightweight AP）** | 控制器统一管理，AP 只负责射频 | ★ **企业标准** |
| **云管理（Meraki / Mobility Express）** | 控制器在云端或某台 AP 上 | 中小企业、分支 |

**自治 AP 的问题**：
- 48 台 AP 要配 48 遍，**配置容易不一致**
- **无法无缝漫游**（每台 AP 独立，客户端切换等于重新连接）
- 无法统一做射频优化（信道、功率自动调整）
- 无法集中认证和策略

### 2.2 集中式架构（WLC + LAP）

```
       ┌──────────────────────────────┐
       │           WLC                │  ← 无线控制器
       │  · 配置下发   · 认证          │
       │  · 漫游管理   · 射频管理(RRM) │
       │  · 策略/QoS   · 安全          │
       └───────┬──────────────────────┘
               │  CAPWAP 隧道
     ┌─────────┼─────────┐
     │         │         │
  [AP-1]    [AP-2]    [AP-3]     ← 轻量 AP（Lightweight AP）
                                    只负责射频收发和实时功能
```

**功能划分（Split-MAC 架构）**：

| 功能 | 在哪执行 |
|:--|:--|
| **实时功能**（AP 侧） | 802.11 帧的收发与 ACK、加解密、beacon/probe 响应、数据加密、EDCA 队列 |
| **非实时功能**（WLC 侧） | 认证、关联管理、漫游、安全策略、QoS 策略、RRM、配置管理 |

**为什么这么分**：实时功能必须在 AP 上做（时延要求微秒级，来不及送到 WLC），管理功能集中做（一致性和效率）。

## ③ CAPWAP

### 3.1 两条隧道（★ 高频考点）

**CAPWAP = Control And Provisioning of Wireless Access Points**（RFC 5415），取代了早期的 LWAPP。

| 隧道 | **端口** | 传输内容 | 默认加密 |
|:--|:--|:--|:--|
| **控制隧道** | **UDP 5246** | AP 注册、配置下发、固件升级、统计上报、管理消息 | ✅ **DTLS** |
| **数据隧道** | **UDP 5247** | 用户业务数据 | ❌ 默认不加密（可选开启） |

> **为什么控制加密、数据不加密**：
> - 控制隧道传配置和凭据，**流量小**，加密开销可接受
> - 数据隧道流量巨大，加密会**显著增加 AP 和 WLC 的 CPU 负担**（部分型号吞吐下降 50%+）
> - 用户数据在无线侧已经被 WPA2/WPA3 加密了

**MTU 提醒**：CAPWAP 封装增加约 **50-60 字节**。如果 AP 和 WLC 之间跨 WAN 或隧道，可能需要调整 MTU，否则出现"AP 能注册但客户端上网异常"。

### 3.2 AP 发现 WLC 的顺序（★ 必考）

```
① AP 本地缓存的 WLC 列表（之前成功连过的，存在闪存里）
        ↓ 没有
② ★ DHCP Option 43 ★
        ↓ 没有
③ DNS 解析 CISCO-CAPWAP-CONTROLLER.<本地域名>
        ↓ 没有
④ 二层广播（只在同网段有效）
        ↓ 都失败
   AP 重启，重新尝试
```

**DHCP Option 43 配置（最常用）**：

```cisco
R1(config)# ip dhcp pool AP-POOL
R1(dhcp-config)#  network 192.168.90.0 255.255.255.0
R1(dhcp-config)#  default-router 192.168.90.1
R1(dhcp-config)#  dns-server 10.0.0.53
R1(dhcp-config)#  option 43 hex f104.0a00.0032
!                             ↑↑ ↑↑ ↑↑↑↑↑↑↑↑
!                             │  │  └─ WLC IP 的十六进制
!                             │  └──── 长度（字节数 × 4，十六进制）
!                             └─────── 类型码 f1
```

**Option 43 编码规则**：
```
f1 <长度> <WLC1的IP十六进制> <WLC2的IP十六进制> ...

一个 WLC：10.0.0.50
  10 = 0a, 0 = 00, 0 = 00, 50 = 32
  → f1 04 0a000032

两个 WLC：10.0.0.50 和 10.0.0.51
  → f1 08 0a000032 0a000033
     ↑  ↑
    类型 长度=8（2个IP × 4字节）
```

**在 Windows DHCP 服务器上**：作用域选项 → 043 供应商特定信息 → 输入相同的十六进制值。

### 3.3 AP 注册流程

```
① AP 开机，通过 DHCP 获取 IP
② 通过发现机制找到 WLC 的 IP
③ 发送 CAPWAP Discovery Request（UDP 5246）
④ WLC 回 Discovery Response（携带自己的负载情况）
⑤ AP 选择一个 WLC，发起 DTLS 握手（证书互验）
⑥ 发送 Join Request
⑦ WLC 回 Join Response
⑧ ★ 版本检查 ★：AP 固件版本与 WLC 不一致 → 自动下载升级 → 重启
⑨ 配置下发（SSID、信道、功率、安全策略）
⑩ AP 进入 Run 状态，开始服务客户端
```

**排障命令**：
```cisco
! 在 AP 上（Console 或 SSH）
AP# show capwap client rcb
AP# show capwap ip config
AP# show capwap client mn
AP# debug capwap client event
AP# capwap ap controller ip address 10.0.0.50    ! 手工指定 WLC

! 在 WLC 上
(WLC) > show ap join stats summary all
(WLC) > show ap join stats detailed <AP-MAC>
(WLC) > show ap summary
(WLC) > debug capwap events enable
(WLC) > debug capwap errors enable
```

### 3.4 AP 模式

| 模式 | 说明 | 用途 |
|:--|:--|:--|
| **Local**（默认） | 数据经 CAPWAP 隧道回 WLC 转发 | 总部、集中策略 |
| **FlexConnect** | **数据在 AP 本地直接转发到有线网** | ★ **分支机构** |
| **Monitor** | 不服务客户端，只做扫描和检测 | 无线 IPS |
| **Sniffer** | 抓包模式，把捕获的帧送到分析主机 | 排障 |
| **Bridge / Mesh** | 无线网桥/网状网 | 户外、跨楼互联 |
| **Rogue Detector** | 检测非法 AP | 安全 |
| **SE-Connect** | 频谱分析（CleanAir） | 干扰排查 |

**Local Mode vs FlexConnect（★ 考点）**：

```
   Local Mode（集中交换）：
   
   [客户端] → [AP] ──CAPWAP隧道──> [WLC] → [有线网]
                     ↑ 所有数据都要绕到 WLC
                     
   问题：分支的客户端访问分支本地的服务器，
        流量要【绕到总部再绕回来】，浪费 WAN 带宽 + 延迟高


   FlexConnect（本地交换）：
   
   [客户端] → [AP] ──直接本地转发──> [分支有线网]
                │
                └─ CAPWAP 控制隧道 ──> [总部 WLC]
                   （只传控制消息）
                   
   优势：数据本地转发，不占 WAN 带宽
        WAN 断了 AP 还能继续服务（Standalone 模式）
```

**FlexConnect 的两种状态**：

| 状态 | 条件 | 行为 |
|:--|:--|:--|
| **Connected** | 能连上 WLC | 认证可以由 WLC 做（中心认证）或本地做 |
| **Standalone** | **WLC 不可达** | AP 独立工作，用本地缓存的策略和本地认证 |

```
! FlexConnect 配置（WLC 上）
Wireless > Access Points > <AP> > General > AP Mode: FlexConnect
Wireless > Access Points > <AP> > FlexConnect > VLAN Support ☑
                                              > Native VLAN ID: 1
                                              > VLAN Mappings: SSID → VLAN
```

## ④ 漫游（Roaming）

### 4.1 漫游的类型

```
   客户端从 AP-1 移动到 AP-2
        ↓
   两个 AP 在同一个 WLC 上？
        ├─ 是 → ★ 站内漫游（Intra-Controller）★  最简单
        └─ 否 → 两个 WLC 在同一个移动组？
                 ├─ 是 → ★ 站间漫游（Inter-Controller）★
                 └─ 否 → 需要移动组配置
                 
   客户端的 VLAN/子网变了？
        ├─ 没变 → ★ L2 漫游 ★（IP 不变，简单）
        └─ 变了 → ★ L3 漫游 ★（需要锚点隧道）
```

| 类型 | 说明 | IP 是否变化 | 机制 |
|:--|:--|:--|:--|
| **站内 L2 漫游** | 同 WLC，同 VLAN | 不变 | WLC 内部更新客户端表 |
| **站间 L2 漫游** | 跨 WLC，同 VLAN | 不变 | 客户端数据库在 WLC 间转移 |
| **L3 漫游** | 跨 WLC，**跨 VLAN/子网** | **不变（关键！）** | **Anchor / Foreign 隧道** |

### 4.2 L3 漫游：Anchor 与 Foreign（★ 核心概念）

**问题**：客户端从 VLAN 10（3楼）漫游到 VLAN 20（8楼）。如果换 IP，所有 TCP 连接都断了。

**解法：让客户端保持原来的 IP，流量通过隧道回到原来的 WLC。**

```
   ┌─────────────────┐         EoIP 隧道         ┌─────────────────┐
   │  WLC-A          │═══════════════════════════│  WLC-B          │
   │  ★ Anchor ★     │                           │  ★ Foreign ★    │
   │  （锚点控制器）    │                           │  （外部控制器）    │
   │  客户端的"户口"   │                           │  客户端"现在在这" │
   │  VLAN 10        │                           │  VLAN 20        │
   └────────┬────────┘                           └────────┬────────┘
            │                                             │
         [AP-1] 3楼                                    [AP-2] 8楼
                                                          │
                                                     [客户端]
                                                  IP 仍然是 VLAN 10 的
```

| 角色 | 定义 | 职责 |
|:--|:--|:--|
| **Anchor WLC** | 客户端**最初关联**的那个 WLC | **保存客户端的 IP 和会话状态**，所有流量最终从这里出网 |
| **Foreign WLC** | 客户端**当前所在**的 WLC | 通过隧道把客户端流量转发给 Anchor |

**流量路径**：
```
客户端 → AP-2 → Foreign WLC → ★EoIP/CAPWAP 隧道★ → Anchor WLC → 有线网
```

> **代价**：流量绕路。客户端明明在 8 楼，流量却要跑回 3 楼的 WLC 才能出网。**所以 L3 漫游能避免就避免——最好的设计是让整个园区的无线用同一个 VLAN/子网。**

**Mobility Group（移动组）**：
- WLC 之间要互相识别，必须配置在**同一个移动组**
- 组名和成员列表必须**在所有 WLC 上一致**
- 最多 24 个 WLC 一组

```
(WLC) > config mobility group domain CAMPUS-A
(WLC) > config mobility group member add <MAC> <IP> CAMPUS-A
(WLC) > show mobility summary
```

### 4.3 快速漫游技术（★ 语音必备）

**问题**：标准的 802.11 漫游需要重新完整认证：
```
   探测 → 认证 → 关联 → ★ 完整的 802.1X/EAP 认证 ★ → 密钥协商
                            ↑ 需要往返 RADIUS 服务器多次
                            ↑ 耗时 300-500ms 甚至更久
```

**300ms 以上的中断，语音通话会明显卡顿甚至掉线**（语音要求切换 < 50ms）。

**三个快速漫游标准**：

| 技术 | 标准 | 作用 |
|:--|:--|:--|
| **802.11r** | Fast BSS Transition (FT) | ★ **预先协商密钥**，漫游时跳过完整 EAP 认证 |
| **802.11k** | Neighbor Report | AP 告诉客户端"你旁边还有哪些 AP，信道是多少" → **减少扫描时间** |
| **802.11v** | BSS Transition Management | AP **主动引导**客户端漫游到更优的 AP（负载均衡） |

**三者配合**：
```
   802.11k：客户端知道该往哪扫（不用扫全部信道）
        ↓
   802.11v：AP 建议"你该切到 AP-5 了"
        ↓
   802.11r：切换时跳过完整认证，★ 50ms 内完成 ★
```

**Cisco 私有的快速漫游技术**（历史遗留，了解即可）：

| 技术 | 说明 |
|:--|:--|
| **CCKM** (Cisco Centralized Key Management) | Cisco 私有，需要 CCX 客户端 |
| **PMK Caching / OKC** | 缓存主密钥，避免重复完整认证 |
| **Sticky Key Caching** | 缓存曾经关联过的 AP 的密钥 |

```
! WLC 上启用 802.11r/k/v
WLANs > <WLAN> > Security > Layer 2 > Fast Transition: Enabled
WLANs > <WLAN> > Advanced > 802.11k: Neighbor List ☑
WLANs > <WLAN> > Advanced > 802.11v: BSS Transition ☑
```

> ⚠️ **802.11r 的兼容性问题**：部分老设备（尤其是老 Android 和某些 IoT 设备）**开启 802.11r 后无法连接**。
>
> **解决方案：Adaptive 802.11r**（Cisco 的做法）——对支持的客户端启用 FT，对不支持的自动降级。或者建两个 SSID：一个开 FT 给语音设备，一个不开给普通设备。

### 4.4 客户端才是漫游的决策者（重要认知）

**关键事实：漫游是【客户端】决定的，不是 AP 或 WLC。**

```
   客户端持续监测当前 AP 的信号强度（RSSI）
        ↓
   低于某个阈值（因厂商而异，通常 -70 ~ -75 dBm）
        ↓
   ★ 客户端主动扫描并切换到更强的 AP ★
```

**这意味着**：
- 网络侧只能"引导"（802.11v），不能"强制"（除非踢掉客户端）
- **不同厂商的客户端漫游行为差异巨大**（苹果、Windows、Android 各不相同）
- **"粘滞客户端"（Sticky Client）问题**：某些客户端信号很弱了还赖着不走

**网络侧的优化手段**：

| 手段 | 说明 |
|:--|:--|
| **合理的 AP 覆盖重叠** | 相邻 AP 覆盖重叠 **15-20%**，太少会有盲区，太多会导致粘滞 |
| **降低 AP 发射功率** | 缩小蜂窝，逼客户端更早切换 |
| **禁用低速率** | 禁掉 1/2/5.5/11 Mbps，弱信号客户端连不上就会切换 |
| **802.11v BSS Transition** | 主动建议客户端漫游 |
| **RSSI 低阈值踢除** | 信号低于阈值直接断开（激进，慎用） |

```
! WLC 上配置
Wireless > 802.11a/n/ac > RRM > TPC > 功率级别
WLANs > <WLAN> > Advanced > Client Exclusion
Wireless > 802.11a/n/ac > Network > Data Rates（禁用低速率）
```

## ⑤ RRM（无线资源管理）

**WLC 自动优化射频参数，无需人工调整每个 AP。**

| 组件 | 全称 | 作用 |
|:--|:--|:--|
| **DCA** | Dynamic Channel Assignment | **自动分配信道**，避开干扰 |
| **TPC** | Transmit Power Control | **自动调整发射功率**，控制蜂窝大小 |
| **CHD** | Coverage Hole Detection | 检测覆盖盲区，自动提高附近 AP 功率 |
| **FRA** | Flexible Radio Assignment | 双频 AP 自动决定射频角色（2.4G/5G/监控） |

```
! 查看 RRM 状态
(WLC) > show advanced 802.11a summary
(WLC) > show advanced 802.11a channel
(WLC) > show advanced 802.11a txpower
(WLC) > show ap auto-rf 802.11a <AP名称>
```

**RRM 的局限（实战重点）**：

> **RRM 是"自动"的，但不总是"最优"的。**
>
> 我处理过的真实案例：某楼层所有 AP 的 5GHz 被硬件锁定在 149-165 这一小段信道池里，还都用了 80MHz 带宽。RRM 在这个受限的池子里怎么分配都会冲突——**6 个 AP 全在互相干扰**。
>
> **RRM 只能在"可用信道池"里优化，它无法解决"池子本身太小"的问题。**
>
> **解法**：手工把带宽降到 20MHz（信道数翻 4 倍），或者解除信道池限制。改完之后即使不用 RRM，手工分配也能得到干净的结果。

**什么时候该手工干预**：
- 高密度部署，需要精确控制蜂窝大小
- 已知的固定干扰源（雷达、微波炉）
- RRM 反复调整导致不稳定
- **信道池被限制**（某些 AP 型号或监管域限制）

```
! 手工指定信道和功率
Wireless > Access Points > <AP> > Radios > 802.11a/n/ac
  > RF Channel Assignment: Custom → 选择信道
  > Tx Power Level Assignment: Custom → 选择功率级别 (1=最高, 8=最低)
```

## ⑥ 配套实验与排障

### 实验：AP 注册排障（最常见的无线问题）

**场景**：新装的 AP 一直不上线。

**Step 1：AP 拿到 IP 了吗？**
```cisco
AP# show capwap ip config
AP IP address: 192.168.90.25
AP IP netmask: 255.255.255.0
AP IP default gateway: 192.168.90.1
```
没 IP → 查 DHCP（VLAN 是否正确、地址池是否耗尽、PoE 是否供电）。

**Step 2：AP 知道 WLC 的地址吗？**
```cisco
AP# show capwap client rcb
AP Mode & Type            : Local        Remote AP
Discovery Timer           : 10
Num of Discovery Request  : 5
Discovered Controllers    : (none)       ← ★ 没发现任何 WLC
```

**Step 3：检查 DHCP Option 43**
```cisco
R1# show ip dhcp pool AP-POOL
R1# show run | section ip dhcp pool AP-POOL
 option 43 hex f104.0a00.0032        ← 确认存在且格式正确
```

**手工指定测试**（快速验证是不是发现机制的问题）：
```cisco
AP# capwap ap controller ip address 10.0.0.50
AP# reload
```
手工指定后能上线 → **确认是 Option 43 / DNS 的问题**。

**Step 4：网络可达性**
```cisco
AP# ping 10.0.0.50
! 不通 → 查路由、VLAN、ACL
```

**Step 5：UDP 5246/5247 通吗？**
```cisco
R1# show access-lists | include 5246|5247
! 确认 ACL 放行

! 必须放行的
permit udp any host <WLC-IP> eq 5246
permit udp any host <WLC-IP> eq 5247
permit udp host <WLC-IP> any eq 5246
permit udp host <WLC-IP> any eq 5247
```

**Step 6：WLC 侧看到 Join 尝试了吗？**
```cisco
(WLC) > show ap join stats summary all
(WLC) > show ap join stats detailed <AP的MAC>

Last Join Error ......................... AP got or has rebooted
Last Join Failure Type .................. Configuration
```

**Step 7：时间同步（★ 容易忽略）**
```cisco
(WLC) > show time
AP# show clock
```
**CAPWAP 用 DTLS，DTLS 依赖证书，证书验证依赖时间。** 时间偏差过大 → DTLS 握手失败 → AP 永远注册不上。

**这个问题的日志很有迷惑性**，通常只显示"DTLS handshake failed"，不会告诉你是时间问题。

**Step 8：AP 授权和国家码**
```cisco
(WLC) > show ap summary
(WLC) > show country
! AP 的监管域必须与 WLC 的国家码匹配
! 从国外买的 AP（-A 域）在中国（-C 域）的 WLC 上可能注册不上
```

### AP 注册失败原因排行榜

| 排名 | 原因 | 排查 |
|:--|:--|:--|
| **1** | **DHCP Option 43 没配或格式错** | `show run \| inc option 43` |
| **2** | **UDP 5246/5247 被 ACL/防火墙拦** | `show access-lists` |
| **3** | AP 和 WLC 之间路由不通 | `ping` |
| **4** | **时间不同步导致 DTLS 失败** | `show clock` / `show time` |

| 7 | WLC 的 AP 授权列表限制 | `show auth-list` |
| 8 | WLC 达到 AP 容量上限 | `show ap summary` |
| 9 | MTU 不足（跨 WAN 场景） | `ping <WLC> size 1500 df-bit` |

## ⑧ 考点提示 + 自测题

### 考点

- **CAPWAP 两条隧道：UDP 5246（控制，DTLS）/ 5247（数据）**
- **AP 发现 WLC 的顺序**，尤其 **DHCP Option 43**

- **L2 漫游 vs L3 漫游**，**Anchor / Foreign** 的角色

### 自测题

**1.** CAPWAP 用哪两个端口？为什么控制隧道加密而数据隧道默认不加密？

<details><summary>答案</summary>

| 隧道 | 端口 | 内容 | 默认加密 |
|:--|:--|:--|:--|
| **控制隧道** | **UDP 5246** | AP 注册、配置下发、固件升级、统计上报 | ✅ **DTLS** |
| **数据隧道** | **UDP 5247** | 用户业务数据 | ❌ 不加密（可选开启） |

**为什么这样设计**：

**① 流量量级差异巨大**
- 控制流量：几十 kbps（周期性的心跳、统计）
- 数据流量：几百 Mbps 甚至 Gbps
- 加密开销与流量成正比，加密控制隧道几乎不影响性能，加密数据隧道会**显著降低 AP 和 WLC 的吞吐**（部分型号下降 50% 以上）

**② 敏感度差异**
- 控制隧道传的是**配置、认证凭据、管理消息**，泄露风险高
- 数据隧道传的是用户业务数据，而**这些数据在无线侧已经被 WPA2/WPA3 加密了**，有线侧再加一层的边际收益有限

**③ 有线网络通常被认为是"半可信"的**
AP 到 WLC 之间是企业自己的有线网，物理安全可控。

**什么时候需要开启数据加密**：
```
WLC > Wireless > Access Points > <AP> > Advanced > Data Encryption ☑
```
- AP 和 WLC 之间跨越**不可信网络**（比如通过互联网连接远程分支）
- 有严格的合规要求（金融、政府）

**⚠️ 开启前必须评估性能影响**——某些 AP 型号开启后吞吐会腰斩。

**MTU 提醒**：CAPWAP 增加 **50-60 字节**开销。跨 WAN 或隧道时可能需要：
```cisco
R1(config-if)# ip mtu 1400
R1(config-if)# ip tcp adjust-mss 1360
```
否则会出现"AP 能注册（控制报文小），但客户端上网异常（数据报文大）"的诡异症状。
</details>

**2.** AP 发现 WLC 的顺序是什么？DHCP Option 43 怎么配？

<details><summary>答案</summary>

**发现顺序（★ 必考）**：
```
① AP 本地缓存的 WLC 列表（之前成功连过的，存在闪存）
        ↓ 没有
② ★ DHCP Option 43 ★
        ↓ 没有
③ DNS 解析 CISCO-CAPWAP-CONTROLLER.<本地域名>
        ↓ 没有
④ 二层广播（只在同网段有效）
        ↓ 全部失败
   AP 重启，重新尝试整个流程
```

**DHCP Option 43 配置**：

```cisco
! Cisco IOS DHCP 服务器
R1(config)# ip dhcp pool AP-POOL
R1(dhcp-config)#  network 192.168.90.0 255.255.255.0
R1(dhcp-config)#  default-router 192.168.90.1
R1(dhcp-config)#  option 43 hex f104.0a00.0032
```

**编码规则**：
```
f1 <长度> <WLC IP 的十六进制>

类型码：f1（固定）
长度：  WLC 个数 × 4，转成十六进制
IP：    每个字节转成两位十六进制

例：单个 WLC = 10.0.0.50
   10 → 0a
   0  → 00
   0  → 00
   50 → 32
   长度 = 4 个字节 = 04
   → f1 04 0a 00 00 32
   → 写作 f104.0a00.0032

例：两个 WLC = 10.0.0.50 和 10.0.0.51
   长度 = 8 = 08
   → f1 08 0a000032 0a000033
   → 写作 f108.0a00.0032.0a00.0033
```

**Windows DHCP 服务器**：
```
作用域选项 → 043 供应商特定信息 → 二进制值输入：
f1 04 0a 00 00 32
```

**Linux ISC DHCP**：
```
option vendor-encapsulated-options f1:04:0a:00:00:32;
```

**验证配置**：
```cisco
R1# show ip dhcp pool AP-POOL
R1# show run | section ip dhcp pool AP-POOL

! 在 AP 上验证是否收到
AP# show capwap client rcb
Discovered Controllers: 10.0.0.50           ← 收到了 ✓
```

**排障时的快捷做法**：
```cisco
! 手工指定 WLC，绕过发现机制
AP# capwap ap controller ip address 10.0.0.50
AP# reload
```
如果手工指定后能上线，**就确认是 Option 43 或 DNS 的问题**，而不是网络连通性问题。这个二分法能快速定位。

**DNS 方式（备选）**：
```
在 DNS 服务器上添加 A 记录：
CISCO-CAPWAP-CONTROLLER.corp.example.com  →  10.0.0.50

AP 需要通过 DHCP Option 15 拿到域名 corp.example.com
```

**注意**：Option 43 的编码格式**因 WLC 型号和 AP 型号而异**：
- **Cisco AireOS WLC**：用 `f1` 类型码（上面的格式）
- **Cisco Catalyst 9800 (IOS-XE)**：同样支持 `f1`
- **某些老型号**：可能需要不同的编码

配置前查阅对应型号的文档，或者**直接用手工指定 + DNS 方式**规避编码问题。
</details>

**3.** L2 漫游和 L3 漫游有什么区别？Anchor 和 Foreign 分别是什么角色？

<details><summary>答案</summary>

| | **L2 漫游** | **L3 漫游** |
|:--|:--|:--|
| 场景 | 漫游前后在**同一个 VLAN/子网** | 漫游前后**跨 VLAN/子网** |
| 客户端 IP | 不变 | **不变（靠隧道实现）** |
| 机制 | WLC 之间转移客户端数据库 | **Anchor / Foreign 隧道** |
| 流量路径 | 直接从新 WLC 出网 | **绕回 Anchor WLC 出网** |
| 复杂度 | 低 | 高 |
| 性能 | 好 | **有绕路开销** |

**L3 漫游的角色**：

```
   ┌─────────────────┐    EoIP / CAPWAP 隧道    ┌─────────────────┐
   │  WLC-A          │══════════════════════════│  WLC-B          │
   │  ★ Anchor ★     │                          │  ★ Foreign ★    │
   │  "客户端的户口"   │                          │  "客户端现在在这" │
   │  VLAN 10        │                          │  VLAN 20        │
   └────────┬────────┘                          └────────┬────────┘
            │                                            │
         [AP-1] 3楼                                   [AP-2] 8楼
                                                         │
                                                    [客户端]
                                                 IP 依然是 VLAN 10 的
```

| 角色 | 定义 | 职责 |
|:--|:--|:--|
| **Anchor WLC**（锚点） | 客户端**最初关联**的 WLC | **保存客户端的 IP、VLAN、会话状态**；所有流量最终从这里进出有线网 |
| **Foreign WLC**（外部） | 客户端**当前所在**的 WLC | 接收客户端的无线流量，**通过隧道转发给 Anchor** |

**流量路径**：
```
客户端 → AP-2 → Foreign WLC → ★隧道★ → Anchor WLC → 有线网 → 互联网
```

**关键价值**：**客户端的 IP 地址完全不变**，所有 TCP 连接、VPN 会话、正在进行的下载都不会中断。

**代价（重要）**：

**流量绕路。** 客户端明明在 8 楼，但流量必须先跑回 3 楼的 Anchor WLC 才能出网。这带来：
- 额外延迟
- WLC 之间的链路带宽消耗
- Anchor WLC 成为潜在瓶颈
- 排障复杂度上升

**设计建议（★ 最重要的一条）**：

> **能避免 L3 漫游就避免。最好的设计是让整个园区的无线客户端使用同一个大的 VLAN/子网。**

比如：
```
   整栋楼的无线用户都在 VLAN 200 / 10.1.200.0/22 （1022 个地址）
        ↓
   无论走到哪一层，都是同一个子网
        ↓
   ★ 所有漫游都是 L2 漫游，简单高效 ★
```

**这也是"无线用大二层"这个设计惯例的由来**——有线网络倾向于用小的广播域（减少广播），但无线为了漫游体验，反而需要大的二层域。

**Mobility Group 配置**：
```
(WLC) > config mobility group domain CAMPUS-A
(WLC) > config mobility group member add <对端WLC的MAC> <对端WLC的IP> CAMPUS-A
(WLC) > show mobility summary

Mobility Architecture ........................... Mobility Controller
Mobility Protocol Port .......................... 16666
Default Mobility Domain ......................... CAMPUS-A
Multicast Mode .................................. Disabled
Mobility Domain ID for 802.11r .................. 0xa1b2

Controllers configured in the Mobility Group
MAC Address        IP Address     Group Name      Status
aa:bb:cc:dd:ee:ff  10.0.0.50      CAMPUS-A        Up          ← 必须是 Up
11:22:33:44:55:66  10.0.0.51      CAMPUS-A        Up
```

**⚠️ 移动组的配置必须在所有 WLC 上一致**：组名、成员列表都要相同。不一致 → 漫游失败，客户端断线重连。

**验证客户端的漫游状态**：
```cisco
(WLC) > show client detail <MAC>
Mobility State .................. Foreign            ← 说明它是从别处漫游过来的
Mobility Anchor IP Address ...... 10.0.0.50          ← 它的 Anchor 在这
```
</details>

**4.** 802.11r、802.11k、802.11v 分别是什么？为什么语音场景需要它们？

<details><summary>答案</summary>

| 标准 | 名称 | 作用 | 类比 |
|:--|:--|:--|:--|
| **802.11k** | Neighbor Report | AP 告诉客户端**"你旁边有哪些 AP，各自在什么信道"** | 给你一张**地图** |
| **802.11v** | BSS Transition Management | AP **主动建议**客户端"该切到 AP-5 了" | 给你**导航建议** |
| **802.11r** | Fast BSS Transition (FT) | **预先协商密钥**，漫游时跳过完整认证 | 提前办好**通行证** |

**为什么语音必须要**：

**标准漫游的流程和耗时**：
```
① 客户端扫描（不知道该扫哪些信道 → 全信道扫描）    100-300ms
② 认证 + 关联                                      10-30ms
③ ★ 完整的 802.1X/EAP 认证 ★                      200-500ms
   （要往返 RADIUS 服务器多次）
④ 4 次握手协商密钥                                 20-50ms
─────────────────────────────────────────────────
   总计：★ 300-800ms ★
```

**语音的要求：切换中断 < 50ms**（超过就能听出"咔"的一声，超过 150ms 会明显卡顿甚至掉话）。

**三者如何解决**：

**802.11k 解决"扫描慢"**：
```
   没有 11k：客户端要扫描所有信道找 AP（2.4G 13 个 + 5G 20+ 个）
             每个信道停留 20-100ms → 几百毫秒
   
   有 11k：  AP 提前告诉客户端"你附近有 AP-3(ch44)、AP-5(ch149)"
             客户端只扫这两个信道 → 几十毫秒 ✓
```

**802.11v 解决"切得太晚"**：
```
   没有 11v：客户端等到信号很差了（-75dBm）才切换，
             这期间通话质量已经很糟了
   
   有 11v：  AP 主动发 BSS Transition Request：
             "AP-5 信号更好，建议你切过去"
             客户端提前切换 ✓
             
   还能用于负载均衡：把客户端从繁忙的 AP 引导到空闲的 AP
```

**802.11r 解决"认证慢"（最关键）**：
```
   没有 11r：每次漫游都要完整的 EAP 认证（往返 RADIUS 多次）
             200-500ms
   
   有 11r：  ★ 在漫游之前，密钥就已经预先分发到目标 AP ★
             漫游时只需要一个 4 次握手 → 50ms 以内 ✓
             
   两种模式：
   - Over-the-Air：客户端直接和目标 AP 协商
   - Over-the-DS：通过当前 AP 中转协商（更快，但需要 AP 支持）
```

**三者配合的效果**：
```
   11k 让客户端知道往哪扫（省 200ms）
        ↓
   11v 让客户端在合适的时机切（避免信号已经很差）
        ↓
   11r 让切换时跳过完整认证（省 300ms）
        ↓
   ★ 总切换时间 < 50ms，语音无感知 ★
```

**配置（WLC）**：
```
WLANs > <WLAN> > Security > Layer 2 > Fast Transition: Enabled
                                    > Over the DS: ☑
WLANs > <WLAN> > Advanced > 802.11k > Neighbor List: ☑
                          > Assisted Roaming Prediction: ☑
WLANs > <WLAN> > Advanced > 802.11v > BSS Transition: ☑
                          > Disassociation Imminent: ☑
```

**⚠️ 802.11r 的兼容性坑**：

**部分老设备（尤其是老 Android、某些 IoT 设备、老打印机）开启 802.11r 后完全无法连接。**

**解决方案**：

| 方案 | 说明 |
|:--|:--|
| **Adaptive 802.11r**（推荐） | Cisco 的方案：对支持的客户端启用 FT，对不支持的自动降级 |
| **双 SSID** | 一个 SSID 开 FT（给语音手机/对讲机），一个不开（给普通设备和 IoT） |
| **逐步启用** | 先在测试 SSID 上验证，确认所有设备类型兼容后再全面推广 |

**部署前的必要测试**：把公司里所有类型的终端（各品牌手机、笔记本、平板、IP 电话、打印机、扫码枪、IoT 设备）都测一遍。

**Cisco 私有的历史方案**（了解即可）：
- **CCKM**（Cisco Centralized Key Management）：Cisco 私有，需要 CCX 兼容客户端
- **PMK Caching / OKC**（Opportunistic Key Caching）：缓存主密钥，比完整认证快，但不如 11r
</details>

**5.** 用户投诉"从 3 楼走到 8 楼，微信语音会断一下"。怎么排查？

<details><summary>答案</summary>

**这是典型的漫游问题。按以下顺序排查：**

**① 确认是不是 L3 漫游（跨子网）**
```cisco
(WLC) > show client detail <客户端MAC>
IP Address ...................... 192.168.10.55        ← 在 3 楼时
Mobility State .................. Local

! 用户走到 8 楼后再查
IP Address ...................... 192.168.20.88        ← ★ IP 变了！
```

**如果 IP 变了**，说明发生了子网切换但没有配置 L3 漫游，所有连接必然中断。

**修复方案（按优先级）**：
```
方案 A（★ 最佳）：把整个园区的无线用户放在同一个大子网
   VLAN 200 / 10.1.200.0/22（1022 个地址）
   → 所有漫游变成 L2 漫游，无缝

方案 B：配置 L3 漫游（Anchor/Foreign）
   → 能用，但流量绕路，性能不如方案 A
```

**② 确认是否启用了快速漫游（802.11r）**
```
WLC > WLANs > <WLAN> > Security > Layer 2 > Fast Transition
```
没启用 → 每次漫游都要完整 EAP 认证，**300-500ms 中断**，语音必然卡。

```
启用：Fast Transition: Enabled (或 Adaptive)
     Over the DS: ☑
同时启用 802.11k 和 802.11v
```

**③ 检查 AP 覆盖重叠是否合理**
```cisco
(WLC) > show client detail <MAC>
Radio Signal Strength Indicator . -78 dBm        ← ★ 太弱了！
Signal to Noise Ratio ........... 12 dB          ← ★ 太低！
```

| 指标 | 健康值 | 说明 |
|:--|:--|:--|
| RSSI | **> -67 dBm** | -70 以下体验下降，-75 以下基本不可用 |
| SNR | **> 25 dB** | 低于 20 速率大幅下降 |

**如果客户端在切换点的信号只有 -78dBm**，说明**覆盖有盲区**——两个 AP 之间的重叠不够，客户端在中间地带信号都很差。

**理想的覆盖重叠：15-20%**（相邻 AP 的 -67dBm 边界有 15-20% 的重叠区）。

**④ 检查是否是"粘滞客户端"（Sticky Client）**
```cisco
(WLC) > show client detail <MAC>
AP Name ......................... AP-3F-05         ← 人都到 8 楼了，还连着 3 楼的 AP！
Radio Signal Strength Indicator . -82 dBm
```

**粘滞客户端**：某些客户端（尤其是某些 Android 和 IoT 设备）信号已经很差了还赖着不切换。

**因为漫游是客户端决定的**，网络侧只能引导：

| 手段 | 配置 |
|:--|:--|
| **启用 802.11v** | 主动建议客户端漫游 |
| **降低 AP 发射功率** | 缩小蜂窝，逼客户端更早切换 |
| **禁用低速率** | 禁掉 1/2/5.5/11 Mbps，弱信号连不上就得切 |
| **RSSI 低阈值踢除** | 信号低于 -80dBm 直接断开（激进，慎用） |

```
WLC > Wireless > 802.11a/n/ac > Network > Data Rates
      1 Mbps: Disabled
      2 Mbps: Disabled
      5.5 Mbps: Disabled
      11 Mbps: Disabled
      12 Mbps: Mandatory              ← 最低强制速率
```

**⑤ 检查 DFS 信道**
```cisco
(WLC) > show ap auto-rf 802.11a AP-8F-05
Channel .......................... 116            ← ★ DFS 信道
```

**DFS 信道（52-144）检测到雷达会立即切换并静默 30 分钟**，表现为"突然全部掉线"。

**如果在机场、港口、气象站附近**，避开 DFS 信道：
```
只用 UNII-1 (36,40,44,48) 和 UNII-3 (149,153,157,161,165)
```

**⑥ 检查信道利用率（干扰）**
```cisco
(WLC) > show ap auto-rf 802.11a AP-3F-05
Channel Utilization .............. 78%           ← ★ 严重拥塞
```
CU > 50% 就会明显影响体验。参见 [Stage 1 第 8 章](../01-CCNA补齐篇/08-无线与安全基础.md) 的无线优化清单。

**⑦ 抓取漫游过程**
```cisco
(WLC) > debug client <客户端MAC>
! 让用户走一遍，观察漫游过程的每一步耗时

! 或用 AP 的 Sniffer 模式抓包
Wireless > Access Points > <AP> > AP Mode: Sniffer
```

**完整的排查清单**：
```
□ ① IP 是否变化（L3 漫游）→ 最好统一子网
□ ② 802.11r/k/v 是否启用
□ ③ 切换点的 RSSI/SNR 是否达标（覆盖重叠 15-20%）
□ ④ 是否粘滞客户端 → 降功率 + 禁低速率 + 11v
□ ⑤ 是否 DFS 信道 → 换非 DFS
□ ⑥ 信道利用率是否过高 → 降带宽 + 重新规划信道
□ ⑦ Mobility Group 配置是否一致（跨 WLC 场景）
□ ⑧ 客户端驱动/固件是否最新
```

**最常见的根因排序**：
1. **没启用 802.11r**（最常见）
2. **跨子网但没配 L3 漫游**
3. **覆盖重叠不足**（切换点信号太差）
4. 粘滞客户端

> **实战提示**：先问用户"是所有设备都这样，还是只有某个牌子的手机？"——如果只有某些设备有问题，大概率是客户端侧的漫游行为差异或 802.11r 兼容性问题；如果所有设备都这样，那是网络侧配置或覆盖的问题。
</details>
