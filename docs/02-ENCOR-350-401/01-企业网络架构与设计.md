# 01 · 企业网络架构与设计

## ① 这章解决什么问题

老板说："我们要搬新办公楼，8 层，1500 人，你来设计网络。"

你会怎么做？买多少台交换机？怎么连？核心用几台？网关放哪儿？

这一章讲的就是**在动手配置之前，怎么把架构想清楚**。架构错了，后面配得再对也是在错误的地基上盖楼——扩容困难、故障域巨大、排障噩梦。

而且这不只是"设计新网"才用得上。**理解架构模型，你才能看懂一张陌生网络的拓扑图，知道哪台是核心、哪台是汇聚、故障域边界在哪。**

## ② 原理讲透

### 2.1 三层架构（Three-Tier / Hierarchical Model）

Cisco 的经典企业网模型：

```
                    ┌─────────────┐  ┌─────────────┐
    核心层 Core     │  Core-SW1   │══│  Core-SW2   │   高速转发，不做策略
                    └──┬───┬──────┘  └──────┬───┬──┘
                       │   │  ╲          ╱  │   │
                       │   │   ╲        ╱   │   │
                       │   │    ╲      ╱    │   │
                    ┌──┴───┴──┐  ╲    ╱  ┌──┴───┴──┐
   汇聚层 Distribution │ Dist-SW1 │══╳══│ Dist-SW2 │  路由边界、策略、聚合
                    └──┬────┬──┘  ╱  ╲  └──┬───┬──┘
                       │    │    ╱    ╲    │   │
                    ┌──┴────┴──┐        ┌──┴───┴──┐
    接入层 Access    │ Access-SW│  ....  │Access-SW│  终端接入、端口安全
                    └────┬─────┘        └────┬────┘
                         │                   │
                       [PC][Phone]        [PC][AP]
```

**各层职责**：

| 层 | 核心职责 | 该做什么 | **不该**做什么 |
|:--|:--|:--|:--|
| **接入层 Access** | 终端接入 | PoE、VLAN 划分、Port Security、802.1X、PortFast、BPDU Guard | 不做复杂路由和策略 |
| **汇聚层 Distribution** | **策略边界** | **三层网关（SVI）**、FHRP、路由汇总、ACL、QoS 标记、故障域隔离 | 不直接接终端 |
| **核心层 Core** | **高速转发** | 大带宽、低延迟、高冗余、快速收敛 | **不做 ACL、不做 QoS 分类、不接终端**（任何策略都会拖慢转发） |

**核心层的设计原则："什么都不做，只做转发。"**

任何在核心层做的策略处理都会成为整网的瓶颈和故障点。核心层应该是"傻快傻快"的——配置尽可能简单，功能尽可能少，可用性尽可能高。

### 2.2 折叠核心（Collapsed Core / Two-Tier）

中小型网络（< 500 人，1-3 栋楼）用三层架构是浪费。把核心层和汇聚层**合并**：

```
                ┌─────────────┐  ┌─────────────┐
  核心+汇聚      │ Core-Dist-1 │══│ Core-Dist-2 │
                └──┬───┬───┬──┘  └──┬───┬───┬──┘
                   │   │   │  ╲ ╱   │   │   │
                ┌──┴───┴───┴──┐   ┌─┴───┴───┴──┐
   接入层        │  Access-SW  │...│ Access-SW  │
                └──────┬──────┘   └──────┬─────┘
                     [终端]            [终端]
```

**优点**：设备少、成本低、管理简单、延迟低。
**缺点**：扩展性有限（核心设备的端口数决定了规模上限）、故障域较大。

> **实践判断标准**：
> - **单栋楼、< 500 用户** → 折叠核心足够
> - **多栋楼、> 1000 用户、或有多个数据中心** → 上三层架构
> - **强制三层的情况**：接入交换机数量超过核心设备的端口容量

### 2.3 Spine-Leaf（数据中心架构）

**为什么数据中心不用三层架构**：

三层架构是为 **"南北向流量"** 设计的——终端访问服务器、访问互联网，流量方向是"从边缘到中心"。

但现代数据中心的流量主要是 **"东西向"** ——服务器之间互访（微服务调用、分布式存储同步、虚拟机迁移）。在三层架构里，两台服务器互访可能要经过 接入→汇聚→核心→汇聚→接入 五跳，**延迟高且不可预测**。

```
             ┌────────┐  ┌────────┐  ┌────────┐
   Spine     │ Spine1 │  │ Spine2 │  │ Spine3 │
             └─┬─┬─┬──┘  └─┬─┬─┬──┘  └─┬─┬─┬──┘
               │ │ │  ╲╱╲╱ │ │ │  ╲╱╲╱ │ │ │
               │ │ └───────┼─┼─┼───────┼─┼─┤   全互联
               │ └─────────┼─┼─┼───────┼─┼─┤
               └───────────┼─┼─┼───────┼─┼─┤
             ┌─────────┐ ┌─┴─┴─┴───┐ ┌─┴─┴─┴──┐
   Leaf      │  Leaf1  │ │  Leaf2  │ │  Leaf3 │
             └────┬────┘ └────┬────┘ └───┬────┘
                [服务器]     [服务器]    [服务器]
```

**核心特点**：

| 特点 | 说明 |
|:--|:--|
| **每个 Leaf 连接所有 Spine** | 全互联（full mesh） |
| **Spine 之间不互联** | 不需要，也不允许 |
| **Leaf 之间不互联** | 不需要 |
| **任意两台服务器之间恒定 2 跳** | Leaf → Spine → Leaf，**延迟可预测** |
| **横向扩展（Scale-out）** | 加 Leaf 增加接入容量，加 Spine 增加带宽 |
| **全部用三层链路 + ECMP** | 不用 STP，所有链路都在转发 |

**对比表**：

| | 三层架构 | Spine-Leaf |
|:--|:--|:--|
| 优化方向 | **南北向流量** | **东西向流量** |
| 跳数 | 不固定（2–5 跳） | **恒定 2 跳** |
| 延迟 | 不可预测 | **可预测** |
| STP | 需要 | **不需要**（三层 + ECMP） |
| 链路利用率 | STP 阻塞部分链路 | **100% 全部使用** |
| 扩展方式 | 纵向（换更大的核心） | **横向（加设备）** |
| 适用 | 园区网、办公楼 | **数据中心** |

> **考点**：ENCOR 会考"给定场景选架构"。记住关键词映射：
> - "**办公楼 / 园区 / 分支**" → 三层或折叠核心
> - "**数据中心 / 虚拟化 / 微服务 / 东西向流量**" → Spine-Leaf

### 2.4 网关放在哪里？（三种设计模型）

这是园区网设计里最实际的决策。

#### 模型 A：传统的"二层接入 + 汇聚做网关"

```
   Access-SW（纯二层，只有 VLAN）
        │  Trunk（VLAN 10,20,30 跨越）
   Dist-SW（SVI 网关 + HSRP）
```

- **二层域延伸到汇聚层** → 需要 STP，需要 FHRP
- **优点**：VLAN 可以跨接入交换机（同一个部门分散在多个楼层）
- **缺点**：STP 收敛慢、故障域大、链路利用率低（有阻塞口）

#### 模型 B：路由到接入层（Routed Access）★ 现代推荐

```
   Access-SW（三层交换机，SVI 网关就在这里）
        │  三层链路（/30 或 /31）
   Dist-SW（纯路由）
```

- **二层域被限制在单台接入交换机内** → **不需要 STP 跨设备**，不需要 FHRP
- **优点**：收敛极快（靠路由协议，亚秒级）、故障域最小、链路全部利用（ECMP）
- **缺点**：**VLAN 不能跨接入交换机**，每台接入交换机需要独立网段

#### 模型 C：VSS / StackWise / vPC（逻辑合并）

把两台物理设备**虚拟成一台逻辑设备**：

```
   Access-SW
        ║ ╲    ← 一个跨设备的 EtherChannel（MEC）
        ║  ╲
   ┌────╨───╨────┐
   │  逻辑上是一台  │   Dist-SW1 + Dist-SW2 = 一台
   └─────────────┘
```

| 技术 | 平台 | 特点 |
|:--|:--|:--|
| **StackWise** | Catalyst 接入层 | 专用堆叠线缆，最多 8-9 台 |
| **VSS** | Catalyst 6500/4500/9600 | 两台合一，共享控制平面 |
| **StackWise Virtual** | Catalyst 9000 系列 | VSS 的现代版 |
| **vPC** | Nexus | **控制平面独立**，只有数据平面协同（更安全） |

**核心价值**：接入交换机可以做**跨设备的 EtherChannel（MEC）**，于是：
- **不需要 STP 阻塞**（逻辑上没有环）
- **不需要 FHRP**（逻辑上只有一个网关）
- **所有链路 100% 利用**
- **上行故障切换在 EtherChannel 层完成，亚秒级**

> **实践建议**：**中大型园区网的现代最佳实践是"接入层堆叠 + 汇聚层 VSS/vPC + 跨设备 EtherChannel"**。这样既保留了 VLAN 跨设备的灵活性，又消除了 STP 的收敛问题。

### 2.5 冗余设计原则

| 层面 | 冗余手段 |
|:--|:--|
| **设备** | 双核心、双汇聚、堆叠/VSS |
| **链路** | EtherChannel、多上行、ECMP |
| **电源** | 双电源、双市电、UPS |
| **网关** | HSRP / VRRP / GLBP |
| **路径** | 路由协议 ECMP、浮动静态路由 + IP SLA |
| **控制平面** | NSF/SSO、GR（Graceful Restart） |
| **出口** | 双运营商 + BGP 或策略路由 |

**避免的反模式**：

| 反模式 | 问题 |
|:--|:--|
| **单点核心** | 核心挂了全网瘫 |
| **链式串联接入交换机**（A→B→C→D） | 中间断一台，后面全断；STP 收敛慢 |
| **过大的二层域** | 广播风暴影响面大，STP 收敛慢 |
| **核心层做 ACL/NAT/QoS** | 拖慢转发，成为瓶颈 |
| **不做地址规划，随手分配网段** | 无法汇总，路由表膨胀 |
| **所有设备用默认配置** | 根桥选举随机、DTP 开着、STP 慢速 |

### 2.6 地址规划原则（实战最重要）

**好的地址规划能让你后面所有工作都轻松，坏的规划会折磨你好几年。**

**原则 1：按位置/功能分段，保证可汇总**

```
10.0.0.0/8 全网
├── 10.1.0.0/16    深圳总部
│   ├── 10.1.0.0/20    办公楼A
│   │   ├── 10.1.0.0/24    A栋1层办公
│   │   ├── 10.1.1.0/24    A栋2层办公
│   │   └── ...
│   ├── 10.1.16.0/20   办公楼B
│   ├── 10.1.240.0/24  设备互联（P2P 链路）
│   └── 10.1.255.0/24  管理地址（Loopback、带外）
├── 10.2.0.0/16    上海分部
├── 10.3.0.0/16    北京分部
└── 10.99.0.0/16   数据中心
```

**好处**：深圳总部可以一条 `10.1.0.0/16` 汇总通告给其他站点，路由表极其干净。

**原则 2：P2P 互联地址集中在一个连续块**

把所有 `/30` 或 `/31` 的设备互联地址放在一个 `/24` 里（比如 `10.1.240.0/24`）。这样它们能被一条路由汇总，不会污染路由表。

**原则 3：Loopback 地址集中，且与 Router ID 一致**

```
10.1.255.1/32   Core-SW1  (Router ID 10.1.255.1)
10.1.255.2/32   Core-SW2  (Router ID 10.1.255.2)
10.1.255.11/32  Dist-SW1
```
排障时看到 Router ID 就知道是哪台设备。

**原则 4：VLAN ID 和第三个八位组对应**

```
VLAN 10 → 10.1.10.0/24
VLAN 20 → 10.1.20.0/24
VLAN 30 → 10.1.30.0/24
```
一看 IP 就知道在哪个 VLAN，排障效率翻倍。

**原则 5：预留扩展空间**

不要把地址空间用满。每个层级至少预留 50% 给未来。今天的 20 人部门，三年后可能是 200 人。

## ④ 配套实验：为一栋 8 层办公楼做设计

**这是一个纸上作业，但它比任何配置实验都重要。**

### 需求

| 项目 | 说明 |
|:--|:--|
| 规模 | 8 层，每层约 180 人，共 1500 人 |
| 无线 | 每层 6 个 AP，共 48 个 |
| 服务器 | 本地小机房，约 20 台服务器 |
| 出口 | 双运营商（电信 + 联通） |
| 特殊要求 | 财务部（3 层）需要独立隔离；访客网络需要隔离；有 IP 电话 |

### 任务 1：选择架构

<details><summary>参考答案</summary>

**折叠核心（Two-Tier）**，理由：
- 单栋楼、1500 用户，规模中等
- 没有多个园区互联的需求
- 三层架构的核心层在这个规模下是浪费

**具体方案**：
```
   [Core-Dist-1] ══ StackWise Virtual / VSS ══ [Core-Dist-2]
         ║ ╲                                   ╱ ║
         ║  ╲──────────────────────────────╱    ║
    每层的接入交换机通过跨设备 EtherChannel 上联
         ║                                      ║
   [1F-Access-Stack] ... [8F-Access-Stack]
```

**每层部署**：
- 2-3 台 48 口 PoE 交换机，**堆叠成一台逻辑设备**（StackWise）
- 通过 **2×10G 跨设备 EtherChannel** 上联到核心（一条到 Core-1，一条到 Core-2）

**为什么用 VSS + 跨设备 EtherChannel**：
- 不需要 STP 阻塞任何链路 → 带宽 100% 利用
- 不需要 HSRP → 逻辑上只有一个网关
- 上行故障切换在 EtherChannel 层完成，**亚秒级**
- 管理面统一，配置只需做一遍
</details>

### 任务 2：VLAN 与地址规划

<details><summary>参考答案</summary>

**VLAN 规划**（按功能 + 楼层）：

| VLAN | 用途 | 网段 | 说明 |
|:--|:--|:--|:--|
| 10–17 | 各层办公数据（1F–8F） | 10.1.10.0/24 – 10.1.17.0/24 | 每层一个 |
| 100 | 语音 VLAN | 10.1.100.0/23 | 全楼共用（IP 电话数量少） |
| 200 | 无线办公 | 10.1.200.0/22 | 1022 个地址够 48 AP 承载 |
| 210 | 无线访客 | 10.1.210.0/24 | **隔离，只能上网** |
| 300 | 服务器区 | 10.1.30.0/24 | |
| 310 | **财务专用** | 10.1.31.0/24 | **独立 VRF 或严格 ACL** |
| 400 | 网管 | 10.1.40.0/24 | 交换机、AP 管理地址 |
| 900 | AP 管理 | 10.1.90.0/24 | AP 自身的地址 |
| 999 | Native/黑洞 | — | 不承载业务 |

**互联与管理地址**：

| 用途 | 网段 |
|:--|:--|
| 设备互联 P2P | 10.1.240.0/24（可切成 64 个 /30） |
| Loopback | 10.1.255.0/24 |

**为什么这么规划**：
1. **VLAN ID 和第三个八位组对应**（VLAN 10 → 10.1.10.x），一看 IP 就知道在哪
2. **P2P 和 Loopback 集中在高位段**，可以单独汇总或过滤
3. **业务网段连续**（10.1.10.0 – 10.1.17.0），可汇总成 `10.1.8.0/21`
4. **财务独立网段**，方便做严格的 ACL 或 VRF 隔离
5. **访客独立网段**，方便一条 ACL 拦掉所有内网访问
</details>

### 任务 3：财务部隔离方案

<details><summary>参考答案</summary>

**三种方案，由弱到强**：

**方案 A：ACL 隔离（最简单）**
```cisco
Core(config)# ip access-list extended FINANCE-PROTECT
Core(config-ext-nacl)# permit ip 10.1.31.0 0.0.0.255 host 10.1.30.50    ! 财务服务器
Core(config-ext-nacl)# permit ip 10.1.31.0 0.0.0.255 host 10.1.30.53    ! DNS
Core(config-ext-nacl)# deny ip any 10.1.31.0 0.0.0.255 log              ! 别人不能进财务
Core(config-ext-nacl)# permit ip 10.1.31.0 0.0.0.255 any                ! 财务能出去
```
- ✅ 简单，无需额外设备
- ❌ ACL 会随需求增长而膨胀，难维护；容易被绕过（如果有人接错 VLAN）

**方案 B：VRF 隔离（推荐）**
```cisco
Core(config)# vrf definition FINANCE
Core(config-vrf)#  address-family ipv4

Core(config)# interface Vlan310
Core(config-if)# vrf forwarding FINANCE
Core(config-if)# ip address 10.1.31.1 255.255.255.0
```
- ✅ **路由表完全隔离**，物理上就不可能路由过去
- ✅ 需要互访的部分通过**受控的路由泄露**（route-target 或静态路由）
- ❌ 配置稍复杂，需要理解 VRF（见 [第 2 章](02-网络虚拟化-VRF-GRE-IPsec.md)）

**方案 C：物理隔离**
财务部用独立的交换机和链路，物理上不与办公网相连。
- ✅ 最安全
- ❌ 成本高，财务也需要访问互联网和部分共享服务，完全隔离不现实

**推荐方案 B（VRF）+ 防火墙**：
```
   [办公网 VRF: default] ──┐
                          ├──> [防火墙] ──> 受控的互访
   [财务 VRF: FINANCE] ────┘
```
VRF 保证默认不通，所有互访必须经过防火墙，有完整的日志和策略控制。这是"零信任分段"的雏形。
</details>

### 任务 4：识别单点故障

<details><summary>参考答案</summary>

审视你的设计，找出所有单点：

| 潜在单点 | 风险 | 对策 |
|:--|:--|:--|
| **单台核心** | 全楼断网 | ✅ 双核心 VSS |
| **接入交换机单上行** | 该层断网 | ✅ 跨设备 EtherChannel（一条到 Core-1，一条到 Core-2） |
| **单电源** | 设备宕机 | ✅ 双电源模块 + 双路市电 + UPS |
| **单运营商出口** | 断网 | ✅ 双运营商 + BGP/PBR |
| **接入交换机不堆叠** | 单台故障影响半层 | ✅ 堆叠 |
| **VSS 心跳线单条** | 脑裂（Split-Brain） | ✅ **VSL 用至少 2 条链路，且分布在不同板卡** |
| **DHCP 服务器单点** | 新终端拿不到 IP | ✅ 两台 DHCP + 冗余中继 |
| **WLC 单点** | 无线全断 | ✅ WLC 双机（N+1 或 SSO） |
| **管理链路和业务链路共用** | 业务故障时无法远程管理 | ✅ **带外管理网 + Console Server + 4G 卡** |

> **最容易被忽略的是最后一条：带外管理。** 当业务网络出故障时，你恰恰最需要能连上设备——而这时候业务网往往已经不通了。**独立的带外管理网络是专业和业余的分水岭。**
>
> **VSS 脑裂**也值得警惕：如果 VSL（虚拟交换链路）全断，两台设备都认为自己是主，会同时用相同的 IP 和 MAC，造成网络严重混乱。**必须配置 Dual-Active Detection**（通过 Fast Hello 或 ePAgP）。
</details>

## ⑤ 排障思路：接手一张陌生网络

**场景**：你入职新公司，前任没留任何文档。怎么在一天内摸清网络结构？

```
第 1 步：找到核心
   随便登一台交换机 →
   SW# show cdp neighbors detail     ← 看邻居，一层层往上爬
   SW# show spanning-tree root       ← 根桥通常在核心/汇聚
   SW# show ip route                 ← 路由最多的通常是核心
   
第 2 步：画出物理拓扑
   逐台执行 show cdp neighbors，记录每个端口的对端
   （或者用 LLDP，跨厂商更通用）
   
第 3 步：确定三层边界
   在每台设备上执行：
   SW# show ip interface brief | include Vlan     ← 有 SVI 且配了 IP = 三层设备
   SW# show standby brief                         ← 有 HSRP = 网关就在这
   → 找到"网关在哪一层"，这决定了二层域的边界
   
第 4 步：摸清 VLAN 和地址规划
   SW# show vlan brief
   SW# show ip route connected
   SW# show ip interface brief
   → 整理出 VLAN ↔ 网段 ↔ 用途 的对应表
   
第 5 步：确认路由协议
   R# show ip protocols                ← 跑的什么协议、有哪些 network
   R# show ip ospf neighbor
   R# show ip bgp summary
   
第 6 步：找出出口和策略
   R# show ip route 0.0.0.0            ← 默认路由指向哪
   R# show ip nat statistics
   R# show access-lists                ← 有哪些策略
   
第 7 步：识别风险点
   - 有没有单点？
   - STP 根桥是不是在核心？（show spanning-tree root）
   - 有没有设备 CPU/内存告急？
   - 配置有没有备份？
```

**产出物**：一张拓扑图 + 一张 VLAN/网段对照表 + 一份风险清单。

> **这套流程我在实际接手项目时用过多次，非常有效。** 关键是**先用 CDP/LLDP 建立物理拓扑，再用 SVI/HSRP 定位三层边界**——这两步做完，网络的骨架就清楚了。

## ⑥ 考点提示 + 自测题

### 考点

- **三层架构各层职责**，尤其"核心层不做策略"。
- **Spine-Leaf 的特点**和适用场景（东西向流量）。
- **StackWise / VSS / vPC 的价值**（消除 STP 和 FHRP）。
- **Routed Access 模型**的优缺点。
- **地址规划的可汇总性原则**。

### 自测题

**1.** 为什么核心层不应该配置 ACL 和 QoS 分类？

<details><summary>答案</summary>

**因为核心层的唯一职责是"尽可能快地转发"，任何策略处理都会成为整网的瓶颈。**

具体原因：

1. **性能代价**。ACL 匹配、QoS 分类都需要额外的查表和处理。虽然现代设备用 TCAM 做硬件加速，但 TCAM 容量有限，规则复杂时可能**下沉到 CPU 处理（process switching）**，性能下降几个数量级。

2. **故障域放大**。核心层的一条错误 ACL 会影响**全网所有流量**。而同样的错误如果发生在汇聚层，只影响一个楼栋或一个区域。

3. **收敛速度**。核心层要求亚秒级收敛。复杂配置会增加故障时的重收敛时间。

4. **可维护性**。核心配置应该尽可能简单稳定，越少改动越好。策略需求天天变，把它们放在核心意味着要频繁改核心配置——这是运维事故的温床。

**正确的做法**：
- **策略在汇聚层做**（这是"策略边界"的含义）——ACL、QoS 标记、路由汇总、路由过滤
- **核心层只做**：高速三层转发、ECMP 负载均衡、快速收敛
- 核心层的配置理想状态是：接口 IP + 路由协议 + 基本管理，**再无其他**

**类比**：核心层像高速公路——只管快速通行，收费站和检查站都设在入口匝道（汇聚层）。如果在高速公路中间设收费站，整条路都会堵。
</details>

**2.** 数据中心为什么用 Spine-Leaf 而不是三层架构？

<details><summary>答案</summary>

**根本原因：流量模型不同。**

**传统三层架构为"南北向流量"优化**——终端访问服务器、访问互联网，流量从边缘流向中心再流出。

**现代数据中心以"东西向流量"为主**——服务器之间互访：
- 微服务之间的 API 调用
- 分布式存储的数据同步（Ceph、HDFS）
- 虚拟机热迁移（vMotion）
- 大数据计算的 shuffle 阶段
- 容器编排的跨节点通信

**在三层架构里，两台服务器互访的问题**：

```
Server-A → Access-1 → Dist-1 → Core → Dist-2 → Access-2 → Server-B
                   跳数：5 跳，且路径长短取决于服务器的物理位置
```

- **延迟不可预测**：同一机架内 1 跳，跨机架 3 跳，跨汇聚 5 跳
- **核心成为瓶颈**：所有东西向流量都要经过核心
- **STP 浪费带宽**：一半链路被阻塞

**Spine-Leaf 的解法**：

```
Server-A → Leaf-1 → Spine-X → Leaf-2 → Server-B
                跳数：恒定 2 跳（Leaf-Spine-Leaf）
```

| 优势 | 说明 |
|:--|:--|
| **恒定跳数** | 任意两台服务器之间永远是 2 跳，**延迟可预测**（这对分布式系统至关重要） |
| **全部链路可用** | 用三层链路 + ECMP，**不用 STP**，带宽 100% 利用 |
| **横向扩展** | 加 Leaf 增加服务器接入容量；加 Spine 增加东西向带宽。**不需要更换更大的设备** |
| **无阻塞设计** | 通过控制收敛比（oversubscription ratio），可以做到无阻塞 |
| **故障影响小** | 挂一台 Spine，只损失 1/N 的带宽，不中断服务 |

**配套技术**：
- **VXLAN + EVPN**：在三层的 Spine-Leaf 网络上叠加二层网络（因为虚拟机迁移需要二层可达）
- **BGP** 作为底层路由协议（Underlay）
- **ECMP** 实现多路径负载均衡

**ENCOR 考点映射**：
- 关键词 "**数据中心 / 虚拟化 / 东西向 / 可预测延迟 / 横向扩展**" → Spine-Leaf
- 关键词 "**园区 / 办公楼 / 分支 / 南北向**" → 三层或折叠核心
</details>

**3.** VSS / StackWise Virtual 最大的价值是什么？

<details><summary>答案</summary>

**把两台物理设备虚拟成一台逻辑设备，从而消除 STP 阻塞和 FHRP 的需要。**

**没有 VSS 的情况**：
```
        Access-SW
        ╱        ╲
    链路1        链路2
      ╱            ╲
  Dist-1  ══════  Dist-2
   
问题：
- 两条上行形成环路 → STP 必须阻塞一条 → 50% 带宽浪费
- 两个独立的网关 → 需要 HSRP/VRRP → 切换需要 1-3 秒
- 两台设备配置要分别做 → 容易不一致
```

**有 VSS 的情况**：
```
        Access-SW
        ║      ║     ← 一个跨设备的 EtherChannel（MEC）
        ║      ║
   ┌────╨──────╨────┐
   │  Dist-1+Dist-2 │  ← 逻辑上是一台设备
   │   (一个控制平面) │
   └────────────────┘
   
好处：
✅ 逻辑上没有环 → 不需要 STP 阻塞 → 100% 带宽利用
✅ 逻辑上只有一个网关 → 不需要 HSRP
✅ 只有一份配置 → 不会不一致
✅ 上行故障切换在 EtherChannel 层完成 → 亚秒级（比 STP 和 HSRP 都快）
```

**技术家族对比**：

| 技术 | 平台 | 控制平面 | 特点 |
|:--|:--|:--|:--|
| **StackWise** | Catalyst 接入层 | 合并 | 专用堆叠线缆，最多 8-9 台 |
| **VSS** | Catalyst 6500/4500 | **合并** | 两台合一，一个控制平面 |
| **StackWise Virtual** | Catalyst 9000 | 合并 | VSS 的现代版，走以太网链路 |
| **vPC** | Nexus | **独立** | 只有数据平面协同，控制平面各自独立 |
| **IRF** | H3C | 合并 | 国产设备的对应技术 |
| **CSS/iStack** | 华为 | 合并 | 同上 |

**vPC 与 VSS 的关键区别**：
- **VSS 合并控制平面**：一台是 Active，一台是 Standby。**主控故障或软件 bug 会影响整个逻辑设备**
- **vPC 保持控制平面独立**：两台各自跑自己的路由协议和管理面，只在数据转发上协同。**一台升级不影响另一台**，可靠性更高

**最大的风险：脑裂（Split-Brain）**

如果 VSL（虚拟交换链路）全部断开，两台设备都认为对方挂了，都会成为 Active。此时**两台设备使用相同的 IP、MAC、Router ID**，网络会陷入严重混乱。

**必须配置 Dual-Active Detection**：
```cisco
! 方法 1：Fast Hello（推荐，用一条独立的带外链路）
SW(config)# switch virtual domain 1
SW(config-vs-domain)# dual-active detection fast-hello
SW(config)# interface GigabitEthernet1/0/48
SW(config-if)# switch virtual link dual-active fast-hello

! 方法 2：ePAgP（通过接入交换机中转检测）
SW(config-vs-domain)# dual-active detection pagp trust channel-group 10
```

**同时：VSL 链路至少用 2 条，且分布在不同的板卡/ASIC 上**，避免单板故障导致 VSL 全断。
</details>

**4.** "Routed Access"（路由到接入层）模型有什么优缺点？什么场景适用？

<details><summary>答案</summary>

**模型**：接入交换机就是三层设备，SVI 网关配在接入层，接入层到汇聚层用**三层链路**（/30 或 /31）而不是 Trunk。

```
   Access-SW（三层交换机，网关在这里）
        │  三层链路，跑 OSPF/EIGRP
   Dist-SW（纯路由转发）
```

**优点**：

| 优点 | 说明 |
|:--|:--|
| **二层域最小** | 每台接入交换机是一个独立的二层域，**广播风暴影响面极小** |
| **不需要跨设备 STP** | STP 只在单台设备内部有意义，不会有跨设备的收敛问题 |
| **不需要 FHRP** | 网关就在本地，不需要 HSRP/VRRP |
| **收敛极快** | 靠路由协议收敛，配合 BFD 可以做到**亚秒级**，比 STP 快得多 |
| **链路全利用** | 三层 ECMP，所有上行链路同时转发 |
| **故障隔离好** | 一台接入交换机的问题不会扩散 |

**缺点**：

| 缺点 | 说明 |
|:--|:--|
| **VLAN 不能跨接入交换机** | 这是最大的限制。同一个部门如果分散在多台交换机上，必须用不同网段 |
| **地址消耗大** | 每台接入交换机需要独立的网段，还要占用 P2P 互联地址 |
| **接入层必须是三层交换机** | 成本更高 |
| **配置复杂度上升** | 每台接入交换机都要配路由协议 |
| **无线漫游受限** | 客户端跨接入交换机漫游会换网段，需要 L3 漫游支持 |

**适用场景**：
- ✅ 每台接入交换机服务的用户群相对固定（一层楼一个部门）
- ✅ 对收敛速度要求高（金融交易、工业控制）
- ✅ 不需要 VLAN 跨设备延伸
- ✅ 团队有足够的路由协议运维能力

**不适用场景**：
- ❌ 需要 VLAN 大范围延伸（比如某个应用要求所有服务器在同一个二层）
- ❌ 无线密集且需要频繁跨设备漫游
- ❌ 虚拟化环境（VM 迁移通常要求同网段）

**现代替代方案**：

如果既想要 Routed Access 的收敛速度和故障隔离，又想要 VLAN 跨设备的灵活性，答案是 **VXLAN + EVPN**（或 SD-Access）：
- 底层（Underlay）是纯三层网络，收敛快、无 STP
- 上层（Overlay）用 VXLAN 提供跨三层的二层连通性
- 二者兼得

**这就是为什么 SD-Access 会成为现代园区网的方向**——详见 [第 15 章](15-SD-Access与SD-WAN.md)。
</details>

**5.** 你接手一张完全没有文档的网络，第一步应该做什么？

<details><summary>答案</summary>

**第一步：用 CDP/LLDP 建立物理拓扑图。**

```cisco
SW1# show cdp neighbors detail
-------------------------
Device ID: Core-SW1.corp.local
Entry address(es):
  IP address: 10.1.255.1
Platform: cisco WS-C9300-48P,  Capabilities: Switch IGMP
Interface: GigabitEthernet1/0/49,  Port ID (outgoing port): TenGigabitEthernet1/0/1
Holdtime : 145 sec
Version : Cisco IOS XE Software, Version 17.06.04
```

一条命令就给了你：**对端设备名、对端 IP、对端型号、对端端口、IOS 版本**。

逐台执行，把每个端口的对端记下来，物理拓扑就出来了。

> **跨厂商环境用 LLDP**：`show lldp neighbors detail`。CDP 是 Cisco 私有的，遇到 H3C/华为设备就看不到了。
>
> ⚠️ **注意**：有些安全加固的网络会关闭 CDP/LLDP。如果 `show cdp neighbors` 是空的，先确认是没有邻居还是协议被关了：`show cdp` / `show run | include cdp`。

**完整的七步接手流程**：

| 步 | 目的 | 命令 |
|:--|:--|:--|
| 1 | **画物理拓扑** | `show cdp/lldp neighbors detail` |
| 2 | **定位三层边界** | `show ip interface brief \| inc Vlan`、`show standby brief` |
| 3 | **摸清 VLAN/地址** | `show vlan brief`、`show ip route connected` |
| 4 | **确认路由协议** | `show ip protocols`、`show ip ospf neighbor`、`show ip bgp summary` |
| 5 | **找出口和策略** | `show ip route 0.0.0.0`、`show ip nat statistics`、`show access-lists` |
| 6 | **STP 与冗余** | `show spanning-tree root`、`show etherchannel summary`、`show switch` |
| 7 | **健康与风险** | `show processes cpu sorted`、`show logging`、`show environment all` |

**产出三份文档**（这是你交付的第一个价值）：
1. **拓扑图**（物理连接 + 三层边界标注）
2. **VLAN / 网段 / 用途对照表**
3. **风险清单**（单点、无备份、配置隐患、容量告警）

**为什么第 2 步"定位三层边界"最关键**：

知道网关在哪一层，你就知道了：
- 二层域的边界在哪 → STP 的影响范围
- 策略应该配在哪 → ACL/QoS 的位置
- 故障域有多大 → 一个广播风暴会影响多少人
- 这是什么架构 → 三层？折叠核心？Routed Access？

**这一步做完，整张网络的骨架就清楚了。** 剩下的都是往骨架上填肉。

> **额外建议**：接手后第一周就把**配置备份**建起来（哪怕只是个简单的定时脚本 + Git 仓库）。没有配置备份的网络，任何一次误操作都可能是灾难。
</details>
