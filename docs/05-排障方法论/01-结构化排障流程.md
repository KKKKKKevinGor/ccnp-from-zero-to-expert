# 01 · 结构化排障流程

## ① 七步框架

```
   ① 精确描述现象
        ↓
   ② 确定影响范围
        ↓
   ③ 查最近的变更
        ↓
   ④ 分层定位
        ↓
   ⑤ 缩小范围（二分 / 对比 / 替换）
        ↓
   ⑥ ★ 验证假设 ★
        ↓
   ⑦ 修复 → 验证 → 记录
```

---

## ② 第 1 步：精确描述现象

**★ 这是最容易被跳过、也最重要的一步。**

### 常见的模糊描述 vs 精确描述

| ✗ 模糊 | ✅ 精确 |
|:--|:--|
| "网络不通" | "PC-A（192.168.10.10）能 ping 通网关，但 ping 不通 192.168.20.10" |
| "网速慢" | "财务部 12 人，访问总部 ERP（10.1.30.50:8080）页面加载要 30 秒，访问互联网正常" |
| "连不上服务器" | "telnet 10.1.30.50 8080 立即返回 connection refused" |
| "有时候断" | "每天上午 9:15 左右会断 2-3 分钟，其他时间正常" |

### 必问的问题清单

```
□ ① 具体是什么不通/慢？（哪个 IP 到哪个 IP，哪个应用）
□ ② 什么时候开始的？
□ ③ 所有人都这样吗？还是个别人？
□ ④ 有线还是无线？
□ ⑤ 一直这样还是间歇性？有规律吗？
□ ⑥ 访问内网还是外网？两者都试过吗？
□ ⑦ 最近有什么变更？（网络、服务器、应用都问）
□ ⑧ 之前正常吗？什么时候还正常过？
□ ⑨ 有没有报错信息？（截图）
□ ⑩ 你做过什么尝试？
```

**★ 第 ⑩ 问很重要**：用户可能已经"顺手"改了什么（重启路由器、改了 IP、关了防火墙），这些信息会影响你的判断。

### 描述的三要素

```
   ★ 谁 → 谁 ★     ：源和目的（精确到 IP 和端口）
   ★ 什么现象 ★     ：不通 / 慢 / 报错 / 间歇
   ★ 什么范围 ★     ：一个人 / 一个部门 / 全公司
```

**一个好的问题描述**：
```
   "财务部 VLAN10（192.168.10.0/24）的 12 台电脑，
    从今天上午 9:00 开始，
    访问总部 ERP 系统（10.1.30.50 的 8080 端口）时页面加载 30 秒以上，
    但访问互联网（8.8.8.8）和本地文件服务器（192.168.10.100）都正常。
    销售部 VLAN20 访问同一个 ERP 系统没有问题。
    没有报错，就是慢。
    今天早上运维在核心交换机上做过配置变更。"
```

**★ 看到这个描述，有经验的人已经能猜到方向了**：
- 范围：只影响 VLAN10 → VLAN10 特有的配置
- 特征：只影响一个目标 → 不是全局路由问题
- 时间：今天早上有变更 → 优先查变更
- 现象：慢而不是不通 → QoS？次优路径？MTU？

## ③ 第 2 步：确定影响范围

**★ 范围决定了问题在哪一层。**

| 影响范围 | 最可能的层 | 优先检查 |
|:--|:--|:--|
| **一台设备** | 终端 / 端口 | 网线、端口配置、终端设置、该用户的策略 |
| **一个 VLAN / 网段** | L2 / 网关 | VLAN 配置、Trunk、SVI、该网段的 ACL/DHCP |
| **一栋楼 / 一层楼** | 汇聚层 / 上联链路 | 汇聚交换机、上联链路、该区域的路由 |
| **全公司** | 核心 / 出口 / 公共服务 | 核心设备、出口链路、DNS、DHCP、NTP |
| **访问某个特定目标** | 路由 / 该目标本身 | 到该目标的路由、目标服务器、中间 ACL |
| **某类应用** | L4 / L7 | 端口、防火墙策略、应用本身 |

### 快速判断范围的方法

```cisco
! ① 同 VLAN 的其他机器呢？
PC-B> ping <同样的目标>
! 通 → 问题在 PC-A 或它的端口
! 不通 → 范围扩大到整个 VLAN

! ② 其他 VLAN 呢？
PC-C(VLAN20)> ping <同样的目标>
! 通 → 问题在 VLAN10 特有的配置
! 不通 → 范围扩大

! ③ 从网关本身测？
SW1# ping <目标> source Vlan10
! 通 → 问题在 PC 到网关这一段（L2）
! 不通 → 问题在网关往上（L3）

! ④ 从核心测？
R3# ping <目标> source Loopback0
! 逐级往上，找到"从哪一跳开始不通"
```

**★ 这个方法本质上就是二分法**，见第 5 步。

## ④ 第 3 步：查最近的变更

> **★ 80% 的故障是变更引起的。**

```cisco
! ── 配置变更历史（★ 最有用）──
R1# ★ show archive log config all ★
 idx   sess           user@line      Logged command
    1     1        admin@vty0        | interface GigabitEthernet0/1
    2     1        admin@vty0        |  shutdown
    3     2        john@vty1         | ip access-list extended WEB-ACL
    4     2        john@vty1         |  no permit tcp any any eq 8080
                                        ↑ ★ 谁、什么时候、改了什么，一目了然 ★

! 需要先配置
R1(config)# archive
R1(config-archive)#  log config
R1(config-archive-log-cfg)#   logging enable
R1(config-archive-log-cfg)#   logging size 500
R1(config-archive-log-cfg)#   hidekeys
R1(config-archive-log-cfg)#   notify syslog

! ── 系统日志里的配置变更 ──
R1# show logging | include ★ CONFIG_I ★
%SYS-5-CONFIG_I: Configured from console by admin on vty0 (10.1.99.50)

! ── 接口状态变化 ──
R1# show logging | include ★ LINK|LINEPROTO ★

! ── 路由协议变化 ──
R1# show logging | include ★ OSPF|BGP|DUAL|HSRP ★

! ── 运行时间（判断是否重启过）──
R1# show version | include uptime
Router uptime is ★ 25 minutes ★                  ← ★ 刚重启过！
```

### 同时要问的

```
□ 网络设备今天改过什么？
□ ★ 服务器/应用今天改过什么？★（很多"网络问题"其实是应用变更）
□ 防火墙策略改过吗？
□ 有没有新上线的设备？
□ 有没有做过升级/补丁？
□ 有没有临时的测试/演练？
```

**★ 不要只问网络团队。** 很多"网络故障"的根因在服务器、应用、安全设备上。

## ⑤ 第 4 步：分层定位

**详见 [02 分层定位法](02-分层定位法.md)。这里给出速查框架**：

```
   ┌──────────────────────────────────────────────┐
   │ L1 物理层                                     │
   │  show interfaces status                      │
   │  show interfaces X | include error|drop|rate │
   │  → down/down? CRC? late collision? drops?    │
   └────────────────┬─────────────────────────────┘
                    │ 物理 OK
   ┌────────────────▼─────────────────────────────┐
   │ L2 链路层                                     │
   │  show mac address-table                      │
   │  ★ show interfaces trunk ★                   │
   │  show spanning-tree [detail | inc occurr]    │
   │  show etherchannel summary                   │
   │  → VLAN 对吗? Trunk 放行了吗? 有环路吗?       │
   └────────────────┬─────────────────────────────┘
                    │ 二层 OK
   ┌────────────────▼─────────────────────────────┐
   │ L3 网络层                                     │
   │  show ip interface brief                     │
   │  ★ show ip route <目标> ★                    │
   │  ★ ping <目标> source <源> ★                 │
   │  ★ ping <目标> size 1500 df-bit ★            │
   │  traceroute <目标> source <源>                │
   │  show standby brief                          │
   │  → 路由有吗? 回程有吗? MTU 够吗?              │
   └────────────────┬─────────────────────────────┘
                    │ 三层 OK
   ┌────────────────▼─────────────────────────────┐
   │ L4 传输层                                     │
   │  ★ telnet <ip> <port> ★                      │
   │  → Open / refused / 超时                      │
   └────────────────┬─────────────────────────────┘
                    │ 四层 OK
   ┌────────────────▼─────────────────────────────┐
   │ L7 应用层                                     │
   │  抓包看协议交互                                │
   │  查应用日志、服务器资源                        │
   └──────────────────────────────────────────────┘
```

### ★ 从哪一层开始查

| 情况 | 从哪开始 |
|:--|:--|
| 完全不通 | **从 L1 往上**（自底向上） |
| ping 通但业务不通 | **从 L4 开始**（跳过 L1-L3） |
| 有明确的报错 | **从报错指向的层开始** |
| 完全没头绪 | **从 L3 开始二分**（ping 网关、ping 目标） |

## ⑥ 第 5 步：三种缩小范围的方法

### 方法 A：二分法（★ 最通用）

**在路径的中间点测试，判断问题在前半段还是后半段。**

```
   PC ── SW3 ── SW1 ── R3 ── R1 ── ISP ── Internet
                        ↑
                  ★ 从中间开始测 ★
```

```cisco
! ① 从中间的 R3 测目标
R3# ping 8.8.8.8 source Loopback0
!!!!!                                    ← 通 → ★ 问题在 R3 左边（PC 到 R3）★

! ② 缩小到左半段，继续二分
SW1# ping 8.8.8.8 source Vlan10
.....                                    ← 不通 → ★ 问题在 SW1 到 R3 之间 ★

! ③ 继续
SW1# ping <R3的接口IP>
!!!!!                                    ← 通 → 链路 OK，是路由或 NAT 问题
SW1# show ip route 8.8.8.8
% Network not in table                   ← ★ 找到了：缺默认路由 ★
```

**★ 二分法的效率**：8 跳的路径，二分 3 次就能定位（log₂8 = 3），而逐跳查要 8 次。

### 方法 B：对比法（★ 最有效）

**"能通的" vs "不能通的"，差异就是线索。**

```cisco
! ── 对比两个端口的配置 ──
SW1# show run interface GigabitEthernet1/0/1     ! 正常的
SW1# show run interface GigabitEthernet1/0/5     ! 有问题的
! 逐行对比

! ── 对比两个 VLAN ──
SW1# show run | section interface Vlan10
SW1# show run | section interface Vlan20

! ── 对比两台设备 ──
SW1# show run | section router ospf
SW2# show run | section router ospf

! ── 对比接口状态 ──
SW1# show interfaces Gi1/0/1 | include error|drop
SW1# show interfaces Gi1/0/5 | include error|drop

! ── 对比路由表 ──
R1# show ip route <目标>
R2# show ip route <目标>
```

**★ 对比法的强大之处**：它不需要你知道"正确的配置应该是什么"，只需要找出差异。

**可对比的维度**：

| 维度 | 例子 |
|:--|:--|
| **同类设备之间** | SW1 vs SW2（应该配置一致） |
| **同类端口之间** | 正常的接入口 vs 有问题的接入口 |
| **同类 VLAN 之间** | VLAN10 正常 vs VLAN20 异常 |
| **正常时间 vs 故障时间** | 配置备份对比 |
| **本机 vs 对端** | 两端的 MTU、Hello 时间、认证 |

**★ 配置差异对比的利器**：
```cisco
R1# show archive config differences flash:good.cfg
! 对比当前配置和备份的差异
```

### 方法 C：替换法

**把可疑的组件换掉，看问题是否消失。**

| 替换 | 用途 |
|:--|:--|
| 换网线 | 排除线缆故障 |
| 换端口 | 排除端口硬件故障 |
| 换光模块 | 排除光模块故障 |
| 换终端 | 排除终端问题 |
| **换路径**（shutdown 主链路强制走备份） | 定位是哪条路径的问题 |

**★ 注意**：替换法在生产环境要谨慎，可能引入新问题。**优先用前两种方法。**

## ⑦ 第 6 步：★★ 验证假设 ★★

**这是专业和业余的分水岭。**

```
   ✗ 业余做法：
      "我觉得是 ACL 的问题" → 直接把 ACL 删了 → 通了 → "果然是 ACL"
      ★ 问题：你不知道是哪条规则，也不知道删了会不会引入安全风险 ★
   
   ✅ 专业做法：
      "我怀疑是 ACL 拦了" 
        ↓
      ★ 用命令验证 ★：show access-lists 看命中计数
        ↓
      看到 "deny ip any any log (1245 matches)" → 假设成立
        ↓
      看日志：show logging | include IPACCESSLOG → 找到具体是哪个端口被拦
        ↓
      精确修复：只加一条 permit，不动其他规则
        ↓
      验证：show access-lists 看新规则有命中
```

### 每种假设的验证方法

| 假设 | 验证命令 |
|:--|:--|
| "是 ACL 拦了" | `show access-lists`（看命中计数）+ `show logging \| inc IPACCESSLOG` |
| "是路由问题" | `show ip route <目标>` + **对端** `show ip route <源>` |
| "是 MTU 问题" | `ping <目标> size 1500 df-bit` + 二分法找实际 MTU |
| "是 VLAN 问题" | `show interfaces trunk`（四段输出法） |
| "是环路" | `show mac address-table address X`（反复执行看是否跳变） |
| "是 NAT 问题" | `show ip nat translations \| include <IP>` |
| "是 DHCP 问题" | `show ip dhcp binding` + `show ip int Vlan10 \| inc Helper` |
| "是 HSRP 没切换" | `show standby brief`（看 P 列和 State）+ `show track` |
| "是 BGP 策略过滤" | `received-routes` vs `routes` 对比 |
| "是时间问题" | `show clock` + `show ntp status` |
| "服务器慢不是网络慢" | **抓包看 SYN→SYN/ACK 的时间 vs 请求→响应的时间** |

### ★ 验证假设的标准

```
   ★ 好的验证 ★：
      有一条命令的输出，能【直接】证明或推翻你的假设
      
      例："show access-lists 显示 deny 规则有 1245 次命中"
          → 直接证明 ACL 在拦
   
   ✗ 差的验证：
      "我把它改了，好像好了"
      → 可能是巧合，可能改坏了别的
```

## ⑧ 第 7 步：修复 → 验证 → 记录

### 修复的原则

```
   ① ★ 最小改动 ★
      只改必要的，不要顺手"优化"别的
      
   ② ★ 可回滚 ★
      改之前先保存配置
      R1# copy running-config flash:before-fix.cfg
      
   ③ ★ 生产环境用保险绳 ★
      R1# write memory
      R1# configure terminal revert timer 5
      ... 改配置 ...
      R1# configure confirm
      
   ④ ★ 一次改一个 ★
      同时改多个，出问题不知道是哪个引起的
```

### 验证的标准

```
   ✗ 不够：
      "用户说好了"
   
   ✅ 足够：
      □ 原始故障现象消失（用同样的方法复现测试）
      □ 相关的监控指标正常
      □ 没有引入新问题（其他业务正常）
      □ 有命令输出作为证据
```

```cisco
! 修复后的标准验证
R1# show access-lists WEB-ACL          ! 新规则有命中
R1# show ip route <目标>                ! 路由正常
R1# ping <目标> source <源>             ! 端到端通
R1# show logging | include ERROR        ! 没有新的错误
```

### ★ 记录（最容易被跳过，但价值最高）

**故障记录模板**：

```markdown
# 故障记录 · YYYY-MM-DD

## 现象
（精确描述：谁到谁、什么现象、什么范围、什么时间）

## 影响
- 影响用户数：
- 影响时长：
- 业务影响：

## 排查过程
1. （做了什么，看到什么）
2. 
3. 

## 根因
（一句话说清楚）

## 修复
```cisco
（具体的配置命令）
```

## 验证
（用什么命令验证的，输出是什么）

## ★ 预防措施 ★
- [ ] 短期：
- [ ] 长期：

## 教训
- 下次遇到 XXX 症状，先查 YYY
- 这个坑的根本原因是流程/设计问题吗？
```

**★ 为什么记录最有价值**：
1. **同类故障再发生时，10 分钟变 1 分钟**
2. **交接时新人能快速上手**
3. **积累成团队的知识库**
4. **★ 从"救火"变成"防火"**——记录多了会发现模式，进而改进架构

## ⑨ 反模式（★ 避免这些做法）

| ✗ 反模式 | 为什么错 | ✅ 正确做法 |
|:--|:--|:--|
| **上来就重启** | 破坏现场，问题可能复现 | 先收集信息再重启 |
| **同时改多个地方** | 出问题不知道是哪个引起的 | 一次改一个，验证后再改下一个 |
| **凭猜测改配置** | 可能改坏别的，可能掩盖真问题 | 先验证假设 |
| **只看自己负责的部分** | 很多"网络问题"根因在服务器/应用 | 全链路思维 |
| **不看日志** | 日志里往往有明确的线索 | `show logging` 是第一批命令之一 |
| **不问变更** | 80% 的故障是变更引起的 | 第一个问题就是"改了什么" |
| **不做记录** | 下次还要重来一遍 | 每次都记录 |
| **`ping` 不加 source** | 测出来的结果不代表真实业务路径 | ★ 永远指定 source |
| **"用户说好了"就结束** | 可能只是暂时好了 | 用命令验证 |
| **不做根因分析** | 同类故障会反复发生 | 问"为什么会这样"，而不只是"怎么修好" |

## ⑩ 应急处理的优先级

**当故障影响面很大时（比如全公司断网），顺序不同**：

```
   ★ ① 止血（恢复业务）★
      · 切到备份链路
      · 回滚最近的变更
      · shutdown 可疑端口（环路场景）
      ★ 先让业务恢复，根因可以后面慢慢查 ★
        ↓
   ★ ② 保护现场 ★
      · 在回滚/重启前，先收集关键信息
      · show tech-support（或至少关键的 show 命令）
      · 保存日志
        ↓
   ③ 通报
      · 告知受影响的团队
      · 给出预计恢复时间
        ↓
   ④ 根因分析（RCA）
      · 业务恢复后再做
        ↓
   ⑤ 改进
      · 防止再次发生
```

**★ 关键权衡**：**业务优先于根因分析**。但**回滚前一定要收集现场**，否则根因永远查不出来。

```cisco
! ★ 应急时的"5 秒现场收集" ★
R1# show logging | last 100
R1# show interfaces status
R1# show processes cpu sorted
R1# show ip route summary
! 然后再动手回滚
```

## ⑪ 完整案例演练

**用户报障**："财务部访问 ERP 系统很慢，其他部门正常。"

### 应用七步框架

```
★ ① 精确描述 ★
   问清楚后：
   "财务部 VLAN10（192.168.10.0/24）12 台电脑，
    今天上午 9:00 开始，
    访问 ERP（10.1.30.50:8080）页面加载 30 秒以上，
    访问互联网和本地文件服务器正常，
    销售部 VLAN20 访问同一个 ERP 正常。"

★ ② 确定范围 ★
   · 只影响 VLAN10 → VLAN10 特有的配置
   · 只影响一个目标 → 不是全局问题
   · 其他 VLAN 正常 → 排除 ERP 服务器本身

★ ③ 查变更 ★
   SW1# show archive log config all | include 09:
   → 发现今天早上有人在 SW1 上改过 QoS 策略

★ ④ 分层定位 ★
   L3: PC1# ping 10.1.30.50
       Reply time=8ms                     ✓ 通，延迟正常
   L4: PC1# telnet 10.1.30.50 8080
       （连上了，但很慢）                   ← 能连但慢
   ★ MTU 测试 ★:
       R3# ping 10.1.30.50 size 1500 df-bit source Vlan10
       M.M.M                              ← ★ 大包不通！★

★ ⑤ 缩小范围 ★
   逐跳测 MTU：
   SW1# ping 10.1.30.50 size 1500 df-bit  → 不通
   R3#  ping 10.1.30.50 size 1500 df-bit  → 通
   ★ 问题在 SW1 到 R3 之间 ★

★ ⑥ 验证假设 ★
   假设："SW1 的某个接口 MTU 被改小了"
   SW1# show interfaces Vlan10 | include MTU
     MTU ★ 1300 ★ bytes                   ← ★ 假设成立 ★
   
   对比正常的：
   SW1# show interfaces Vlan20 | include MTU
     MTU 1500 bytes                       ← VLAN20 是正常的
   
   ★ 这也解释了为什么只有 VLAN10 受影响 ★

★ ⑦ 修复 → 验证 → 记录 ★
   SW1# copy running-config flash:before-fix.cfg
   SW1(config)# interface Vlan10
   SW1(config-if)# ip mtu 1500
   
   验证：
   SW1# ping 10.1.30.50 size 1500 df-bit source Vlan10
   !!!!!                                  ✓
   PC1> curl http://10.1.30.50:8080       ✓ 秒开
   
   记录：见故障记录模板
```

**★ 关键的推理链**：
```
   "慢而不是不通" + "只影响某个 VLAN" + "只影响某个应用"
        ↓
   ★ 第一反应就该测 MTU ★（小包通大包不通是最典型的特征）
        ↓
   逐跳测 MTU 定位到设备
        ↓
   对比正常 VLAN，发现配置差异
```
