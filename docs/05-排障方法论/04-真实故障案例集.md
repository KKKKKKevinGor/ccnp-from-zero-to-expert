## 案例 01 · 办公楼 WiFi 慢，加 AP 没用

### 现象
```
   某楼层 60 人，WiFi 信号满格（-55dBm），但网速只有 5-10 Mbps。
   已经加过 AP（从 4 个加到 6 个），★ 加完之后更慢了 ★。
   有线网络正常。
```

### 排查过程

```
① 信号强度正常，排除覆盖问题
   (WLC) > show client detail <MAC>
   Radio Signal Strength Indicator . -55 dBm        ✓ 很好
   Signal to Noise Ratio ........... ★ 11 dB ★      ← ★ 噪声很大！

② ★ 关键指标：信道利用率 ★
   (WLC) > show ap auto-rf 802.11a AP-8F-01
   Channel .......................... ★ 149 ★
   Channel Utilization .............. ★ 82% ★       ← ★ 严重拥塞
   
   (WLC) > show ap auto-rf 802.11a AP-8F-02
   Channel .......................... ★ 153 ★
   Channel Utilization .............. 78%
   
   ... 检查全部 6 个 AP ...

③ ★ 发现规律 ★
   所有 6 个 AP 的信道都在 ★ 149-165 ★ 这个小范围内
   而且都用了 ★ 80MHz 带宽 ★

④ 80MHz 在 5GHz 只能划出这几个不重叠信道：
   36-48 / 52-64 / 100-112 / 116-128 / 149-161
   
   ★ 149-165 这个范围，80MHz 只能划出【1 个】信道 ★
        ↓
   ★★ 6 个 AP 全部挤在同一个 80MHz 信道上互相干扰 ★★
```

### 根因

**AP 型号的硬件限制**，5GHz 射频被锁定在 UNII-3（149-165）这个信道池里，加上用了 80MHz 带宽，**导致所有 AP 只能用同一个信道**。

**加 AP 反而更慢**——因为多了两个干扰源。

### 修复

```
   ① ★ 把信道带宽从 80MHz 降到 20MHz ★
      → 149-165 范围内可划出 ★ 5 个 ★ 20MHz 信道：149/153/157/161/165
   
   ② 手工分配信道（不依赖 RRM 自动分配）
      AP-01: 149    AP-02: 153    AP-03: 157
      AP-04: 161    AP-05: 165    AP-06: 149（离 AP-01 最远）
   
   ③ 降低发射功率（缩小蜂窝，减少重叠）
   
   ④ 禁用低速率（1/2/5.5/11 Mbps）
```

**结果**：单用户实测速率从 5-10 Mbps 提升到 60-80 Mbps。**一分钱设备都没加。**

### ★ 教训

```
   ★ 1. 无线的瓶颈通常是【干扰】，不是【带宽】★
      信号满格 ≠ 网速快
   
   ★ 2. 高密度场景，带宽越窄越好 ★
      80MHz 单 AP 峰值高，但信道少 → AP 之间必然干扰
      20MHz 峰值低，但信道多 → 每个 AP 独占干净信道
      ★ 信道复用能力 > 单 AP 峰值速率 ★
   
   ★ 3. 无线优化往往是"减法" ★
      降功率、降带宽、减 SSID、禁低速率
      加 AP、加功率、加带宽常常让情况更糟
   
   ★ 4. RRM 只能在"可用信道池"里优化 ★
      它解决不了"池子本身太小"的问题
   
   ★ 5. 关键指标是【信道利用率 CU】，不是信号强度 ★
      CU > 50% 就会明显影响体验
```

## 案例 02 · 部署 DHCP Snooping 后全楼断网

### 现象
```
   周末维护窗口，在接入交换机上启用了 DHCP Snooping（安全加固）。
   周一早上：★ 整层楼的人都拿不到 IP ★。
   之前一直正常。
```

### 排查过程

```cisco
! ① 用户的 IP
PC> ipconfig
IPv4 Address. . . . : ★ 169.254.x.x ★            ← APIPA，完全没拿到

! ② 端口和 VLAN 正常
SW3# show interfaces Gi1/0/5 status
Gi1/0/5   PC-01   ★ connected ★   10   a-full  a-1000     ✓

! ③ helper-address 正常
SW1# show ip interface Vlan10 | include Helper
  Helper address is 10.1.30.53                             ✓

! ④ ★ 查日志（关键）★
SW3# show logging | include DHCP
★ %DHCP_SNOOPING-5-DHCP_SNOOPING_UNTRUSTED_PORT: DHCP_SNOOPING drop message
   on untrusted port, message type: ★ DHCPOFFER ★ ★
                                      ↑↑↑↑↑↑↑↑↑
                    ★ DHCP 服务器的 OFFER 被丢弃了 ★

! ⑤ 确认
SW3# show ip dhcp snooping
Switch DHCP snooping is enabled
DHCP snooping is configured on following VLANs: 10,20
Interface                  ★ Trusted ★    Rate limit (pps)
GigabitEthernet1/0/23      ★ no ★        unlimited
GigabitEthernet1/0/24      ★ no ★        unlimited
!                            ↑↑
!            ★★ 上联口是 untrust！★★
```

### 根因

**开了 DHCP Snooping，但忘了把上联口（通往 DHCP 服务器方向）设为 `trust`。**

**untrust 口不允许发 DHCP OFFER/ACK** → 服务器的响应全被丢弃。

### 修复

```cisco
SW3(config)# interface range GigabitEthernet1/0/23-24
SW3(config-if-range)# ★ ip dhcp snooping trust ★
```

### ★ 教训

```
   ★ 1. DHCP Snooping 的 trust 口必须配在"通往合法 DHCP 服务器"的方向 ★
      忘配 = 全网拿不到 IP（这是部署 Snooping 最常见的翻车方式）
   
   ★ 2. 安全加固必须先在测试环境/小范围验证 ★
      不要一次性 vlan 1-4094 全开
   
   ★ 3. 部署顺序很重要 ★
      ① 开 DHCP Snooping，跑一个完整租期周期
      ② 检查绑定表覆盖率
      ③ ★ 为静态 IP 设备加手工绑定 ★
      ④ 再开 DAI
      ⑤ 最后开 IPSG
      
      ★ 跳过第 ③ 步 = 服务器/打印机/摄像头全部断网 ★
   
   ★ 4. 变更后要在【业务高峰前】验证 ★
      周末改，周一才发现，影响面已经最大化了
```

## 案例 03 · 双出口备份，实际从没生效过

### 现象
```
   公司接了电信和联通两条线路做冗余，配了浮动静态路由。
   某天电信线路故障（★ 但物理接口依然 up ★，故障在运营商侧）。
   ★ 全公司断网 2 小时 ★，浮动路由没有切换。
```

### 排查过程

```cisco
! ① 确认路由状态
R1# show ip route 0.0.0.0
Gateway of last resort is ★ 202.1.1.254 ★ to network 0.0.0.0
S*    0.0.0.0/0 [1/0] via ★ 202.1.1.254 ★
!                          ↑ 依然指向电信

! ② 检查接口
R1# show ip interface brief | include Gi0/1
GigabitEthernet0/1   202.1.1.1   YES manual  ★ up      up ★
!                                              ↑↑↑↑↑↑↑↑↑↑
!                    ★ 接口依然 up！★

! ③ 但实际不通
R1# ping 8.8.8.8 source Gi0/1
.....                                          ✗

R1# ping 202.1.1.254                           ← 运营商网关
.....                                          ✗ 网关都不通

! ④ 检查配置
R1# show run | include ip route 0.0.0.0
 ip route 0.0.0.0 0.0.0.0 202.1.1.254
 ip route 0.0.0.0 0.0.0.0 203.2.2.254 ★ 10 ★
!                                        ↑ 浮动路由配了，但没生效
```

### 根因

**浮动静态路由的撤销条件是"本地出接口 down 或下一跳不可达"。**

```
   R1 ── [光猫] ── [运营商设备] ── Internet
    ↑
   Gi0/1 连的是光猫，光猫没断电
        ↓
   ★ R1 的接口一直是 up ★
        ↓
   ★ 主路由永远不会被撤销 ★
        ↓
   ★ 流量持续送进黑洞 ★
```

### 修复

```cisco
! ★ 用 IP SLA 探测端到端可达性 ★
R1(config)# ip sla 1
R1(config-ip-sla)#  icmp-echo 114.114.114.114 source-interface GigabitEthernet0/1
R1(config-ip-sla-echo)#   frequency 5
R1(config-ip-sla-echo)#   timeout 2000
R1(config)# ip sla schedule 1 life forever start-time now

R1(config)# ip sla 2
R1(config-ip-sla)#  icmp-echo 223.5.5.5 source-interface GigabitEthernet0/1
R1(config-ip-sla-echo)#   frequency 5
R1(config)# ip sla schedule 2 life forever start-time now

R1(config)# track 1 ip sla 1 reachability
R1(config-track)#  delay down 10 up 30
R1(config)# track 2 ip sla 2 reachability
R1(config-track)#  delay down 10 up 30

! ★ 组合跟踪：两个目标都不通才算故障（避免单目标故障误切换）★
R1(config)# track 10 ★ list boolean or ★
R1(config-track)#  object 1
R1(config-track)#  object 2
R1(config-track)#  delay down 15 up 60

! ★ 主路由绑定 track ★
R1(config)# no ip route 0.0.0.0 0.0.0.0 202.1.1.254
R1(config)# ★ ip route 0.0.0.0 0.0.0.0 202.1.1.254 track 10 ★
R1(config)# ip route 0.0.0.0 0.0.0.0 203.2.2.254 10
```

### ★ 教训

```
   ★ 1. "接口 up" ≠ "链路可用" ★
      经过光猫/交换机/运营商设备时，远端故障本地接口不会 down
   
   ★ 2. 浮动路由必须配 IP SLA + Track ★
      这是必配项，不是可选项
   
   ★ 3. 探测多个目标，用布尔或组合 ★
      单个 DNS 服务器可能自己在维护
   
   ★ 4. 必须配 delay 防抖 ★
      不配的话链路轻微抖动就切换，震荡比不切换更糟
      ★ up 的延迟要大于 down ★（故障快速响应，恢复谨慎确认）
   
   ★★ 5. 冗余方案必须做【故障演练】★★
      没演练过的冗余 = 没有冗余
      每季度断一次主链路，验证切换
```

## 案例 04 · 重分发环路导致核心 CPU 100%

### 现象
```
   公司并购，新增一个 EIGRP 网络与原有 OSPF 网络互联。
   配了双点双向重分发（为了冗余）。
   ★ 上线三天后，某天核心交换机 CPU 100%，全网卡顿 ★。
   两台核心之间的横向链路流量从 5Mbps 涨到 900Mbps。
```

### 排查过程

```cisco
! ① CPU 和流量
R1# show processes cpu sorted | exclude 0.00
CPU utilization for five seconds: ★ 98% ★/85%
 PID Runtime(ms) Invoked uSecs 5Sec  1Min  5Min TTY Process
   3   98765432 87654321  1125 ★52.3%★ ... ★ IP Input ★
                                              ↑ 转发进程占用极高

R1# show interfaces GigabitEthernet0/2 | include rate
  5 minute input rate ★ 890000000 ★ bits/sec
  5 minute output rate ★ 890000000 ★ bits/sec
!                        ↑ 横向链路被打满

! ② ★ 关键：traceroute ★
R1# traceroute 10.1.5.1
  1 ★ 10.0.12.2 ★  4 msec
  2 ★ 10.0.12.1 ★  8 msec
  3 ★ 10.0.12.2 ★  4 msec
  4 ★ 10.0.12.1 ★  8 msec
  ...
  ★★ IP 往复 = 路由环路 ★★

! ③ 查路由
R1# show ip route 10.1.5.0
Routing entry for 10.1.5.0/24
  Known via "ospf 1", distance 110, metric 20, ★ type extern 2 ★
  Routing Descriptor Blocks:
  * ★ 10.0.12.2 ★, from 2.2.2.2, via GigabitEthernet0/2
!                     ↑ 指向 R2

R2# show ip route 10.1.5.0
  Known via "ospf 1", distance 110, metric 20, ★ type extern 2 ★
  * ★ 10.0.12.1 ★, from 1.1.1.1, via GigabitEthernet0/2
!                     ↑ ★ 指向 R1 —— 互相指 ★

! ④ 为什么变成了外部路由？
R1# show ip ospf database external | include 10.1.5.0 -A 3
  Link State ID: 10.1.5.0
  ★ Advertising Router: 2.2.2.2 ★
!                        ↑ ★ R2 把这条路由重分发【回】了 OSPF ★

! ⑤ 时间线
R1# show logging | include OSPF
! 发现前一天 EIGRP 域里某个网段的源链路断了
```

### 根因

**双点双向重分发，没有做防环。**

```
   ① 10.1.5.0/24 原本是 EIGRP 域的路由
   ② R1 把它重分发进 OSPF（变成 O E2）
   ③ R2 从 OSPF 学到，又把它重分发【回】EIGRP
   ④ R1 从 EIGRP 学到这条"回流"的路由
   
   ⑤ ★ 平时靠 AD 关系压着（EIGRP 内部 90 < OSPF 外部 110）★
   
   ⑥ ★★ 某天原始源断了 ★★
        ↓
   ⑦ R1 只剩下从 R2 学到的回流路由
   ⑧ R2 只剩下从 R1 学到的回流路由
        ↓
   ★★★ 互相指，环路形成 ★★★
```

### 修复

```cisco
! ★ Route Tag 防环（R1 和 R2 配完全相同的内容）★

route-map OSPF-TO-EIGRP ★ deny 5 ★
 ★ match tag 200 ★
route-map OSPF-TO-EIGRP permit 10
 ★ set tag 100 ★
 set metric 100000 100 255 1 1500

route-map EIGRP-TO-OSPF ★ deny 5 ★
 ★ match tag 100 ★
route-map EIGRP-TO-OSPF permit 10
 ★ set tag 200 ★

router eigrp 100
 redistribute ospf 1 route-map OSPF-TO-EIGRP

router ospf 1
 redistribute eigrp 100 subnets route-map EIGRP-TO-OSPF
```

### ★ 教训

```
   ★ 1. 双点双向重分发必须做防环 ★
      这不是"可选的优化"，是"必须的配置"
   
   ★ 2. Route Tag 是首选方案 ★
      · 属性随路由传播（不像 AD 是局部行为）
      · 自动适应拓扑变化
      · 两个重分发点配完全相同的内容
   
   ★ 3. 环路可能潜伏很久才爆发 ★
      平时被 AD 关系压着，某次链路故障才触发
      ★ 所以配置时就要防，不能"没出问题就不管"
   
   ★ 4. traceroute 看到 IP 往复 = 环路的确定证据 ★
      这是最快的判断方法
   
   ★ 5. 上线新的重分发配置后，要做【故障演练】★
      主动断掉源链路，验证不会形成环路
      ★ 修复成功的标志是"路由消失"，而不是"环路可达" ★
```

## 案例 05 · VPN 隧道 UP 但内网不通

### 现象
```
   分支到总部配了 IPsec VPN。
   ★ show crypto session 显示 UP-ACTIVE ★
   ★ 但两边内网互相 ping 不通 ★
```

### 排查过程

```cisco
! ① 隧道状态确实正常
Branch# show crypto session
Interface: Tunnel0
Session status: ★ UP-ACTIVE ★
Peer: 202.1.1.1 port 500
  IKEv2 SA: local 203.2.2.2/500 remote 202.1.1.1/500 ★ Active ★

! ② ★ 关键：看计数器 ★
Branch# show crypto ipsec sa | include pkts
    #pkts encaps: ★ 0 ★, #pkts encrypt: ★ 0 ★, #pkts digest: 0
    #pkts decaps: ★ 0 ★, #pkts decrypt: ★ 0 ★, #pkts verify: 0
!                  ↑↑↑↑↑
!    ★★ 两个都是 0 = 流量根本没进隧道 ★★

! ③ 路由呢？
Branch# show ip route 192.168.99.0
S    192.168.99.0/24 [1/0] via 203.2.2.254         ← 有路由 ✓

! ④ ★ 查 NAT ★
Branch# show ip nat translations | include 192.168.99
★ tcp 203.2.2.2:50001  192.168.1.10:51234  192.168.99.10:445 ... ★
!                                            ↑
!  ★★ 去总部的流量被 NAT 了！★★

! ⑤ 查 NAT 的 ACL
Branch# show access-lists NAT-LIST
Extended IP access list NAT-LIST
    10 permit ip 192.168.1.0 0.0.0.255 any (23451 matches)
!   ★ 没有 deny 去总部的流量 ★
```

### 根因

**NAT 的 ACL 没有排除去往 VPN 对端的流量。**

```
   ① PC (192.168.1.10) → 总部 (192.168.99.10)
   ② ★ NAT 先执行：源地址被改成 203.2.2.2 ★
   ③ 再匹配 IPsec 的感兴趣流 ACL：
      permit ip 192.168.1.0 0.0.0.255 192.168.99.0 0.0.0.255
      ★ 源地址已经变成 203.2.2.2，不匹配了 ★
   ④ 包不进隧道，直接从互联网发出
   ⑤ 总部收不到（或收到源地址是公网的包，回不来）
```

### 修复

```cisco
Branch(config)# ip access-list extended NAT-LIST
Branch(config-ext-nacl)# ★ 5 deny ip 192.168.1.0 0.0.0.255 192.168.99.0 0.0.0.255 ★
!                          ↑ ★ 必须在 permit 之前 ★
```

**验证**：
```cisco
Branch# show access-lists NAT-LIST
    ★ 5 deny ip 192.168.1.0 0.0.0.255 192.168.99.0 0.0.0.255 (456 matches) ★
    10 permit ip 192.168.1.0 0.0.0.255 any (23451 matches)

Branch# show ip nat translations | include 192.168.99
! ★ 空 ✓ ★

Branch# show crypto ipsec sa | include pkts
    #pkts encaps: ★ 456 ★, #pkts encrypt: 456
    #pkts decaps: ★ 452 ★, #pkts decrypt: 452
!                  ↑ ★ 双向都在涨 ✓ ★
```

### ★ 教训

```
   ★★ 1. 配完 VPN，第一件事查 NAT ★★
      这是站点到站点 VPN 部署的头号故障
   
   ★ 2. encaps/decaps 计数器是 IPsec 排障的黄金工具 ★
      | encaps | decaps | 诊断 |
      |  涨   |  涨   | ✅ 正常 |
      |  涨   |  0    | ❌ 对端问题 |
      |  0    |  涨   | ❌ 本端问题（路由/NAT） |
      |  0    |  0    | ❌ 流量没进隧道 |
      ★ 30 秒定位问题在哪一端 ★
   
   ★ 3. "隧道 UP" ≠ "业务通" ★
      控制平面（IKE）和数据平面（ESP）是两回事
   
   ★ 4. NAT 和 IPsec 的处理顺序 ★
      Inside→Outside：路由 → ★ NAT ★ → 加密
      所以 NAT 会破坏感兴趣流的匹配
   
   ★ 5. deny 语句必须在 permit 之前 ★
      ACL 自上而下，顺序错了 deny 永远不生效
```

## 案例 06 · 会议室 Wi-Fi 通话卡顿

### 现象
```
   员工从工位走到会议室的路上，微信语音/Teams 会议会断 2-3 秒。
   在固定位置使用时正常。
   ★ 只有部分品牌的手机有这个问题 ★
```

### 排查过程

```cisco
! ① 确认是漫游问题
(WLC) > show client detail <MAC>
! 走动前
AP Name ......................... AP-8F-05
IP Address ...................... ★ 192.168.200.55 ★

! 走动后
AP Name ......................... AP-8F-12
IP Address ...................... ★ 192.168.200.55 ★     ← IP 没变 ✓
! ★ 排除 L3 漫游问题 ★

! ② 检查快速漫游
(WLC) > show wlan 1 | include Fast Transition
Fast Transition .................. ★ Disabled ★          ← ★ 找到了

! ③ 检查覆盖重叠
(WLC) > show client detail <MAC>
! 在切换点
Radio Signal Strength Indicator . ★ -76 dBm ★            ← 太弱
Signal to Noise Ratio ........... ★ 15 dB ★              ← 太低

! ④ 为什么只有部分手机有问题
! → 不同厂商的漫游阈值不同
!   有的 -70dBm 就切，有的 -80dBm 才切（★ 粘滞客户端 ★）
```

### 根因

**两个原因叠加**：
1. **没启用 802.11r（快速漫游）** → 每次漫游要完整的 EAP 认证，**300-500ms 中断**
2. **AP 覆盖重叠不足** → 切换点信号只有 -76dBm，质量已经很差

### 修复

```
   ① 启用快速漫游三件套
      WLANs > <WLAN> > Security > Layer 2 > 
         ★ Fast Transition: Adaptive ★（兼容老设备）
         Over the DS: ☑
      WLANs > <WLAN> > Advanced > 
         ★ 802.11k: Neighbor List ☑ ★
         ★ 802.11v: BSS Transition ☑ ★
   
   ② 调整 AP 覆盖
      · 提高切换区域的 AP 功率（或加一个 AP）
      · 目标：覆盖重叠 15-20%，切换点 RSSI > -67dBm
   
   ③ 应对粘滞客户端
      · ★ 禁用低速率（1/2/5.5/11 Mbps）★
      · 降低 AP 发射功率（缩小蜂窝，逼客户端更早切换）
      · 启用 802.11v 主动引导
```

**结果**：切换时间从 400ms 降到 40ms 以内，用户无感知。

### ★ 教训

```
   ★ 1. 漫游是【客户端】决定的，不是网络 ★
      网络侧只能"引导"（802.11v），不能"强制"
      ★ 不同厂商的客户端漫游行为差异巨大 ★
   
   ★ 2. 802.11r/k/v 三者配合才有最佳效果 ★
      · 11k：告诉客户端往哪扫（省扫描时间）
      · 11v：主动建议何时切换
      · 11r：★ 跳过完整认证（省 300ms）★
   
   ★ 3. 802.11r 有兼容性问题 ★
      部分老设备开启后连不上
      → 用 ★ Adaptive 802.11r ★，或建两个 SSID
      → ★ 部署前必须测试所有终端类型 ★
   
   ★ 4. "只有部分设备有问题"往往指向客户端行为差异 ★
      这个信息本身就是重要线索
   
   ★ 5. 语音对漫游的要求：★ 切换 < 50ms ★
      标准漫游 300-500ms → 必然卡顿
```

## 案例 08 · 打印机每天早上失联

### 现象
```
   一台网络打印机，★ 每天早上第一次打印时失败 ★，
   重新打印一次就好了。
   打印机配的是静态 IP。
```

### 排查过程

```cisco
! ① 打印机的 IP 和 MAC
SW1# show ip arp | include 192.168.10.200
Internet  192.168.10.200   ★ 245 ★  0011.2233.4455  ARPA  Vlan10
!                            ↑ ARP 表项的老化时间（分钟）

! ② ★ 关键发现 ★
SW1# show mac address-table address 0011.2233.4455
! ★ 早上第一次查：空 ★
! 打印一次之后再查：有了

! ③ 时间线分析
!   打印机晚上会进入省电休眠
!   休眠时不发任何流量
!        ↓
!   ★ 交换机 MAC 表老化（默认 300 秒）★
!   ★ ARP 表也老化（默认 4 小时）★
!        ↓
!   早上第一次打印：
!   · 交换机不知道这个 MAC 在哪个口 → ★ 泛洪 ★
!   · 路由器 ARP 表没有 → 发 ARP 请求
!        ↓
!   ★ 打印机在休眠，不响应 ARP ★
!        ↓
!   打印失败
!        ↓
!   但 ARP 请求把打印机唤醒了
!        ↓
!   第二次打印成功
```

### 根因

**打印机的省电休眠 + ARP/MAC 表老化的组合效应。**

### 修复

```cisco
! ── 方案 1：静态 ARP 绑定（最直接）──
R1(config)# ★ arp 192.168.10.200 0011.2233.4455 ARPA ★

! ── 方案 2：静态 MAC 表项 ──
SW1(config)# ★ mac address-table static 0011.2233.4455 vlan 10 interface Gi1/0/30 ★

! ── 方案 3：延长老化时间 ──
SW1(config)# mac address-table aging-time 1800          ! 30 分钟
R1(config)# interface Vlan10
R1(config-if)# arp timeout 28800                         ! 8 小时

! ── 方案 4（★ 治本）：关闭打印机的省电模式 ──
! 在打印机的 Web 管理界面：
! 设置 → 节能 → 休眠模式 → 关闭
! 或延长休眠等待时间到 8 小时以上
```

**推荐**：**方案 4 + 方案 1 组合**。

### ★ 教训

```
   ★ 1. "每天早上第一次"是极强的时间规律线索 ★
      → 一定与"某个定时行为"或"老化机制"有关
      → 常见的：ARP 老化、MAC 老化、DHCP 租约、会话超时、休眠
   
   ★ 2. 老化时间的默认值要记住 ★
      | 表 | 默认老化 |
      |---|---|
      | MAC 地址表 | ★ 300 秒（5 分钟）★ |
      | ARP 表 | ★ 4 小时 ★ |
      | NAT 表（TCP） | 24 小时 |
      | NAT 表（UDP） | 5 分钟 |
      | DHCP 租约 | 视配置 |
   
   ★ 3. IoT/嵌入式设备的省电特性是隐藏的坑 ★
      打印机、摄像头、门禁、传感器都可能有类似问题
   
   ★ 4. "重试一次就好"的问题，往往是缓存/表项失效 ★
      第一次触发了建表，第二次就命中了
```

## 案例 09 · MPLS L3VPN 上线后业务时好时坏

### 现象
```
   新开通的 MPLS L3VPN 专线。
   · ping 正常
   · SSH 能连
   · ★ 但网页打开一半就卡住，大文件传输失败 ★
   · 有时候又好像正常
```

### 排查过程

```cisco
! ① ★ 第一反应：MTU 测试 ★
PE1# ping vrf CUSTOMER-A 192.168.2.10 size 100
!!!!!                                              ✓

PE1# ★ ping vrf CUSTOMER-A 192.168.2.10 size 1500 df-bit ★
★ M.M.M ★                                          ✗

! ② 二分法找实际 MTU
PE1# ping vrf CUSTOMER-A 192.168.2.10 size 1400 df-bit
!!!!!                                              ✓
PE1# ping vrf CUSTOMER-A 192.168.2.10 size 1492 df-bit
!!!!!                                              ✓
PE1# ping vrf CUSTOMER-A 192.168.2.10 size 1493 df-bit
M.M.M                                              ✗
! ★ 实际可用 MTU = 1492 = 1500 - 8（两层 MPLS 标签）★

! ③ ★ 用 MPLS 专用工具逐跳查 MTU ★
PE1# ★ trace mpls ip 2.2.2.2/32 ★
Tracing MPLS Label Switched Path to 2.2.2.2/32, timeout is 2 seconds

  0 10.0.12.1 ★ MRU 1600 ★ [Labels: 16 Exp: 0]
R 1 10.0.12.2 ★ MRU 1600 ★ [Labels: 17 Exp: 0] 4 ms
R 2 10.0.23.3 ★ MRU 1500 ★ [Labels: implicit-null] 8 ms
                   ↑↑↑↑↑↑↑↑
       ★★ 这一跳的 MRU 只有 1500，其他都是 1600 ★★

! ④ 定位到具体设备
P2# show interfaces GigabitEthernet0/1 | include MTU
  MTU ★ 1500 ★ bytes                              ← 找到了
```

### 根因

**骨干网中有一台 P 路由器的接口 MTU 没有加大。**

```
   MPLS L3VPN 需要两层标签 = ★ 8 字节开销 ★
        ↓
   1500 字节的用户包 + 8 = 1508
        ↓
   ★ 超过该接口的 1500 MTU → 被丢弃 ★
```

**"有时候好像正常"**：因为小包（ping、SSH、HTTP 首部）不受影响，只有满载的大包才失败。

### 修复

```cisco
P2(config)# interface GigabitEthernet0/1
P2(config-if)# ★ mtu 1600 ★
P2(config-if)# ★ mpls mtu 1600 ★

! ★ 更彻底：全网开巨帧 ★
P2(config-if)# mtu 9000
P2(config-if)# mpls mtu 9000
```

**验证**：
```cisco
PE1# trace mpls ip 2.2.2.2/32
  0 10.0.12.1 MRU 1600 [Labels: 16]
R 1 10.0.12.2 MRU 1600 [Labels: 17] 4 ms
R 2 10.0.23.3 ★ MRU 1600 ★ [Labels: implicit-null] 8 ms      ✓

PE1# ping vrf CUSTOMER-A 192.168.2.10 size 1500 df-bit
!!!!!                                              ✓
```

### ★ 教训

```
   ★★ 1. MPLS/VXLAN/GRE 部署的第一个检查项永远是 MTU ★★
      | 封装 | 开销 |
      |---|---|
      | MPLS（每层标签） | 4 字节 |
      | ★ MPLS L3VPN（两层）★ | ★ 8 字节 ★ |
      | GRE | 24 字节 |
      | IPsec 隧道模式 | ~58 字节 |
      | ★ VXLAN ★ | ★ 50 字节 ★ |
   
   ★ 2. "小包通大包不通" = MTU 问题 ★
      这是最典型的特征，第一反应就该测
   
   ★ 3. 必须【全路径】检查，漏一台就有问题 ★
      ★ trace mpls ip 的 MRU 字段是最直接的工具 ★
   
   ★ 4. 推荐直接开巨帧（9000）★
      一劳永逸，未来加更多标签也不怕
   
   ★ 5. "时好时坏"往往指向"部分流量受影响" ★
      而不是"间歇性完全中断"
      ★ 要问清楚：是所有操作都慢，还是只有某类操作失败 ★
```

```cisco

PC> ping <域控IP>
Reply                                              ✓
PC> telnet <域控IP> 389                            ← LDAP
（连上了）                                          ✓
PC> telnet <域控IP> 88                             ← Kerberos
（连上了）                                          ✓
! ★ 网络完全正常 ★

! ② 客户端报错
"安全数据库上的服务器没有此工作站的计算机账户信任关系"
或 "时钟偏差太大"

! ③ ★ 检查时间 ★
PC> w32tm /query /status
! 时间显示：2026-08-31 09:15
! 域控时间：2026-08-31 ★ 09:23 ★
! ★ 相差 8 分钟 ★

! ④ 检查网络设备的时间
SW-CORE# ★ show clock ★
★ 09:15:23.123 CST Mon Aug 31 2026 ★

SW-CORE# ★ show ntp status ★
★ Clock is unsynchronized ★, stratum 16, no reference clock

SW-CORE# ★ show ntp associations ★
  address        ref clock   st  when poll ★reach★ delay offset disp
  ~10.1.30.61    ★.INIT.★   ★16★   -  1024   ★0★   0.000  0.000 16000
!                   ↑         ↑             ↑
!            未初始化    无效层级    ★ 一次都没成功 ★

! ⑤ 为什么 NTP 不通？

!!!!!                                              ← IP 通

! ★ 查 ACL ★

    45 ★ deny udp any any eq ntp (12456 matches) ★
!      ↑ ★ 找到了 ★
```

### 根因

**周末做安全加固时，新增的 ACL 拦截了 UDP 123（NTP）。**

```
   ① NTP 被拦 → 网络设备和服务器时间逐渐漂移
   ② ★ Kerberos 默认只容忍 5 分钟的时间偏差 ★
   ③ 偏差超过 5 分钟 → ★ 域认证全部失败 ★
```

### 修复

```cisco

R3(config-ext-nacl)# 46 permit udp any host 10.1.30.62 eq ntp

! ② ★ 时间偏差 > 1000 秒时 NTP 会拒绝同步，需先手工校准 ★
SW-CORE# ★ clock set 09:23:00 31 Aug 2026 ★

! ③ 等待同步
SW-CORE# show ntp status
★ Clock is synchronized ★, stratum 4, reference is 10.1.30.61     ✓
```

### ★ 教训

```
   ★★ 1. NTP 是很多功能的隐藏前提 ★★
      | 依赖 NTP | 时间不准的后果 |
      |---|---|
      | ★ Kerberos/AD ★ | ★ 容忍 5 分钟，超了全公司登录失败 ★ |
      | 证书验证 | HTTPS/802.1X/DTLS 报"证书尚未生效" |
      | 日志关联 | 多设备日志对不上，无法还原时间线 |
      | 时间 ACL | 行为不可预测 |
      | key-chain lifetime | 路由协议认证失败 |
      | 审计合规 | 时间戳不可信 |
   
   ★ 2. 安全加固的 ACL 必须评估影响面 ★
      不能只想着"拦掉不需要的"，要列出"必须放行的"清单：
      □ NTP (UDP 123)
      □ DNS (UDP + ★ TCP ★ 53)
      □ ★ ICMP unreachable ★（PMTUD）
      □ 路由协议（OSPF 89、EIGRP 88、BGP TCP 179）
      □ ★ IPsec（UDP 500/4500 + ESP 协议号 50）★
      □ RADIUS (1812/1813)、TACACS+ (TCP 49)
      □ Syslog (UDP 514)、SNMP (161/162)
   
   ★ 3. "网络正常但业务不通"要往服务层想 ★
      NTP、DNS、DHCP、AAA 都是"网络层正常但业务依赖"的服务
   
   ★ 4. NTP 偏差 > 1000 秒会拒绝同步 ★
      必须先手工 clock set
   
   ★ 5. 加固变更也要做完整的验证清单 ★
      不能只测"网络通不通"
```

### 长期加固

```cisco
! ── ① 全局和单机上限 ──
R1(config)# ★ ip nat translation max-entries 60000 ★
R1(config)# ★ ip nat translation max-entries all-host 500 ★

! ── ② 缩短超时（快速释放）──
R1(config)# ip nat translation timeout 3600
R1(config)# ip nat translation udp-timeout 60
R1(config)# ip nat translation icmp-timeout 10
R1(config)# ★ ip nat translation syn-timeout 30 ★
!            ↑ ★ 半开连接超时，专门对付扫描 ★

! ── ③ 出站过滤（限制内网主动扫描）──
R1(config)# ip access-list extended OUTBOUND-CONTROL
R1(config-ext-nacl)#  ★ deny tcp any any eq 445 log ★
R1(config-ext-nacl)#  deny tcp any any eq 135 log
R1(config-ext-nacl)#  deny tcp any any eq 139 log
R1(config-ext-nacl)#  permit ip any any
R1(config)# interface Gi0/0
R1(config-if)# ip access-group OUTBOUND-CONTROL in

! ── ④ EEM 自动告警 ──
R1(config)# event manager applet NAT-TABLE-HIGH
R1(config-applet)#  event snmp oid 1.3.6.1.4.1.9.10.77.1.2.1.0 \
                     get-type exact entry-op ge entry-val 50000 poll-interval 60
R1(config-applet)#  action 1.0 cli command "enable"
R1(config-applet)#  action 2.0 cli command "show ip nat statistics"
R1(config-applet)#  action 3.0 syslog msg "ALERT: NAT translations > 50000"
```

### ★ 教训

```
   ★★ 1. 出口 CPU 突然飙高 + NAT 表暴涨 = 内网有机器中毒扫描 ★★
      这是最常见的模式
   
   ★ 2. 定位命令 ★
      show ip nat translations | include <IP> | count
   
   ★ 3. 扫描 vs 正常业务的特征区分 ★
      | 特征 | 扫描 | 正常 |
      |---|---|---|
      | 目的 IP | ★ 连续变化 ★ | 相对固定 |
      | 目的端口 | ★ 固定（445/3389/22）★ | 多样 |
      | 每流字节数 | ★ 极少（只有 SYN）★ | 正常 |
      | 成功率 | ★ 极低 ★ | 高 |
   
   ★ 4. 预防比救火重要 ★
      · ★ max-entries all-host 500 ★（单机上限，让中毒机器不拖垮全网）
      · syn-timeout 30（快速释放半开连接）
      · 出站过滤（限制内网主动访问的高危端口）
      · 监控告警（EEM/SNMP）
   
   ★ 5. NetFlow 是流量分析的关键工具 ★
      "★ 流数量极多但每条流字节数很少 ★" = 扫描的确定特征
```

## 案例 12 · BGP 策略变更导致部分网段不可达

### 现象
```
   运维人员在出口路由器上修改了 BGP 的 route-map（想给某个网段加高优先级）。
   改完执行 clear ip bgp x.x.x.x soft in。
   ★ 5 分钟后开始有用户报"某些网站打不开" ★。
```

### 排查过程

```cisco
! ① ★ 立即检查前缀数（第一反应）★
R1# show ip bgp summary
Neighbor       V   AS  MsgRcvd MsgSent TblVer InQ OutQ Up/Down ★State/PfxRcd★
202.1.1.254    4  100     2451    2438      8   0    0 02:15:33     ★ 3 ★
!                                                                     ↑
!                              ★★ 只收到 3 条！本来应该有 1245 条 ★★

! ② ★ 关键对比：received vs routes ★
R1# ★ show ip bgp neighbors 202.1.1.254 received-routes | count ★
Number of lines which match regexp = ★ 1248 ★          ← 原始收到 1245 条

R1# ★ show ip bgp neighbors 202.1.1.254 routes | count ★
Number of lines which match regexp = ★ 6 ★             ← 过滤后只剩 3 条

! ★★ received 有但 routes 没有 = 被 in 方向的策略过滤了 ★★

! ③ 查策略
R1# show run | include neighbor 202.1.1.254
 neighbor 202.1.1.254 route-map ★ TELECOM-POLICY ★ in

R1# ★ show route-map TELECOM-POLICY ★
route-map TELECOM-POLICY, permit, sequence 10
  Match clauses:
    ip address prefix-lists: ★ IMPORTANT-NETS ★
  Set clauses:
    local-preference 200
  Policy routing matches: 0 packets, 0 bytes
! ★★ 只有 sequence 10，没有兜底！★★

! ④ 确认
R1# show ip prefix-list IMPORTANT-NETS
ip prefix-list IMPORTANT-NETS: 1 entries
   seq 5 permit 203.119.0.0/16
! ★ 只匹配一个网段，其他所有路由被隐含 deny 拦掉 ★
```

### 根因

**route-map 末尾有隐含的 `deny`，运维人员只写了 `permit 10`（匹配特定网段），没有加兜底的 `permit`。**

**结果**：除了那一个网段，**其他 1242 条路由全被拒绝了**。

### 修复

```cisco
R1(config)# ★ route-map TELECOM-POLICY permit 20 ★
! ★ 空的 permit 语句 ★
!   没有 match = 匹配所有剩余的
!   没有 set   = 不修改任何属性
!   → 原样放行

R1# clear ip bgp 202.1.1.254 soft in
```

**验证**：
```cisco
R1# show ip bgp summary | include 202.1.1.254
202.1.1.254  4  100  2451  2438  8  0  0 02:15:33  ★ 1245 ★        ← 恢复 ✓

R1# show route-map TELECOM-POLICY
route-map TELECOM-POLICY, permit, sequence 10
  Match clauses:
    ip address prefix-lists: IMPORTANT-NETS
  Set clauses:
    local-preference 200
★ route-map TELECOM-POLICY, permit, sequence 20 ★
  ★ Match clauses: ★                                ← 空 = 匹配所有
  ★ Set clauses: ★                                  ← 空 = 不修改
```

### ★ 教训

```
   ★★ 1. route-map / prefix-list / ACL / as-path 末尾都有隐含 deny ★★
      ★ 永远记得加兜底的 permit ★
   
   ★★ 2. 改完 BGP 策略立即对比前缀数 ★★
      show ip bgp summary  ← 数字大幅下降 = 有问题
   
   ★ 3. received-routes vs routes 的对比是判断"是否被策略过滤"的黄金方法 ★
      需要先配 neighbor X soft-reconfiguration inbound
   
   ★★ 4. 生产环境改 BGP 策略的标准流程 ★★
      ① 记录当前状态
         R1# show ip bgp summary | redirect flash:before.txt
      ② ★ 用 configure revert 保险 ★
         R1# write memory
         R1# configure terminal revert timer 5
      ③ 改策略（★ 记得加兜底 ★）
      ④ 软重置
         R1# clear ip bgp X soft in
      ⑤ ★ 立即对比前缀数 ★
      ⑥ 确认无误
         R1# configure confirm
   
   ★ 5. 永远不要用 clear ip bgp * ★
      硬重置会断开所有会话，全表重传，业务中断几分钟
```

## 案例 13 · 网站时好时坏，主站正常但页面白屏

### 现象
```
   用户报"某业务网站访问极慢"。
   ★ 主站能打开，但页面一直白屏 ★
   干等几十秒也出不来内容。

   ★ 过几小时它自己好了，之后又复发 ★
   同一时间，其他网站都正常。
```

### 排查过程

```bash
! ① 先分层：主站到底慢不慢？
$ curl -o /dev/null -w "code=%{http_code} ttfb=%{time_starttransfer}\n" https://www.example.com
code=200 ttfb=0.502
!                ↑ ★ 主站 0.5 秒就返回了，根本不慢 ★
$ ping www.example.com
!   平均 8ms，★ 0% 丢包 ★
!   → 链路、带宽、防火墙全部排除

! ② 那慢在哪？看浏览器的完整请求列表
!   GET www.example.com/                => 200
!   GET g.alicdn.com/....js             => 200
!   GET cdn.example.com/index.js        ★ 无状态码 ★
!   GET cdn.example.com/index.css       ★ 无状态码 ★
!   GET cdn.example.com/font/*.woff     ★ 无状态码 ★
!
!   ★★ CSS 和入口 JS 全在独立的 CDN 域名上，且全部永不返回 ★★
!   → 所以是白屏干等超时，不是"网速慢"

! ③ 单独测这个 CDN 域名
$ dig cdn.example.com +noall +answer
cdn.example.com.        CNAME  cdn.example.com.w.kunluncan.com.
...w.kunluncan.com.  ★ 16722 ★  IN  A  103.228.211.38
!                       ↑ TTL 16722 秒 = 4.6 小时，可疑
$ curl --max-time 8 https://cdn.example.com/index.js
!   ★ 8 秒超时，code=000 ★

! ④ ★ 关键对照：换个 DNS 问同一个域名 ★
$ dig @223.5.5.5 cdn.example.com +noall +answer
...w.kunluncan.com.     ★ 54 ★  IN  A  125.73.210.84
!                          ↑ ★★ 权威只给 54 秒，差了 310 倍 ★★
!                          ↑ ★★ 而且给的是完全不同的一组 IP ★★

! ⑤ ★★ 决定性实验：同一个 URL，只换目标 IP ★★
$ curl --connect-to cdn.example.com:443:103.228.211.38:443 https://cdn.example.com/index.js
    code=000                      ★ 超时 ★
$ curl --connect-to cdn.example.com:443:125.73.210.84:443  https://cdn.example.com/index.js
    code=200  0.19s               ★ 秒开 ★
!
!   ★★ 同一台电脑、同一条网线、同一个 URL ★★
!   ★★ 唯一变量是目标 IP ★★
!   → 一次实验同时排除：客户端、防火墙、链路、带宽、网站本身

! ⑥ 那批死 IP 是什么来头？
$ whois 103.228.211.38    → 广西广电 GXRTVNET   ★ 8 个 IP 全不通 ★
$ whois 125.73.210.84     → 广西电信 CHINANET-GX  可用
!   都是 CDN 在当地运营商机房部署的节点，IP 归属运营商属正常现象

! ⑦ ★ 守着它自愈，把周期抓全 ★
!   14:20   内网 DNS 给 103.228.211.x，剩余 TTL ★ 4257 ★
!   15:30   同一条记录，剩余 TTL ★ 1710 ★     ← 在正常倒数
!   17:06   ★ 缓存到期，重新向上游查询 ★
!           改给 125.73.210.x，新 TTL 16755
!           ★★ 网站自己好了，全程无人干预 ★★
```

> **旁证**：该站点前端自带遥测，白屏期间它自己上报了
> `/_boot?e=stuck&cdn_ms=5002&cdn_ok=0&same_ms=18&same_ok=1`
> ——**站点自判 CDN 探测失败、同源正常**，与排查结论完全一致。
> **遇到陌生站点，翻一眼它自己的埋点请求，有时能白捡一个交叉验证。**

### 根因

**内网 DNS 开启了 min-TTL 覆盖（缓存下限），把 CDN 的秒级 TTL 冻成了小时级。**

```
   权威说：这组节点你只能记 54 秒
   内网 DNS：我记 16722 秒（4.6 小时）
        │
        ▼
   某次缓存刷新，恰好抄到一组已下线的节点
        │
        ▼
   ★ 这组死地址被冻住 4.6 小时，期间照发给全公司 ★
        │
        ▼
   缓存到期 → 重新查询 → 这次抽到可用节点 → "自己好了"
        │
        ▼
   ★★ 下次刷新再抽一次签，故障必然复发 ★★
```

**抽查其他域名，确认这是全局配置而非单域名问题**：

| 域名 | 权威 TTL | 内网 TTL | 放大倍数 |
|:--|--:|--:|--:|
| `www.baidu.com` | 6 | 8,656 | ★ **1443×** ★ |
| `g.alicdn.com` | 12 | 15,963 | ★ **1330×** ★ |
| `img.alicdn.com` | 26 | 16,260 | 625× |
| `cdn.example.com` | 54 | 16,722 | 310× |
| `www.taobao.com` | 55 | 14,468 | 263× |
| `www.qq.com` | 18 | 2,268 | 126× |

→ **所有域名都被放大几百到一千多倍。这不是某个网站的问题，而是一颗对所有 CDN 站点生效的定时炸弹。**

### 修复

```bash
! ── 治本：关掉 DNS 设备的 min-TTL 覆盖 ──
dnsmasq  :  删除 --min-cache-ttl（或设为 0）
AdGuard  :  cache_min_ttl: 0
设备侧   :  cache-min-ttl / TTL override 关闭
!  ★ 若设备不支持全局关闭，至少对 CDN 类域名放行真实 TTL ★

! ── 改完必须复验：两边 TTL 应在同一量级 ──
$ dig @<内网DNS>  cdn.example.com +noall +answer
$ dig @223.5.5.5  cdn.example.com +noall +answer
!  ★ 内网若仍是上万秒，说明配置没生效 ★

! ── 应急：清掉该域缓存 ──
H3C   :  reset dns host
华为  :  reset dns dynamic-host
!  ★ 只是把抽签时间提前，不解决根因 ★

! ── 应急（单机）：客户端 DNS 改公共 DNS ──
!  ★ 会绕过内网域名解析，仅适合临时验证 ★

! ── ⚠️ 禁止：用 hosts 写死 CDN 的 IP ──
!  CDN 节点本就轮换，写死等于把当前这组永久冻住
!  ★★ 会把间歇故障变成永久故障，而且更难定位 ★★
```

### ★ 教训

```
   ★★ 1. "主站正常但页面白屏" = 立刻去查独立的资源域名 ★★
      现代网站的 CSS/JS/字体几乎都托管在单独的 CDN 域名上
      主站域名正常，完全不代表资源域名正常
      → ★ 要看浏览器的完整请求列表，而不是只 ping 主站 ★
   
   ★★ 2. "过一会儿自己好了" 不等于修好了 ★★
      间歇周期 = 缓存周期
      → ★ 能自愈的故障反而更要查清根因，因为它必然复发 ★
      → 这类报障历来"找不到规律"，规律就藏在 TTL 里
   
   ★★ 3. 同一个 URL 只换目标 IP，是最干净的对照实验 ★★
      curl --connect-to  /  curl --resolve
      → 一次实验同时排除：客户端、防火墙、链路、带宽、网站本身
      → ★ 学会这一招，能省掉大量无效排查 ★
   
   ★ 4. 比 TTL 量级，一条命令定性 ★
      权威给几十秒、内网给上万秒 = min-TTL 覆盖
      → 这个手法可套用到任何"怀疑解析有问题"的场景
   
   ★ 5. TTL 有两个含义，别混 ★
      IP 头 TTL = 跳数     DNS TTL = 秒
      → 详见 [CCNA 补齐篇 07](../01-CCNA补齐篇/07-DHCP-DNS-NTP基础服务.md)
   
   ★★ 6. 善意的优化同样会制造故障 ★★
      min-TTL 的初衷是"减少上游查询、加快解析"，出发点没错
      → 但对秒级调度的 CDN，它直接废掉了调度机制
      → ★ 任何"缓存加速"类配置都要先问一句：
           被缓存的东西，变化有多快？★
   
   ★ 7. tracert 中间跳超时 ≠ 丢包 ★
      骨干路由器普遍不回 ICMP Time Exceeded
      → ★ 以末跳是否稳定回包为准 ★
   
   ★ 8. 服务层是分层排障最容易被跳过的一层 ★
      ping 通、traceroute 通、telnet 端口通，用户还是打不开
      → 问题可能在"解析"而不是"转发"
      → ★ 判断口诀：换个 DNS 试试 ★
```

- 看到"证书报错"就想到 NTP

**你已经到 L2 了。**

**通往 L3 的路**：每次故障后问一句 —— **"这类故障怎么才能不再发生？"**，然后把答案变成设计规范、监控项或演练流程。
