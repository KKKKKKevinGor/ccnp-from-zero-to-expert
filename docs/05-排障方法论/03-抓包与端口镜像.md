# 03 · 抓包与端口镜像

> **抓包是排障的"终极武器"**：当所有 `show` 命令都显示正常，但业务就是不通时，抓包能告诉你**实际发生了什么**。

## ① 什么时候需要抓包

| 场景 | 为什么需要抓包 |
|:--|:--|
| **`show` 命令都正常但业务不通** | 看实际的报文交互 |
| **需要证明"不是网络的问题"** | ★ 用数据说话，而不是争论 |
| **协议层面的疑难问题** | TCP 重传、乱序、窗口、握手失败 |
| **应用行为异常** | 看应用层的实际请求和响应 |
| **间歇性故障** | 长时间抓包，事后分析 |
| **安全事件取证** | 保留证据 |

**★ 什么时候【不】需要抓包**：
- 症状已经明确指向某个配置问题（先查配置更快）
- 用 `show` 命令能直接验证的假设
- **抓包成本高（存储、CPU、时间），是最后手段，不是第一手段**

---

## ② 三种抓包方式对比

| | **SPAN（端口镜像）** | **IOS EPC（内嵌抓包）** | **NetFlow** |
|:--|:--|:--|:--|
| 抓什么 | **完整数据包** | **完整数据包** | **流的元数据** |
| 抓在哪 | 交换机镜像到目的口 | **设备自己抓到内存/闪存** | 设备统计 |
| 需要额外设备 | ✅ 需要抓包主机 | ❌ 不需要 | 需要采集器 |
| 数据量 | **巨大** | 中（受缓冲区限制） | **小** |
| 设备开销 | 中-高 | **中**（占 CPU 和内存） | 低 |
| 适合 | 长时间、大流量分析 | ★ **快速排障** | 长期趋势、流量成分 |

## ③ SPAN / RSPAN / ERSPAN

### 3.1 本地 SPAN

**把一个或多个端口的流量复制到另一个端口。**

```cisco
! ── 基本配置 ──
SW1(config)# monitor session 1 source interface GigabitEthernet1/0/5 ★ both ★
SW1(config)# monitor session 1 destination interface GigabitEthernet1/0/48

! ── 镜像整个 VLAN ──
SW1(config)# monitor session 1 source vlan 10 both
SW1(config)# monitor session 1 destination interface Gi1/0/48

! ── 只镜像某个方向 ──
SW1(config)# monitor session 1 source interface Gi1/0/5 ★ rx ★     ! 只收
SW1(config)# monitor session 1 source interface Gi1/0/5 ★ tx ★     ! 只发

! ── 多个源 ──
SW1(config)# monitor session 1 source interface Gi1/0/5 - 10 both

! ── 目的口保留 VLAN 标签（分析 VLAN 时需要）──
SW1(config)# monitor session 1 destination interface Gi1/0/48 ★ encapsulation replicate ★

! ── 目的口允许正常收发（少见，用于把抓包机接在生产口）──
SW1(config)# monitor session 1 destination interface Gi1/0/48 ingress vlan 10

! ── 查看与清除 ──
SW1# ★ show monitor session 1 ★
SW1# show monitor session all
SW1(config)# no monitor session 1
```

**验证**：
```cisco
SW1# show monitor session 1
Session 1
---------
Type                   : Local Session
Source Ports           :
    Both               : Gi1/0/5
Destination Ports      : Gi1/0/48
    Encapsulation      : Native
          Ingress      : Disabled
```

### 3.2 RSPAN（跨交换机）

**源和目的在不同的交换机上，用一个特殊的 VLAN 承载镜像流量。**

```cisco
! ── ① 创建 RSPAN VLAN（所有相关交换机都要建）──
SW1(config)# vlan 999
SW1(config-vlan)#  name RSPAN-VLAN
SW1(config-vlan)#  ★ remote-span ★

SW2(config)# vlan 999
SW2(config-vlan)#  name RSPAN-VLAN
SW2(config-vlan)#  remote-span

! ── ② 源交换机 ──
SW1(config)# monitor session 1 source interface GigabitEthernet1/0/5 both
SW1(config)# monitor session 1 ★ destination remote vlan 999 ★

! ── ③ 目的交换机 ──
SW2(config)# monitor session 1 ★ source remote vlan 999 ★
SW2(config)# monitor session 1 destination interface GigabitEthernet1/0/48

! ── ④ 中间的 Trunk 必须放行 VLAN 999 ──
SW1(config)# interface GigabitEthernet1/0/24
SW1(config-if)# switchport trunk allowed vlan add ★ 999 ★
```

### 3.3 ERSPAN（跨三层）

**把镜像流量封装成 GRE，可以跨路由网络传输。**

```cisco
! ── 源设备 ──
SW1(config)# monitor session 1 ★ type erspan-source ★
SW1(config-mon-erspan-src)#  source interface GigabitEthernet1/0/5 both
SW1(config-mon-erspan-src)#  no shutdown
SW1(config-mon-erspan-src)#  destination
SW1(config-mon-erspan-src-dst)#   ★ erspan-id 100 ★
SW1(config-mon-erspan-src-dst)#   ip address 10.1.30.230           ! 抓包主机
SW1(config-mon-erspan-src-dst)#   origin ip address 10.1.1.1       ! 本机
SW1(config-mon-erspan-src-dst)#   ★ mtu 1500 ★

! ── 目的设备（如果目的也是 Cisco 设备）──
SW2(config)# monitor session 2 ★ type erspan-destination ★
SW2(config-mon-erspan-dst)#  destination interface GigabitEthernet1/0/48
SW2(config-mon-erspan-dst)#  no shutdown
SW2(config-mon-erspan-dst)#  source
SW2(config-mon-erspan-dst-src)#   erspan-id 100
SW2(config-mon-erspan-dst-src)#   ip address 10.1.30.230

! ── 或者直接让 Wireshark 解 ERSPAN ──
! Wireshark 能直接解析 ERSPAN 封装（Decode As → ERSPAN）
```

### 3.4 ★ SPAN 的五个注意事项

**① 目的口的带宽必须足够**
```
   镜像一个千兆口的【双向】流量
        ↓
   目的口需要 ★ 2Gbps ★ 才不丢
        ↓
   ★ 实践：用万兆口做目的口，或只镜像单向 ★
```

**② 目的口被独占**
```cisco
SW1# show interfaces GigabitEthernet1/0/48 status
Gi1/0/48   Status: ★ monitoring ★
! ★ 该口不再参与正常转发 ★
```

**③ 会话数量有限**
```cisco
SW1# show monitor session all
! 多数平台只支持 2-4 个本地 SPAN 会话
```

**④ 高流量下 SPAN 本身会丢包**
```
   源口流量 900Mbps 双向 = 1.8Gbps
   目的口只有 1Gbps
        ↓
   ★ 抓到的不是完整的流量 ★
        ↓
   分析结论可能是错的
```

**⑤ 对设备有性能影响**
在高负载设备上开 SPAN 要谨慎，可能影响正常转发。

## ④ IOS EPC（Embedded Packet Capture）★ 最实用

**设备自己抓包，不需要额外的抓包主机。**

### 4.1 基本流程

```cisco
! ── ① 定义抓包点（capture point）──
R1# ★ monitor capture CAP interface GigabitEthernet0/0 both ★

! 或者抓控制平面的流量
R1# monitor capture CAP control-plane both

! ── ② 定义过滤条件（★ 强烈建议，否则数据量爆炸）──
R1# ★ monitor capture CAP match ipv4 any any ★
! 或用 ACL 精确过滤
R1(config)# ip access-list extended CAP-FILTER
R1(config-ext-nacl)#  permit tcp host 192.168.10.10 host 10.1.30.50 eq 8080
R1# monitor capture CAP ★ access-list CAP-FILTER ★

! ── ③ 设置缓冲区 ──
R1# monitor capture CAP buffer size 10                  ! 10 MB
R1# monitor capture CAP buffer circular                 ! 循环覆盖
R1# monitor capture CAP limit packets 1000              ! 最多 1000 个包
R1# monitor capture CAP limit duration 60                ! 抓 60 秒

! ── ④ 开始 ──
R1# ★ monitor capture CAP start ★

! ── ⑤ 复现问题 ──

! ── ⑥ 停止 ──
R1# ★ monitor capture CAP stop ★

! ── ⑦ 查看 ──
R1# ★ show monitor capture CAP buffer brief ★
R1# show monitor capture CAP buffer detailed
R1# show monitor capture CAP buffer dump

! ── ⑧ 导出到 pcap（用 Wireshark 分析）──
R1# ★ monitor capture CAP export flash:cap.pcap ★
R1# monitor capture CAP export tftp://10.1.30.220/cap.pcap

! ── ⑨ 清理 ──
R1# no monitor capture CAP
```

### 4.2 输出示例

```cisco
R1# show monitor capture CAP buffer brief
 ----------------------------------------------------------------------------
  #   size   timestamp     source             destination      protocol
 ----------------------------------------------------------------------------
    0   74    0.000000     192.168.10.10  ->  10.1.30.50       TCP
    1   74    0.000123     192.168.10.10  ->  10.1.30.50       TCP
    2   74    3.001456     192.168.10.10  ->  10.1.30.50       TCP
    3   74    9.002789     192.168.10.10  ->  10.1.30.50       TCP
 ----------------------------------------------------------------------------
```

**★ 从这个输出能看出什么**：
- 只有**去程**的包，**没有回程** → 对端没响应或回程被拦
- 时间间隔 0、3、9 秒 → **TCP SYN 重传的指数退避** → 确认是"发出去没回应"

```cisco
R1# show monitor capture CAP buffer detailed
 ----------------------------------------------------------------------------
 #   size   timestamp     source             destination      protocol
 ----------------------------------------------------------------------------
   0  74     0.000000     192.168.10.10  ->  10.1.30.50       TCP
0000:  00505600 AABB0011 22334455 08004500  .PV......"3DU..E.
0010:  003C1234 40004006 A1B2C0A8 0A0A0A01  .<.4@.@.........
0020:  1E32C822 1F900000 00010000 0000A002  .2."............
0030:  FFFF1234 00000204 05B40402 080A0000  ...4............
                    ↑
              ★ TCP 标志位：0x02 = SYN ★
```

### 4.3 ★ EPC 的优势

| 优势 | 说明 |
|:--|:--|
| **不需要额外设备** | 在设备上直接抓 |
| **不占用端口** | 不像 SPAN 要独占一个口 |
| **能抓控制平面** | `control-plane both`（SPAN 抓不到） |
| **可远程操作** | SSH 上去就能抓 |
| **可导出 pcap** | 用 Wireshark 深度分析 |

### 4.4 EPC 的限制

| 限制 | 说明 |
|:--|:--|
| 缓冲区有限 | 通常几 MB 到几十 MB |
| **占用 CPU 和内存** | 高流量下影响性能 |
| 平台差异大 | 不同型号支持的功能不同 |
| **必须加过滤** | 否则缓冲区几秒就满 |

**★ 生产环境用 EPC 的规范**：
```cisco
! ① 必须加精确的过滤条件
R1(config)# ip access-list extended CAP-FILTER
R1(config-ext-nacl)#  permit ip host <特定源> host <特定目的>

! ② 限制时长和包数
R1# monitor capture CAP limit duration 60 packets 1000

! ③ 用完立即删除
R1# no monitor capture CAP
```

## ⑤ Wireshark 实战

### 5.1 必备过滤器

```
# ── 基础 ──
ip.addr == 192.168.10.10                    # 某个 IP（源或目的）
ip.src == 192.168.10.10                     # 源
ip.dst == 10.1.30.50                        # 目的
tcp.port == 8080                            # 端口
tcp.stream eq 5                             # ★ 追踪某个 TCP 流

# ── ★ TCP 问题诊断（最有用的几个）★ ──
★ tcp.analysis.retransmission ★             # 重传（丢包）
★ tcp.analysis.duplicate_ack ★              # 重复 ACK
★ tcp.analysis.out_of_order ★               # 乱序
★ tcp.analysis.zero_window ★                # 零窗口（接收端处理不过来）
★ tcp.analysis.flags ★                      # 所有 TCP 异常
tcp.flags.reset == 1                        # RST（连接被拒绝/中断）
tcp.flags.syn == 1 && tcp.flags.ack == 0    # 只有 SYN（连接请求）

# ── ★ 时间分析 ★ ──
tcp.time_delta > 1                          # 同一流中间隔 > 1 秒的包
frame.time_delta > 1                        # 任意相邻包间隔 > 1 秒

# ── ★ MTU 问题 ★ ──
icmp.type == 3 && icmp.code == 4            # ★ Fragmentation Needed
ip.flags.df == 1 && ip.len > 1400           # 大的 DF 包

# ── 应用层 ──
http.response.code >= 400                   # HTTP 错误
dns                                         # DNS 查询
dns.flags.rcode != 0                        # DNS 错误响应

# ── 网络协议 ──
ospf                                        # OSPF
bgp                                         # BGP
eigrp                                       # EIGRP
stp                                         # STP BPDU
vrrp || hsrp                                # FHRP
arp.duplicate-address-detected              # ★ ARP 冲突

# ── VLAN / 封装 ──
vlan.id == 10                               # 某个 VLAN
gre                                         # GRE 隧道
esp                                         # IPsec ESP
vxlan                                       # VXLAN
```

### 5.2 ★ 判断"网络慢"还是"服务器慢"

**这是网络工程师最有价值的分析能力。**

**在 Wireshark 中**：
```
   Statistics → Conversations → TCP 标签
   或用过滤器：tcp.stream eq <流号>
```

**看时间戳**：
```
   No.  Time      Source          Destination     Protocol  Info
   1    0.000000  192.168.10.10   10.1.30.50      TCP       ★ [SYN] ★
   2    0.015234  10.1.30.50      192.168.10.10   TCP       ★ [SYN, ACK] ★
                  ↑ ★ 15ms = 网络往返时间（RTT），正常 ★
   3    0.015456  192.168.10.10   10.1.30.50      TCP       [ACK]
   4    0.016789  192.168.10.10   10.1.30.50      HTTP      GET /erp/index
   5    ★ 8.523456 ★ 10.1.30.50   192.168.10.10   HTTP      HTTP/1.1 200 OK
        ↑↑↑↑↑↑↑↑↑
   ★★ 服务器处理了 8.5 秒！网络往返只有 15ms ★★
```

**★ 结论**：
```
   RTT（SYN → SYN/ACK）= 15ms        → 网络正常
   请求 → 响应 = 8.5 秒               → ★ 服务器慢 ★
   
   ★ 网络工程师的任务完成了：用数据证明不是网络问题 ★
```

**反过来的情况**：
```
   No.  Time      Info
   1    0.000000  [SYN]
   2    ★ 0.450000 ★ [SYN, ACK]
        ↑ ★ 450ms RTT！网络延迟高 ★
   ...
   10   1.234567  [TCP Retransmission]              ← ★ 有重传 = 丢包 ★
   11   1.456789  [TCP Dup ACK]
   
   ★ 结论：网络有延迟和丢包 ★
```

### 5.3 常见问题的抓包特征

| 问题 | 抓包特征 |
|:--|:--|
| **服务未启动** | SYN → **RST, ACK** |
| **被防火墙 drop** | SYN → **无任何响应**，SYN 重传（0s、3s、9s、21s） |
| **★ MTU 黑洞** | 小包正常，大包发出后**无响应**；或看到 **ICMP type 3 code 4** |
| **丢包** | 大量 `[TCP Retransmission]` 和 `[TCP Dup ACK]` |
| **乱序** | `[TCP Out-Of-Order]` |
| **接收端处理不过来** | `[TCP Window Full]`、`[TCP ZeroWindow]` |
| **应用层慢** | 请求和响应之间时间间隔大，但 RTT 正常 |
| **DNS 慢** | DNS 查询到响应间隔大，或 **AAAA 查询无响应** |
| **ARP 冲突** | 同一 IP 有多个不同 MAC 的 ARP 响应 |
| **路由环路** | 同一个包反复出现，TTL 递减 |

### 5.4 有用的统计视图

```
   Statistics → ★ Conversations ★
      按会话统计流量、包数、持续时间
      → 找出流量大户
   
   Statistics → ★ Protocol Hierarchy ★
      协议分布
      → 看流量成分
   
   Statistics → ★ IO Graph ★
      流量随时间的变化
      → 看突发、看丢包时刻
   
   Statistics → ★ TCP Stream Graphs ★ → Time Sequence
      TCP 序列号随时间的变化
      → ★ 直观看出重传、窗口、停顿 ★
   
   Statistics → ★ Service Response Time ★
      应用响应时间统计
```

## ⑥ 抓包位置的选择（★ 关键决策）

**在哪抓，决定了你能看到什么。**

```
   PC ──① SW3 ──② SW1 ──③ R3 ──④ R1 ──⑤ ISP ── Server
```

| 抓包位置 | 能看到 | 适合诊断 |
|:--|:--|:--|
| **① 靠近 PC** | 客户端发出的原始报文 | 客户端行为、是否真的发出请求 |
| **② 接入/汇聚** | 二层信息、VLAN 标签 | VLAN、ARP、STP、DHCP |
| **③ 核心** | 路由后的流量 | 路由、QoS 标记 |
| **④ 出口** | ★ NAT 前后、加密前后 | NAT、VPN、出口 ACL |
| **⑤ 靠近服务器** | 服务器实际收到的 | 服务器侧问题 |

### ★ 二分法抓包

```
   ① 先在【中间】抓（比如核心 R3）
        ↓
   看到请求了吗？
        ├─ ★ 看到了 ★ → 问题在 R3 右边（往服务器方向）
        │              → 去 ④ 或 ⑤ 抓
        └─ ★ 没看到 ★ → 问题在 R3 左边（往客户端方向）
                       → 去 ① 或 ② 抓
```

**★ 同时在两个点抓，对比差异**：
```cisco
! 在 R1 的内网口抓（NAT 前）
R1# monitor capture CAP-IN interface Gi0/0 both
R1# monitor capture CAP-IN match ipv4 any any
R1# monitor capture CAP-IN start

! 在 R1 的外网口抓（NAT 后）
R1# monitor capture CAP-OUT interface Gi0/1 both
R1# monitor capture CAP-OUT match ipv4 any any
R1# monitor capture CAP-OUT start

! 对比：进来的包和出去的包，源地址变了吗？
```

## ⑦ 实战案例

### 案例 1：证明"不是网络的问题"

**背景**：应用团队说"网络慢导致 ERP 打不开"。

```cisco
! 在核心交换机上抓包
R3# monitor capture CAP interface Gi0/1 both
R3(config)# ip access-list extended CAP-ERP
R3(config-ext-nacl)#  permit tcp host 192.168.10.10 host 10.1.30.50
R3# monitor capture CAP access-list CAP-ERP
R3# monitor capture CAP buffer size 10
R3# monitor capture CAP start
! 让用户复现
R3# monitor capture CAP stop
R3# monitor capture CAP export flash:erp.pcap
```

**Wireshark 分析**：
```
   No.  Time        Source          Destination     Info
   1    0.000000    192.168.10.10   10.1.30.50      [SYN]
   2    ★0.008234★  10.1.30.50      192.168.10.10   [SYN, ACK]
        ↑ ★ RTT = 8ms，网络非常好 ★
   3    0.008456    192.168.10.10   10.1.30.50      [ACK]
   4    0.009123    192.168.10.10   10.1.30.50      GET /erp/login HTTP/1.1
   5    ★12.456789★ 10.1.30.50      192.168.10.10   HTTP/1.1 200 OK
        ↑↑↑↑↑↑↑↑↑↑
   ★★ 服务器处理了 12.4 秒 ★★
```

**★ 给应用团队的结论**：
```
   网络往返时间（RTT）：8 毫秒 —— 优秀
   TCP 握手：正常，无重传
   无丢包、无乱序
   ★ 但服务器从收到 HTTP 请求到返回响应，用了 12.4 秒 ★
   
   ★ 结论：网络传输正常，瓶颈在服务器端处理 ★
   建议检查：数据库慢查询、应用线程池、服务器 CPU/内存/磁盘 IO
   
   证据：erp.pcap（附件）
```

**★ 这份结论比"我们查过了网络没问题"有力得多。**

### 案例 2：定位 MTU 黑洞

**背景**：用户报"网页打不开一半"。

```cisco
! 在隧道两端抓包
R1# monitor capture CAP interface Tunnel0 both
R1# monitor capture CAP match ipv4 any any
R1# monitor capture CAP start
! 复现
R1# monitor capture CAP stop
R1# monitor capture CAP export flash:mtu.pcap
```

**Wireshark 中的特征**：
```
# 过滤器
icmp.type == 3 && icmp.code == 4

   No.  Source      Destination    Info
   45   10.0.13.3   192.168.10.10  ★ Destination unreachable (Fragmentation needed) ★
                                     ★ MTU of next hop: 1400 ★
```

**如果连这个 ICMP 都看不到**（被中间设备拦了）：
```
# 特征：大包发出去没有任何响应
ip.len > 1400 && tcp.flags.push == 1

   No.  Time      Source          Destination     Length   Info
   30   1.234567  192.168.10.10   10.1.30.50      ★ 1514 ★  [PSH, ACK]
   31   4.234567  192.168.10.10   10.1.30.50      1514     [TCP Retransmission]
   32   10.234567 192.168.10.10   10.1.30.50      1514     [TCP Retransmission]
   ! ★ 大包反复重传，没有响应，也没有 ICMP → PMTUD 黑洞 ★
   
   ! 同时，小包正常
   28   1.100000  192.168.10.10   10.1.30.50      ★ 60 ★     [ACK]
   29   1.105000  10.1.30.50      192.168.10.10   60       [ACK]
```

**★ 结论**：路径 MTU 不足 + ICMP unreachable 被拦 = PMTUD 黑洞。

**修复**：
```cisco
R1(config)# interface Tunnel0
R1(config-if)# ip mtu 1400
R1(config-if)# ip tcp adjust-mss 1360
! 同时放行 ICMP unreachable
```

### 案例 3：ARP 冲突

**背景**：某个 IP 时通时不通。

```cisco
SW1# monitor capture CAP interface Vlan10 both
SW1# monitor capture CAP match any
SW1# monitor capture CAP start
```

**Wireshark 过滤器**：
```
arp.duplicate-address-detected
```

```
   No.  Source MAC          Info
   12   00:50:56:AA:BB:CC   ARP: 192.168.10.50 is at 00:50:56:AA:BB:CC
   15   ★00:11:22:33:44:55★ ARP: 192.168.10.50 is at ★00:11:22:33:44:55★
        ↑ ★ 同一个 IP，两个不同的 MAC → IP 地址冲突 ★
```

**定位**：
```cisco
SW1# show mac address-table address 0011.2233.4455
  10    0011.2233.4455    DYNAMIC     ★ Gi1/0/15 ★
!                                       ↑ 找到冲突设备接在哪个口
```

**预防**：部署 DHCP Snooping + DAI + IPSG。

## ⑧ 抓包的注意事项

### 安全与合规

```
   ★ 抓包会捕获所有明文数据，包括：
      · 用户名密码（HTTP、Telnet、FTP、SNMP v1/v2c）
      · 业务数据（可能含个人信息、商业机密）
      · 内部网络结构
   
   ★ 必须遵守：
      □ 抓包前获得授权
      □ 只抓必要的流量（★ 用精确的过滤条件）
      □ pcap 文件加密存储
      □ 分析完及时删除
      □ 不要把 pcap 传到外部服务/公网
      □ 遵守公司的数据合规要求（GDPR、等保等）
```

### 性能影响

```cisco
! ★ 用完立即清理 ★
R1# monitor capture CAP stop
R1# no monitor capture CAP

SW1(config)# no monitor session 1

! 检查是否有遗留的抓包会话
R1# show monitor capture
SW1# show monitor session all
```

**★ 忘记关闭抓包会话是常见的运维事故**——长期占用 CPU/内存/端口。

### 存储管理

```cisco
R1# dir flash: | include pcap
R1# delete flash:cap.pcap
R1# show flash: | include free
```

## ⑨ 抓包决策树

```
   遇到问题
        ↓
   ★ show 命令能验证假设吗？★
        ├─ 能 → ★ 用 show 命令（更快）★
        └─ 不能 → 继续
             ↓
   ★ 需要看包的内容吗？★
        ├─ 只需要知道"谁在用带宽" → ★ NetFlow ★
        ├─ 需要看协议交互细节 → 继续
        └─ 需要长期趋势 → ★ SNMP/监控 ★
             ↓
   ★ 在哪抓？★
        ├─ 设备上快速抓 → ★ IOS EPC ★（首选）
        ├─ 需要长时间大流量 → ★ SPAN + 抓包主机 ★
        └─ 跨三层 → ★ ERSPAN ★
             ↓
   ★ 加精确的过滤条件 ★（必须！）
             ↓
   抓 → 分析 → ★ 清理 ★
```
