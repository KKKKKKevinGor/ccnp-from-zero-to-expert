# Stage 5 · 排障方法论

> **这一篇不教技术，教思维方式。**
>
> 技术会过时（IOS 会更新，协议会演进），但**排障的思维框架不会**。掌握它，你面对任何陌生的故障都有下手的地方。

## 为什么单独讲方法论

**观察一个现象**：同样一个故障，有人 5 分钟定位，有人查 3 小时还在瞎试。

**差别不在知识量，在方法。**

```
   ✗ 业余做法：
      "试试重启？"
      "试试改改这个参数？"
      "把 ACL 删了看看？"
      → 靠运气，改坏了还不知道
   
   ✅ 专业做法：
      精确描述现象 → 确定范围 → 分层定位 → 提出假设 → ★ 用命令验证假设 ★ → 修复 → 验证
      → 每一步都有依据，可复现，可交接
```

## 排障的三个层次

```
   ★ L1 会查 ★
      知道 show 命令，能看懂输出
      → 能解决"教科书上有的"故障
        ↓
   ★ L2 会推 ★
      看到症状能推出可能的根因，能设计验证方案
      → 能解决"没见过但有规律"的故障
        ↓
   ★★ L3 会防 ★★
      从故障中提炼模式，改进架构和流程
      → 让同类故障不再发生
```

**大多数人停在 L1。** 这一篇的目标是带你到 L2，并给出通往 L3 的方法。

## 核心信条

> **1. 精确的描述本身就包含 50% 的答案。**
> "A 能 ping B，B 不能 ping A" ≠ "网络不通"
>
> **2. 80% 的故障是变更引起的。**
> 第一个问题永远是"什么时候开始的？改了什么？"
>
> **3. 影响范围决定问题在哪一层。**
> 一台机器 vs 一个 VLAN vs 一栋楼 vs 全网
>
> **4. 不要凭猜测改配置。先用命令证明你的假设。**
> 瞎改是运维事故的主要来源。
>
> **5. 分层排除，每一层都有明确的验证手段。**
> L1 看接口，L2 看 MAC/VLAN，L3 看路由，L4 看端口。
>
> **6. 能通的和不能通的对比，差异就是线索。**
> 这是最有效的方法之一。
>
> **7. 修复后必须验证，并记录。**
> 没记录的排障 = 下次还要重来一遍。
